# EggMail design

Status: design phase, no code. Source of truth for individual choices is [decisions.md](decisions.md); this document explains how they fit together. Items marked **unverified** were not confirmed against a primary source; defaults marked **proposed** are the design authors' choices.

## 1. Goals and scope

EggMail is an open-source, self-hosted outbound email server: SMTP ingress, HTTP API, delivery tracking, webhooks and a dashboard. It also receives mail for domains its tenants enable, routes it to webhooks, forwards, storage or the bin, and verifies it with SPF, DKIM, DMARC and ARC ([section 11](#11-inbound-mail)). Primary goal: the fastest SMTP server, claimed only after reproducible measurement ([benchmarks.md](benchmarks.md)). Target runtime: .NET 10 LTS (supported to 2028-11-14), deployed as a Docker image.

"Fastest" is scoped to **SMTP ingest** (accept) throughput and latency, reported separately from outbound delivery.

**Design principle 1: the storage backend changes nothing but storage.** SQLite and PostgreSQL are only a choice of how data is stored persistently and long-term. All features (SMTP/API, DKIM/SPF/DMARC, domain verification, tenants, API keys, suppressions, webhooks, rate limits, warm-up, settings, dashboard pages, ACME/TLS) behave identically on both. How much per-message history is recorded is a separate setting (`History:Mode`), not a property of the backend (§4.1). "Lite" and "Full" are friendly names for the two default presets.

**Design principle 2: performance is a permanent first-class goal on both backends.** The SQLite backend is engineered to perform well for large and high-throughput workloads and is not treated as a toy; optimization work applies to both, and each is benchmarked separately with the identical feature set ([benchmarks.md](benchmarks.md)).

## 2. Architecture

### 2.1 Build boundary

Hand-written, using only the BCL and ASP.NET Core shared framework (no package references, enforced by a CI check on `project.assets.json`):

- SMTP server and client: BDAT/CHUNKING, full SMTPUTF8, PIPELINING, SIZE, 8BITMIME, ENHANCEDSTATUSCODES, STARTTLS, AUTH PLAIN/LOGIN
- MIME parse and build
- DKIM sign and verify (RSA-2048 only, `rsa-sha256`)
- SPF, DMARC, DSN/ARF
- DNS client (UDP/TCP wire format, EDNS0, MX/A/AAAA/TXT/TLSA/PTR/CNAME, caching, retries; talks to a local validating resolver)
- MTA-STS, TLS-RPT, DANE
- ARC is optional and deferrable

Allowed libraries elsewhere: Npgsql + EF Core, Microsoft.Data.Sqlite, Certes (ACME), OpenTelemetry with OTLP, ASP.NET Core Data Protection, the dashboard frontend stack, and test tooling (MimeKit and MailKit as test oracles only).

The one carve-out from "no external binaries": DANE uses a local validating resolver (Unbound on loopback), because the DNS client cannot validate DNSSEC and the AD bit is only trustworthy from a local validator.

### 2.4 Shared vs provider-specific

Shared (identical on both backends): SMTP server/client, MIME, DKIM/SPF/DMARC, DNS, scheduler logic, routing, rate limits and warm-up, webhook dispatch, API, auth, tenants, domain verification, all dashboard pages, secrets handling, TLS/ACME, observability, config and stats stores, history and content logic, retention policy, and the backend-switch engine.

Provider-specific (storage mechanics only): queue claim SQL and leases, the writer model (per-file writers on SQLite, pooled concurrent writers on PostgreSQL), partition management vs batched-delete executors, sync/WAL tuning, migrations.

Two EF Core providers, one `DbContext`, a separate migrations assembly per provider selected by configuration. Branch on `migrationBuilder.ActiveProvider` for partition DDL, which exists only in the Postgres migration. Isolate provider-specific annotations in a per-provider model hook (the EF docs do not cover them in a shared model; **unverified** which behave). CI runs `has-pending-model-changes` once per provider; `Migrate()` throws on pending changes in EF 9+. The test matrix doubles; SQLite tests are fast and are the default for local development.

## 3. SMTP stack and performance design

- **Pipelines-based server.** Copy Kestrel's zero-byte-read default (`WaitForDataBeforeAllocatingBuffer`) so idle connections hold no buffer; cap read/write buffers explicitly (Kestrel defaults are 1 MiB and 64 KiB). Always call `AdvanceTo(consumed, examined)` and never touch a `ReadOnlySequence` afterwards.
- **DATA path.** Scan for `\r\n.\r\n` incrementally with `SearchValues<byte>`. The body is buffered in memory up to `Smtp:MaxMessageSize` (default 25 MiB on both backends) behind a **global in-flight bytes budget**; when exhausted, reply `452`. Objects of 85,000 bytes or more land on the large object heap. Start with EF `byte[]`; use Npgsql directly for the body insert only if profiling shows LOH pressure (owner permission for raw Npgsql is an open question).
- **Smuggling and STARTTLS hardening.** Only `\r\n` ends a line; reject bare CR/LF and NUL with a 5xx and close; end DATA only on `\r\n.\r\n`. On STARTTLS, if the reader holds any bytes beyond the command line, close the connection; rebuild pipes over `SslStream` and reset session state (RFC 3207 §4.2). The client must re-EHLO after TLS and ignore the pre-TLS capability list. The client never emits a bare CR/LF.
- **Group commit.** One writer per database file drains queued commands into one transaction so the per-commit cost (an fsync under SQLite `Normal`/`Full` or a PostgreSQL commit; transaction overhead under the SQLite default `Off`) is amortized across many messages. `250` is sent only after the commit returns. On PostgreSQL, events are buffered in a channel and flushed every few milliseconds, and claims fetch N rows per round trip.
- **TLS.** One shared `SslServerAuthenticationOptions` and certificate; stable `TargetHost` on outbound so session resumption works.
- **GC.** Start with workstation non-concurrent GC below 2 cores and server GC with DATAS above; decide from benchmarks.
- **EF Core on the hot path.** Use `AddPooledDbContextFactory` with a short-lived context per batch (never per message, never long-lived in a worker); `AsNoTracking`, `ExecuteUpdate`/`ExecuteSql`, `SqlQuery<T>`, compiled queries for fixed lookups. EF costs several KB per operation even when tuned, so the per-message allocation budget applies to the SMTP/protocol path; the database layer has its own proposed budget (see [benchmarks.md](benchmarks.md)).

## 4. Storage

### 4.1 Backends, history level and presets

**Principle: SQLite vs PostgreSQL is only a storage-backend choice.** Every feature behaves identically on both backends: SMTP and API, DKIM/SPF/DMARC and domain verification, tenants, API keys, suppressions, webhooks, rate limits, warm-up, settings, dashboard pages, ACME/TLS, retries, routing. The backend decides only *how data is stored persistently and long-term* (and the operational characteristics that follow from that, §4.2). A feature is never gated on the backend; where a capability depends on what data is recorded, it depends on a separate, orthogonal setting.

Two orthogonal settings:

| Setting | Values | Meaning |
|---|---|---|
| `Storage:Backend` | `Sqlite` \| `Postgres` | Where data is stored. **Default: `Sqlite`** (owner-decided), so the single-container quick start works with no external database; PostgreSQL is selected by configuration in the same image ([release.md](release.md)) |
| `History:Mode` | `StatsOnly` \| `Full` | How much per-message history is recorded |

**Any combination is allowed:** SQLite + `Full` history, PostgreSQL + `StatsOnly`, SQLite + `StatsOnly` and PostgreSQL + `Full`. The default is `History:Mode=Full` on both backends (below).

`History:Mode`:

| | `StatsOnly` | `Full` |
|---|---|---|
| Aggregated statistics (hourly/daily counters per tenant, sending domain, recipient-domain bucket; §4.5) | yes | yes |
| Recent-events ring (`History:RecentEvents`, default 1,000, content-free, recipient domain only) | yes | yes (alongside full events) |
| Per-message events, timeline, search | no | yes (`Retention:MetadataDays`) |
| Stored content, retained raw, view and resend (§5) | no | yes (`Content:*` settings) |
| Bounce correlation | stateless signed VERP token (tenant id, domain id, timestamp, destination-domain tag, HMAC); the recipient to suppress comes from the DSN's `Final-Recipient` or `Original-Recipient` and must lie in the destination domain the token was issued for (decision 92) | same token, additionally linked to the message's rows; the recipient must also be a recipient of the message whose `Message-ID` the report quotes, attempted in the hour the token was issued (decisions 112 and 113) |
| Send response | returns an id, for log correlation only | returns an id that resolves to the message |

Everything not listed in this table (queue, delivery, suppressions, webhooks, domain verification, authentication, all settings) is identical in both history modes. The dashboard shows the same pages on every backend; pages that need per-message history show an explanatory state when `History:Mode=StatsOnly`, and the UI reads `History:Mode` from a capabilities endpoint (never the backend). Per-message API lookups made in `StatsOnly` return `410 Gone` with code `history_not_recorded` (error body and the other cases in §5.2). That reflects data that was never recorded, not a missing feature of the backend.

**Presets (unified defaults, owner-decided).** "Lite" and "Full" remain friendly names, now for the two storage backends' default deployment shapes: **Lite = the SQLite backend (the default backend), Full = the PostgreSQL backend.** They have **exactly the same defaults for every behavioural setting.** Only storage-backend characteristics differ (§4.2), and backend-specific storage tuning defaults (the SQLite sync pragmas, connection-pool sizes, partition granularity) are not behavioural settings.

The single default set, on both backends (names marked proposed; values are the earlier Full-preset values unless noted):

| Setting | Default | Notes |
|---|---|---|
| `History:Mode` | **`Full`** | **DESIGN-DECIDED** (the owner delegated the value). Justification below |
| `History:RecentEvents` | 1,000 | |
| `Retention:MetadataDays` | 30 | `0` = keep forever (§5.1) |
| `Content:Mode` / `Content:RetentionDays` | `Retain` / 7 | subject + text + html + attachment index; range 6–30 |
| `Content:StoreAttachments` | `false` | `Content:AllowAttachmentStorage` master switch also `false` |
| `Content:MaxStoredBodyBytes` | 256 KiB | |
| `Stats:*` | 30 days hourly, 400 days daily, top-20/top-10 domains, 200,000 series | |
| `Queue:MaxLifetime` (proposed name) | 5 days | |
| `Smtp:MaxMessageSize` (proposed name) / recipients | 25 MiB / 50 | |
| `Webhooks:*` | 7-day outbox and attempt-log retention, 15 s timeout, concurrency 4, HTTPS only | |

Backend-specific storage defaults (not behavioural, and not changed by the other backend): SQLite: `Sqlite:SyncMode=Off`, `Sqlite:ConfigSyncMode=Full`, `Sqlite:QueuePersistence=Persistent`; PostgreSQL: `Mail__Database__Migrate=Auto`, pool sizes, day partitions.

**Why `History:Mode=Full` is the default.** (1) EggMail's product is delivery tracking: the dashboard's message search, timeline and resend work out of the box. (2) The owner wanted identical behavior on both backends, so a single default must serve both, and tracking is the behavior users expect from an outbound email service. (3) `StatsOnly`, the lightweight "fire-and-forget, no per-message record" option the owner asked for earlier, stays one setting away and is documented as such. (4) Switching backends then changes nothing. The cost, stated plainly: `Full` writes more per message (events, content, optionally attachments) and stores personal data (subject and body) for the content retention period (7 days by default); operators who do not want that set `History:Mode=StatsOnly` or `Content:Mode=None`. On the SQLite backend `Full` also means more writes and a larger `history.db`. Benchmarks publish both history levels ([benchmarks.md](benchmarks.md)). The value is easy to flip if the owner prefers `StatsOnly` as the single default. **Open question, flagged rather than changed:** now that SQLite is the default backend, `History:Mode=Full` is also the default for the single-container quick start, which writes events and content into `history.db` by default; whether that conflicts with the quick start's size and performance expectations is **unmeasured** ([open-questions.md](open-questions.md)).

Switching backends never changes behavior silently: the migration tool records the *effective* values of all settings in the bundle and writes them explicitly into the target (§4.6).

### 4.2 Backend characteristics (not feature differences)

These are properties of the storage engines. They affect scale and operations, never what EggMail can do.

| Characteristic | SQLite backend | PostgreSQL backend |
|---|---|---|
| Nodes / replicas | Single node, one replica (single process owns the files) | Several replicas (`SKIP LOCKED` claims) |
| High availability | None built in; backups via `VACUUM INTO`, restore returns the last backup | Managed HA is a deployment prerequisite; `451` during an outage |
| Writes | One writer per database file; single-writer throughput ceiling; group commit | MVCC; many concurrent writers; batching |
| Storage location | Local volume only (WAL does not work on network filesystems) | External server |
| Retention mechanism | Batched `DELETE` plus `incremental_vacuum` (no partition drop) | Day partitions dropped with `DETACH … CONCURRENTLY`, then `DROP` |
| Atomicity | Per file, not across files (§4.4): cross-file effects are idempotent and ordered | One transaction across all tables |
| Durability default | `synchronous=OFF`: process-crash-safe, **not** power-loss-safe; corruption possible on OS crash or power loss (§4.4) | WAL synced at commit (Postgres default) |
| Operational footprint | No external dependency | Managed Postgres, roles, pool sizing, partition job |

The advisory dashboard indicators (§4.4) tell an operator when a backend's characteristics are becoming a constraint. They never trigger a switch.

### 4.3 PostgreSQL backend (EF Core + Npgsql only)

One database, one schema, three roles: **owner** (runs migrations, owns objects), **runtime** (the app; default privileges set with `ALTER DEFAULT PRIVILEGES FOR ROLE <owner>`), and **read-only** (dashboard queries, with `statement_timeout`, e.g. 5 s, and `idle_in_transaction_session_timeout`). One database is kept because a transaction cannot span databases: one transaction writes message, delivery rows, content and event together, and splitting would force an outbox. Minimum PostgreSQL 16; default `postgres:17`. **Managed HA is a deployment prerequisite**; `451` during a database outage is accepted.

Tables:

| Table | Partitioning | Holds / lifetime |
|---|---|---|
| `delivery_queue` | none (live rows only, small) | One row per recipient delivery: id, message_id, recipient, domain, due_at, attempt, lease_owner, lease_until, state, last_error. Row deleted on completion. Own autovacuum settings, lower fillfactor (proposed) |
| `message_spool` | none | Full raw `.eml`, byte-for-byte as accepted, until all recipients are final, then deleted |
| `message_content` | day | (`History:Mode=Full`) Subject, text, html, attachment index (name, type, size), extracted at accept time. Dropped after `Content:RetentionDays` |
| `message_raw_retained` | day | (`History:Mode=Full`, attachment storage on) Raw `.eml` including attachments; written by moving the spool row at the final state in one transaction |
| delivery events | day | (`History:Mode=Full`) 30 days of metadata by default |
| stats, config, webhook, tenant, key, domain, suppression, certificate and ACME-state tables | none | See §4.5, §6, §7.3 |

The schema is identical whatever `History:Mode` is; the history tables are simply left empty in `StatsOnly`.

Rules:

- Retention is partition drop: `DETACH PARTITION … CONCURRENTLY`, then `DROP`. A background in-app job creates partitions ahead under a transaction-level advisory lock (`pg_try_advisory_xact_lock`; session-level locks are incompatible with PgBouncer transaction pooling). `pg_partman` is optional.
- Partition constraints must include the partition key, concurrent detach is not allowed with a DEFAULT partition, and foreign keys into partitioned tables must include the partition key, so references to the big tables are soft. Autovacuum does not analyze partitioned parents; schedule a manual `ANALYZE`. The Npgsql provider has no partition API (efcore.pg#1035), so DDL goes in `migrationBuilder.Sql`.
- **Claim:** native `UPDATE … WHERE id IN (SELECT … FOR UPDATE SKIP LOCKED LIMIT @n) RETURNING …` via `Database.SqlQuery<T>`. Do not compose LINQ over it. A pure-LINQ `ExecuteUpdate` claim (three round trips, loses races under contention) exists only as a test double behind the same interface. **Unverified:** that the Npgsql provider does not wrap `UPDATE … RETURNING` in `SqlQuery<T>`; confirm in a spike.
- **Migrations:** `Mail__Database__Migrate=Auto` by default (EF 9+ takes a database-wide lock, so concurrent startup is safe), or `Never` plus an `mta migrate-db` subcommand and an idempotent SQL script for locked-down setups. Two connection strings: schema owner and runtime. *Implemented* as hand-written, versioned SQL (`Schema/V001__initial.sql`, frozen) applied by one idempotent `DO` block under `pg_advisory_xact_lock`, so the same text serves `Auto`, `mta migrate-db` and a DBA; see [components/storage.md](components/storage.md).
- **Connections:** Npgsql's default pool is 100 per connection string; set explicit sizes (roughly 8–16 claim workers, 16 API, 8 dashboard, 2 maintenance; proposed) and keep the total across replicas under about half of `max_connections`. Enforce with `ALTER ROLE … CONNECTION LIMIT`.
- **Split later only if** sustained volume exceeds roughly 1M messages/day or WAL exceeds roughly 50 GB/day (move events or bodies to a separate instance, accepting an outbox), a compliance rule needs secrets in a separate store, or analytics load belongs on a replica. These thresholds are unsourced rules of thumb.
- **No blob store.** Filesystem, S3 and R2 providers were dropped; bodies live in Postgres `bytea` and restore together with metadata. `IMessageBodyStore` stays so a provider could be added later (about 12–14 weeks, if volume demands it).

### 4.4 SQLite backend (Microsoft.Data.Sqlite)

Single node, one replica, local volume only (WAL does not work on network filesystems). Microsoft.Data.Sqlite 10.0.12 bundles SQLite 3.53.3, so `UPDATE … RETURNING` works; the WAL-reset bug (3.7.0–3.51.2) is fixed in 3.51.3. Everything in §4.1 applies: this backend runs every feature, with the same defaults as the PostgreSQL backend (including `History:Mode=Full`).

**Database files, each with its own WAL and its own writer:**

| File | Contents | Sync mode |
|---|---|---|
| `queue.db` | Spool bodies, delivery queue, webhook outbox | `Sqlite:SyncMode`, default **`Off`** |
| `stats.db` | Aggregates, recent-events ring, webhook attempt log | `Sqlite:SyncMode`, default **`Off`** |
| `history.db` | (`History:Mode=Full`, the default; absent under `StatsOnly`) delivery events, content, retained raw | `Sqlite:SyncMode`, default **`Off`** |
| `config.db` | Tenants, API keys, domains, DKIM keys, suppressions, webhook endpoints, settings, certificates and ACME state, Data Protection keys | `Sqlite:ConfigSyncMode`, default `Full` (rarely written) |

The `Off` default for the data files is **owner-decided**. Keeping `config.db` at `Full` is **owner-decided** (it is rarely written and holds DKIM keys, API-key hashes, certificates and ACME state, and the Data Protection key ring, whose loss or corruption would be severe).

**History file layout (DESIGN-DECIDED): one `history.db`, with batched deletes.** SQLite has no partition drop, so retention of events and content cannot be a cheap metadata operation the way it is on PostgreSQL. Options considered:

| | A. Single `history.db` (chosen) | B. Per-day files (`history-YYYYMMDD.db`) | C. Per-day tables in one file |
|---|---|---|---|
| Retention | Batched `DELETE` in short transactions plus `incremental_vacuum`: costs write amplification and WAL churn at high volume | Delete the file: as cheap as a partition drop | `DROP TABLE` per day, then `incremental_vacuum` |
| Writers / WAL | One writer, one WAL | Writer touches only today's file; a WAL per open file | One writer, one WAL |
| Queries across days (search, timelines) | One SQL query | Fan-out over up to retention-window files and merge in the app; or `ATTACH`, whose default limit is 10 databases (compile-time maximum 125; the limit in the bundled SQLite build is **unverified**), too few for a 30-day window | `UNION ALL` views or fan-out; EF cannot map table names that change daily, so raw SQL |
| Schema migrations | One file | Apply to every existing day file, and to a number of files that is unbounded when `Retention:MetadataDays=0` | One file, but daily tables are created dynamically |
| Export and backup | One consistent stream | Old day files are immutable: copy or stream whole files (best for large history) | One file |
| EF Core fit | Plain | One `DbContext` per file, dynamic connection strings | Poor |

Recommendation: **A for v1.** It is the simplest to implement, search and export, keeps the EF model plain and avoids the `ATTACH` limit. Its weakness is retention cost at high volume, mitigated by `WITHOUT ROWID` tables keyed `(day, id)` so expiry is a sequential range delete (proposed), small delete batches off-peak, and `incremental_vacuum`; and at volumes where this still hurts, PostgreSQL's partition drop is the backend characteristic designed for that (§4.2). B is the upgrade path if SQLite history retention proves too expensive: the store interface hides the layout, and day-first keys and UUIDv7 ids (time-ordered, so the day is derivable from an id) keep the move mechanical. C is rejected because of the EF mapping cost. This is a design judgement without measurements; the retention-delete cost under load is a spike item ([open-questions.md](open-questions.md)).

Separate files keep a stats rollup or history retention job from stalling queue commits. That independent-writer property is inferred from per-file WALs; no explicit sqlite.org statement was found (**unverified**). SQLite documents that a transaction across several databases in WAL mode is atomic per file but not as a set, so **every cross-file effect must be idempotent and ordered**. Examples: on a hard bounce, write the suppression to `config.db` first, then complete the queue row (a crash in between just means the retry bounces again); with attachment storage on, write the retained raw to `history.db` first, then delete the spool row (a crash in between leaves a duplicate that a reconcile job removes). On PostgreSQL these are single transactions; the observable behavior is the same.

**Writer design:** one writer thread per file. Callers submit write commands through a bounded channel and await the result; the writer drains up to N commands or T milliseconds (e.g. 2 ms) into one `BEGIN IMMEDIATE … COMMIT`. Under load, batches grow. The `250` is sent after the commit returns (see "Acknowledgement and sync mode" below for what that does and does not guarantee). Reads use separate short connections. Avoid `Cache=Shared` with WAL; one connection per operation. Queue claim is a single-process claim (no `SKIP LOCKED` needed); retention is batched `DELETE` in short transactions with pauses, followed by `incremental_vacuum` (no partition drop).

**There is no rate limiter in the product, on either backend.** The only back-pressure is natural: the bounded channel into the writer (SMTP reads slow through TCP flow control) and `452` for disk full.

**Acknowledgement and sync mode (read this before deploying the SQLite backend).** The earlier design acknowledged after a `synchronous=FULL` commit and called the queue "durable". The owner chose `PRAGMA synchronous=OFF` as the default for speed, so that wording no longer applies and the term "durable queue" is retired. The SQLite backend's default is **process-crash-safe, not power-loss-safe**:

- `250`/`202` now means the data has been **handed to the operating system**, not synced to disk.
- A **process kill or container restart is safe**: per the SQLite docs, "If the application running SQLite crashes, the data will be safe".
- If the **operating system crashes or the host loses power**, the SQLite docs say that with `synchronous=OFF` "the database might become corrupted", and their durability matrix lists WAL mode with `OFF` as "Not consistent". This is **corruption, not just loss of the last commits**: the whole `queue.db` (all queued mail and the webhook outbox, including mail already acknowledged with `250`) or `stats.db`/`history.db` may be unusable. By contrast, `NORMAL` in WAL mode is documented as safe from corruption but may roll back recently committed transactions, and `FULL` is documented as durable (ACID) in WAL mode. Source: [sqlite.org/pragma.html](https://www.sqlite.org/pragma.html#pragma_synchronous).
- A server that acknowledges `250` takes responsibility for the message (RFC 5321). Under the default, that responsibility is not backed by a disk sync. Operators who need it must opt in to `Normal` or `Full`, or use the PostgreSQL backend.

**Loud warnings, no acknowledgement gate (DESIGN-DECIDED; the owner delegated).** `Off` does **not** require an explicit acknowledgement setting. Instead EggMail is deliberately loud about it, every time:

- a **startup log warning** at `Warning` level, naming each file running with `synchronous=OFF` and the safer settings;
- a **persistent dashboard banner** on every page while any data file runs with `Off` (not permanently dismissible; a per-session collapse is acceptable);
- a **metric and health detail**: a gauge for each file (`mta_storage_sqlite_sync_off`, 1 when that file runs with `Off`) and a `warnings` entry (`sqlite_sync_off`) in the health detail. Readiness is not failed by it, because the configuration is a supported choice;
- the **README** text and the quick-start documentation ([release.md](release.md)).

Reason: an acknowledgement gate adds friction to the single-container quick start and, in the owner's judgment, is not what comparable tools do (not independently verified). The documented safer knobs are `Sqlite:SyncMode=Normal` (safe from corruption, may lose recent commits on power loss) and `Sqlite:SyncMode=Full` (durable). The startup integrity check and quarantine recovery below stay.

Knobs (names are proposed; they were `Lite:*` before backends were made feature-identical):

| Knob | Values | Default | Notes |
|---|---|---|---|
| `Sqlite:SyncMode` | `Off` \| `Normal` \| `Full` | `Off` | Applies to `queue.db`, `stats.db` and `history.db`. `Normal`: WAL synced at checkpoints only, safe from corruption, may lose recent commits on power loss. `Full`: WAL synced on every commit, ACID in WAL mode |
| `Sqlite:ConfigSyncMode` | `Off` \| `Normal` \| `Full` | `Full` | Applies to `config.db`. Owner-decided |
| `Sqlite:QueuePersistence` | `Persistent` \| `Memory` | `Persistent` | Renamed from the earlier `QueueDurability = Durable \| Memory` because "durable" is no longer accurate. `Memory` is an explicit opt-in: "accepted means in memory; lost on restart" |

All leases clear on startup (single process) and delivery is at-least-once, so a message in flight at crash time may duplicate.

Cost and benefit versus `Sqlite:SyncMode=Full` (qualitative; no numbers measured): SQLite documents that commits "can be much faster" with `OFF`, and with no fsync per commit the writer is no longer bound by fsync latency. The price is the corruption exposure above. The size of the speedup on our workload is **unmeasured** and must be benchmarked as a pair ([benchmarks.md](benchmarks.md)). Group commit is kept in all sync modes: under `Normal`/`Full` it amortizes fsync; under `Off` it still amortizes per-transaction overhead (inference, to be measured).

**Corruption detection and recovery.**

- At startup, run an integrity check on each file: `PRAGMA quick_check` by default (O(N), skips UNIQUE and index-content checks) or the full `PRAGMA integrity_check` (O(N log N)) by configuration. Startup time grows with file size. A passing check does not prove the file is free of corruption.
- If a file fails: **quarantine** it (move the file and its `-wal`/`-shm` to a timestamped quarantine directory, never delete), **start with an empty file** for that database, and raise an alert (dashboard banner, log, metric). The quarantined file is kept for manual salvage.
- Consequences by file: a quarantined `queue.db` loses all queued mail and pending webhook events; a quarantined `stats.db` loses statistics history and the attempt log; a quarantined `history.db` loses per-message history; `config.db` at `Full` is expected to survive (not guaranteed). If `config.db` is on `Off` and is quarantined, the instance starts without tenants, keys and DKIM keys and must be restored from backup or re-provisioned.
- Optional scheduled backups with `VACUUM INTO` (works while running; `BackupDatabase` blocks writers). A restore returns the state at the last backup; mail accepted since is lost.

**Housekeeping:** `auto_vacuum=INCREMENTAL` must be set before tables exist; `VACUUM` needs up to 2× free space. Set `journal_size_limit`; run `wal_checkpoint(PASSIVE)` after batches and `TRUNCATE` at idle, because long-lived readers starve checkpoints (dashboard reads hit `stats.db`/`history.db`, not `queue.db`). Export WAL size as a metric. Keep the SQLite schema small and stable: AlterColumn/DropColumn need table rebuilds, idempotent scripts are unsupported, a killed migration can leave an abandoned `__EFMigrationsLock`, and `DateTimeOffset`/`decimal`/`TimeSpan` comparisons run client-side (store UTC `DateTime` or `long`).

**Honest ceiling.** This backend is engineered for large, high-throughput workloads; its performance is a first-class goal ([benchmarks.md](benchmarks.md)). With the default `Off` the limit is no longer fsync latency but single-writer CPU, WAL write bandwidth and checkpoint I/O (each body is written to the WAL and again at checkpoint, at least 2× disk writes); with `Normal`/`Full` fsync latency returns as a limit. With `History:Mode=Full` the volume of retained content and events adds file growth and batched-delete cost; the size model in §5 (modeled for PostgreSQL) applies to bytes, not to engine behavior. No credible published commits/s figure for SQLite on SSD with `FULL` was found; one snippet (about 442 inserts/s WAL+FULL vs 33k/s NORMAL) is **unverified** and not our workload. The earlier expectation of thousands of messages/s on local NVMe and hundreds on cloud block storage was an inference made for `FULL`; it is not re-derived for `Off`. Measure it.

**Dashboard indicators (advisory only).** A "storage pressure" indicator for the SQLite backend fed by `sqlite_commit_latency_ms`, `sqlite_writer_batch_size`, `sqlite_writer_queue_depth` and WAL size (equivalent indicators for PostgreSQL, such as pool saturation and claim latency, are proposed). Suggested default signals: writer queue depth over 1,000 for 5 minutes, or p99 commit latency over about 100 ms (both configurable; calibrate after benchmarking, since commit latency will be much lower under `Off`). These are **advisory indicators on the dashboard only**; the system **never switches backend automatically**. Suggested docs wording: *"The SQLite backend has no built-in rate limit. Throughput is bounded by your hardware. If the writer queue stays deep or p99 commit latency is high, you have reached the ceiling; consider faster local disk or switching to PostgreSQL."* Reasons to consider PostgreSQL: more than one node or HA, power-loss safety without the cost of `Sqlite:SyncMode=Full`, scale beyond the single-writer ceiling, or an indicator that stays red. The owner decides whether and when to switch (§4.6).

### 4.5 Statistics (both backends)

Statistics are recorded on every backend and in every history mode, through one shared `IStatsStore` (both engines support `INSERT … ON CONFLICT DO UPDATE`, so the hourly upsert SQL is identical). One row per (period, tenant, sending domain, recipient-domain bucket) with about ten counters (accepted, delivered, deferral attempts, hard bounce, soft bounce, expired, complained, rejected, suppressed), written as upserts. Counters accumulate in memory and flush about every 10 s, so a process crash loses at most that window.

| Knob | Default |
|---|---|
| `Stats:HourlyRetentionDays` | 30 (matches the default `Retention:MetadataDays`); `0` = keep forever, see §5.1 |
| `Stats:DailyRetentionDays` | 400; `0` = keep forever, see §5.1 |
| `Stats:RecipientDomainTopNHourly` | 20 (rest bucketed as "other") |
| `Stats:RecipientDomainTopNDaily` | 10 |
| `Stats:MaxSeriesPerHour` | 200,000 (overflow goes to "other") |
| `History:RecentEvents` | 1,000 (content-free ring, recipient domain only) |

Size model (assumes about 120 B per row plus a similar index, about 250 B per row total, and active series at 30% of the maximum; both assumptions **unverified**): 50 tenants × 2 domains × 21 buckets ≈ 0.45M hourly rows plus 0.25M daily rows ≈ 0.2 GB; 1,000 tenants × 3 domains × 21 buckets ≈ 13.7M hourly rows plus 4M daily rows ≈ 4–5 GB.

**Rollup job** (on SQLite it runs on the stats file's own writer, so it never blocks the queue): hourly, roll each completed day up with `INSERT … SELECT … GROUP BY`, delete expired hourly rows in batches of about 5k with short pauses (and `PRAGMA incremental_vacuum` on SQLite).

### 4.6 Switching backends: manual and symmetric

EggMail never changes backend on its own: no auto-failover, no auto-upgrade, no threshold that triggers a switch. Switching is an **owner-triggered, explicit action** and works **the same in both directions** (SQLite → PostgreSQL and PostgreSQL → SQLite). Because the backend only decides how data is stored, a switch moves data and nothing else changes: every feature, setting and behavior stays as it was (and because the presets share every behavioural default, §4.1, nothing needs translating).

**Two entry points, one engine:** a guided dashboard action, and a CLI, `mta migrate-storage --to postgres|sqlite` (subcommands `export`, `import`, `verify`, `confirm`, `activate`, `rollback`, `finalize`; options such as `--dry-run`, `--bundle <path>`, `--drain` or `--quiesce`, `--skip-history`). Both call the same portable export/import engine.

**One portable, versioned bundle** (NDJSON files plus a `manifest.json`, streamed so memory stays bounded):

- `manifest.json`: switch id (UUIDv7), bundle format version (semantic; the importer accepts older minors and refuses a newer major), source backend and schema version, creation time, counts and SHA-256 per file and per chunk, what is included, the effective values of settings, and secret-protection metadata.
- `config/*.ndjson`: tenants, domains, DKIM keys (protected), API-key hashes, SMTP credential hashes, suppressions, webhook endpoints (secrets protected), relay routes, per-domain TLS policies, settings, warm-up and rate-limit configuration, **certificates and ACME state** (§7.3; private keys and the ACME account key protected), and API idempotency keys.
- `stats/*.ndjson`: hourly and daily aggregates, the recent-events ring, the webhook attempt log.
- `queue/*.ndjson` plus spool bodies: queued deliveries with their retry state, spool bodies and the pending webhook outbox.
- `history/*.ndjson` plus raw files: delivery events, content, retained raw, in checksummed chunks (resumable).
- `secrets/`: the bundle's own Data Protection key ring and its passphrase-protected certificate (below).

Each store (config, stats, queue, history) implements the same export/import contract over the provider-neutral EF model, so adding a table adds it to the bundle in one place. Config is accessed through one shared config-store abstraction implemented once over EF for both providers.

**What moves:**

| Data | Moves? |
|---|---|
| Config: tenants, domains, DKIM keys, API-key hashes, suppressions, webhook endpoints, relay routes, TLS policies, settings, API idempotency keys | Always |
| Certificates and ACME state (account key, certificates, private keys, renewal metadata) | Always (they live in the config store on both backends; secrets protected as below). In-flight ACME orders and DNS-01 challenge state are not moved; the target restarts any pending order |
| Effective values of settings | Always, recorded in the manifest and written explicitly into the target, so behavior does not change |
| Stats and aggregates, recent-events ring, webhook attempt log | Yes |
| Queued messages with bodies and retry state, pending webhook outbox | **In v1, two ways** (below): `--drain` (safe default; waits for an empty queue, nothing to move) or `--quiesce` (does not wait; transfers what remains) |
| Per-message history (events, content, retained raw) | **In v1** when `History:Mode=Full` on both sides: streamed, resumable, skippable with `--skip-history`. If the target is `StatsOnly`, history is not carried to the target and stays in the read-only source; the guided flow states this in the confirmation |
| Data Protection key ring of the deployment | No: the target keeps its own ring; secrets are re-protected (below) |
| Deployment configuration (ports, connection strings, `Storage:Backend`, sync modes, the key-protection certificate or KMS credential) | Not exported; it belongs to the deployment. The tool shows exactly what to change (see "Activation, and orchestrator-managed configuration" below) |

**Secrets: ASP.NET Core Data Protection is the mechanism, and nothing is ever written in clear.** Everything secret in the bundle (DKIM private keys, webhook secrets, the ACME account key, certificate private keys) is protected with Data Protection. In each deployment these secrets are protected at rest by that deployment's own Data Protection key ring, which is persisted in the config store and itself protected by `Secrets:KeyProtection` (`Certificate` or `Kms`; `None` is dev only). Those two settings are *how a deployment protects its ring*; they are independent of the bundle and may differ between source and target.

Across two different key rings the design is (the simplest sound design that still uses Data Protection; **DESIGN-DECIDED**):

1. **Export** (needs a user-supplied *export passphrase*): the source unwraps each secret in memory with its own ring (so the source's certificate or KMS must be reachable during export). The export then creates a **bundle certificate** (a throwaway self-signed RSA certificate) and a **bundle key ring**, a standalone Data Protection key ring written under `secrets/` and protected with that certificate (`ProtectKeysWithCertificate`). Each secret is protected with a purpose string dedicated to the bundle (for example `EggMail.Bundle.v1`) from that ring and written as a protected blob. The bundle certificate's private key is exported as PKCS#12 encrypted under the passphrase (`ExportPkcs12` with PBES2 / AES-256 / SHA-256, available in .NET 9 and later; exact parameters to be confirmed). Plain-text keys are never written to disk.
2. **Import** (same passphrase): load the PKCS#12 to recover the bundle certificate, open the bundle key ring, unprotect each secret in memory, and **re-protect it with the target's own ring** (the target's own `Secrets:KeyProtection`). The target never needs the source's ring, certificate or KMS key, and the bundle certificate and key ring are discarded after import.
3. The only secret that must travel out of band is the passphrase. Its strength is the strength of the bundle (PKCS#12 password-based encryption); the guided flow enforces a minimum length and the bundle should be treated as sensitive and deleted after finalization.

Sub-choices, flagged honestly: (a) Data Protection has no built-in passphrase mode, so the passphrase goes through a PKCS#12 certificate rather than custom crypto; this is a design choice. (b) A "public-key mode" (protect the bundle to the *target's* certificate, so no passphrase is shared) is possible later and is not in v1. (c) RSA is assumed for the bundle certificate because Data Protection's certificate-based key encryption is documented with RSA certificates (**unverified** for other key types). (d) If the target runs with `Secrets:KeyProtection=None` the import warns and requires explicit confirmation, since the re-protected keys are then only as safe as the database.

**Draining and quiescing queued mail (both in v1).** Delivery stays **at-least-once**. The goal is that the switch itself adds as few duplicate sends as possible, and that the ones it cannot avoid are visible.

- **`--drain` (the safe option):** stop accepting, stop starting new deliveries, wait for the queue to empty (the owner can wait, cancel and resume, or let messages expire). Nothing queued moves, so there is nothing to duplicate.
- **`--quiesce` (does not wait for a full drain):**
  1. *Stop accepting:* SMTP listeners reply `421` and the API replies `503` with `Retry-After`; clients retry later (client-side retries are inherently at-least-once).
  2. *Stop starting deliveries:* the scheduler stops claiming new rows. Deliveries already leased (mid-conversation with a remote server) are allowed to **finish**, up to `Switch:QuiesceTimeoutSeconds` (**default 30 seconds**, overridable with `--quiesce-timeout`; DESIGN-DECIDED, the graceful-shutdown pattern). Finished deliveries are recorded final in the source before export.
  3. *Fence:* the source writes a durable **fence record** (`switch_id`, state `Fenced`, time) in its config store. A fenced source never accepts mail and never claims or sends, including after a restart, until the fence is cleared by `rollback`. This is the cutover fence: at most one side is ever allowed to dispatch.
  4. *Requeue what did not finish (no blocking state):* anything still in flight at the timeout is aborted, its lease is cleared, and the delivery is **requeued with the same message id and delivery id and its retry state preserved** (attempt count, `due_at`, last error; the aborted attempt is recorded as `aborted_by_switch`). Delivery stays at-least-once, like Postfix and Exim after a crash or restart. There is no `in_doubt` state and nothing blocks the switch. If the abort happened *after* the terminating `.` of the message body was sent (the remote may have accepted it although we did not see the final reply), the delivery also gets a **`possible_duplicate` flag** and, under `History:Mode=Full`, a `possible_duplicate` event, so operators can see which deliveries might have been sent twice. Aborts before the end of data cannot have been accepted by the remote and are requeued without the flag (reasoning from SMTP acceptance semantics). The flag travels with the row into the target.
  5. *Export and mark:* queued rows (retry state: attempt count, `due_at`, last error), spool bodies and pending webhook outbox rows are exported with their **message ids, delivery ids, webhook event ids and API idempotency keys preserved**, and the source marks each exported row `transferred(switch_id)`. A marked row cannot be claimed even if the fence were cleared by mistake.
  6. *Import:* the target stores the rows with ids preserved, leases cleared and state `queued`, but **does not dispatch** until it is activated. Import is idempotent per `switch_id` and chunk, so repeating it creates no duplicates; the importer refuses a non-empty target that does not carry the same `switch_id`.
  7. *After cutover:* receivers can de-duplicate webhooks by event id, and clients retrying an API send after cutover are de-duplicated by the preserved idempotency keys. SMTP submissions have no idempotency key, so a client that retried because it never saw a `250` can still create a duplicate, as in any SMTP system.
- **Rollback and the fence:** before activation, `rollback` clears the transfer marks and the fence on the source and discards the target's imported data; nothing was sent from the target, so no duplicates are possible. After activation the target may have delivered the rows, so un-fencing the source is refused; going back means running the same flow in reverse (target → source), which fences the target and transfers what is still queued.

**History migration (in v1).** When `History:Mode=Full` on both sides, events, content and retained raw are exported in time-ordered, checksummed chunks (per-day chunks, further split by size) and imported in order with a progress record (`switch_id`, last verified chunk). The job is **streamed** (bounded memory) and **resumable** (restart continues after the last verified chunk; re-sending a chunk is idempotent). `--skip-history` skips it. History is not needed to send mail, so the cutover does not wait for it: the config, stats and queue move in the cutover, and history can be copied **before activation (default for small history) or backfilled after activation** from the read-only source (the target keeps recording new history meanwhile; backfilled rows are older and cannot conflict). The source is kept until the backfill is verified. Size and time are proportional to retained bytes (the modeled example of §5 is about 14 GB at 7 days of content, or about 35–150 GB with attachments) but **no throughput was measured**, so any time estimate is **unverified**; the preflight prints row and byte counts, and the throughput is to be measured in a spike ([open-questions.md](open-questions.md)).

**Steps (identical in both directions; each is a checkpoint the owner can stop at).** Source states: `Active → Quiescing | Draining → Fenced → (Active again on rollback | Finalized)`. Target states: `Importing → Verified → Confirmed → Active`.

1. **Preflight**: target reachable and empty (the importer refuses to merge into a non-empty target), schema/migrations current, target key protection available, bundle format compatible, disk space and size/time estimate from row counts, sync-mode warning if the target is SQLite with `Off`, and a statement of what will not carry over (for example history when the target is `StatsOnly`).
2. **Drain or quiesce** the source, ending with the source `Fenced`.
3. **Export** the bundle (stats flushed first).
4. **Import** into the target (state `Importing`).
5. **Verify**: per-table row counts against the manifest, per-file and per-chunk SHA-256, and a checksum recomputed from the target's tables; report shown to the owner. State `Verified`.
6. **Confirm** (explicit owner action). State `Confirmed`.
7. **Activate**: see "Activation".
8. **Finalize** (separate, explicit): only then may the owner remove the old data. The tool never deletes the source.

**Activation, and orchestrator-managed configuration (DESIGN-DECIDED).** The storage pointer (`Storage:Backend` and its connection) cannot live in the database it points to, so it is always *deployment configuration*. Precedence for every setting is: **command line > environment variables / mounted ConfigMap files > bootstrap file on the data volume > settings persisted in the config store > built-in defaults**. A value supplied by the deployment layer shows in the dashboard as "locked by deployment" and cannot be edited there; settings that are not set by the deployment are editable in the dashboard and persisted in the config store. The storage pointer itself is never persisted in the config store (it would be circular, and a stale override in the old store would conflict after a switch).

The switch **never rewrites environment variables, ConfigMaps or compose files.** The tool detects where `Storage:*` comes from:

- *Bootstrap-file-managed* (typically a single container with a writable data volume): after confirmation the tool writes the new pointer into the bootstrap file and restarts.
- *Orchestrator-managed* (Kubernetes, compose with environment-supplied settings): the tool completes everything up to `Confirmed`, then **produces a cutover patch** with the exact keys to change (an environment diff, a ConfigMap patch or a compose override snippet; secrets are referenced by name, never printed) and stops. The operator applies it and restarts.
- **Startup gate (the same in both cases):** on start, the application reads the `switch_state` of the store it is pointed at. With no switch record, or `Active`, it runs normally. With `Confirmed`, it atomically moves to `Active` and only then starts accepting and dispatching. With `Importing` or `Verified` it starts in a restricted mode (dashboard and API read-only, no accepting, no dispatching) and shows what is pending. A **fenced source** (an old pod, or an instance restarted with the old configuration) shows a banner naming the switch and refuses to accept or dispatch, so a forgotten replica cannot double-send.

Rationale: patching the deployment is the operator's job and cannot be done safely from inside the pod; the persisted state plus the startup gate make the order of operations safe whatever the orchestrator does.

**Rollback.** The source is kept read-only (fenced, files unmodified) until the owner finalizes. Before activation, rollback is `rollback`: discard the target, clear marks and fence, resume the source. After activation, going back is the same flow in reverse. That symmetry is the point of the design.

**Implementation notes (built; details in [components/switch.md](components/switch.md)).** Choices made while building, each **DESIGN-DECIDED**:

- *The bundle row is the EF entity.* One registry (`TransferTables`) lists the 36 tables that move; the relational providers share one implementation of export/import (`EfStorageTransfer`), the in-memory backend has its own. The queue, stats and history stores of SQLite are raw SQL for the hot paths, but export and import go through EF, so adding a table adds it to the bundle in one place. Bundle format 1.1.0 adds per-table checksums, chunk metadata and the history export progress; 1.2.0 the persisted runtime state tables (domain check results, TLS-RPT counters, sending counters) and the Message-ID header and tags of the history index.
- *Chunks and body packs.* Tables are exported in chunk files (5,000 rows or 32 MiB); the raw messages of a chunk are one body pack, not one file per message; history is chunked per day.
- *Order-independent table checksums.* Providers return rows in different orders, so a table checksum is the 256-bit sum of the SHA-256 of each canonical row. Secrets are checked separately by a keyed digest (HMAC) whose key travels protected by the bundle key ring.
- *Hold column and gate.* `delivery_queue` and `webhook_outbox` carry `transfer_switch_id`: a transfer mark on the source, an activation hold on the target; a held row is never claimed. A persisted-state gate in every backend refuses accept, claim, outbox claim and maintenance on a fenced source and on an unactivated target, including after a restart.
- *Progress records.* One `transfer_chunk_<part>` table per model part (a part is one SQLite file): a chunk and its record commit together, which makes import idempotent per switch id and chunk and history resumable. SQLite schema version 3, PostgreSQL migration V003.
- *Drain does not wait for the webhook outbox.* Pending outbox rows move in both modes (receivers de-duplicate by event id); only the delivery queue gates a drain.
- *Effective values travel in the pointer.* They are deployment configuration, not rows, so the activation carries every effective source setting that differs from the built-in default (bootstrap file, or cutover patch), instead of writing them into the `setting` table.
- *One process per SQLite directory.* A lock file proves the server is stopped before the offline `mta migrate-storage` commands open the files.
- *Abort flag precision.* `SmtpClientConnection.EndOfDataStarted` tells the delivery engine whether the end-of-data terminator of the current transaction had begun to be written when a quiesce cancelled it; only then is the requeued delivery flagged `possible_duplicate` (item 4 above).
- The dashboard flow is built (`dashboard/src/pages/admin/StorageSwitch.tsx`) over the admin API (`StorageSwitchService` over `IStorageSwitchEngine`) and is exercised by the browser end-to-end tests. There is no bundle download in the dashboard: the bundle stays on the server volume.

Effort: the switch engine, quiesce and fence, resumable history migration, Data Protection bundle protection, the orchestrator-aware cutover, the CLI and the dashboard flow ([plan.md](plan.md)); engine, fence, history migration, bundle protection, cutover, CLI and the dashboard flow are built.

## 5. History and content retention

(`History:Mode=Full`, on either backend.) The raw message is delivered verbatim (apps may DKIM-sign their own mail; rebuilding MIME would break the signature), so it stays untouched in `message_spool` until every recipient is final. Stripping a partitioned row in place would create dead tuples and rewrite TOAST, so content is split into separate tables instead (on SQLite the same split applies, with `history.db` holding the content and retained-raw tables).

- Default stored content: subject + text + html + attachment index. Attachments are **not** stored unless enabled.
- Attachment flag precedence: per-send API flag, then per-tenant setting, then global default (`false`), behind the master switch `Content:AllowAttachmentStorage`. SMTP ingress uses the tenant setting only.
- Config (proposed): `Content:Mode = Retain | None` (default `Retain`; `None` deletes content at the final state), `Content:RetentionDays = 7` (range 6–30, **no unlimited value**; see §5.1), `Content:StoreAttachments = false`, `Content:MaxStoredBodyBytes = 256 KiB` (truncated with a flag), `Content:StoreSubject` configurable (subjects can contain personal data). Event metadata is kept 30 days (`Retention:MetadataDays`, `0` = keep forever, see §5.1); anything content-like (e.g. a preview) follows the content retention.
- Resend: from retained raw when attachment storage was on; for attachment-free messages, "send again from content" re-composes from stored subject/body and is labelled as re-composed (headers not byte-identical); otherwise the dashboard shows "attachments were not stored" and the API returns a clear error. In `StatsOnly` there is nothing to resend from (§5.2).
- The dashboard renders stored HTML only in a sandboxed iframe under a strict CSP, with plain text as the default.
- Size model (illustrative, not measured; 100k messages/day, about 20 KB content per message, an assumption; sizes are bytes, whichever backend): about 2 GB/day and 14 GB at 7 days before TOAST compression (PostgreSQL). Worst case spool (all mail deferred 5 days) about 25 GB. With attachment storage on: about 35 GB at 7 days, about 150 GB at 30 days.
- Revisit the Postgres-only body design if retained content passes roughly 200–300 GB, WAL passes roughly 50 GB/day or restore time becomes unacceptable (rules of thumb, unsourced).

### 5.1 Retention knobs and unlimited retention

**Convention (applies everywhere): a retention value of `0` means "keep forever" (unlimited).** Negative values are invalid. Unlimited means no automatic cleanup: disk grows without bound and the operator must clean up manually or with external tooling. The dashboard shows a warning next to any knob set to `0`. The knobs and their meaning are the same on both backends; only the cleanup mechanism differs (partition drop on PostgreSQL, batched `DELETE` plus `incremental_vacuum` on SQLite).

| Knob | Default | Allowed | Unlimited (`0`)? | Cost / reasoning |
|---|---|---|---|---|
| `Webhooks:OutboxRetentionDays`, `Webhooks:AttemptLogDays` | 7 | any positive integer, or `0` (**owner-decided**; the earlier cap of 30 is removed) | Yes | Rows grow with event volume. On SQLite the outbox lives in `queue.db`, the hot file, so unlimited outbox retention inflates the file the writer commits to and slows vacuum/backup; the attempt log lives in `stats.db`. Prefer a finite outbox value on SQLite |
| `Retention:MetadataDays` (events, `History:Mode=Full`) | 30 | positive integer, or `0` | Yes, with warning | PostgreSQL: partitions are never dropped, so the partition count grows by one per day; PostgreSQL's partitioning docs caution that very many partitions raise planning time and memory (not re-fetched, **unverified**); consider week-sized partitions if used. SQLite: the events table grows without bound. Backup size and restore time grow on both |
| `Stats:HourlyRetentionDays` | 30 | positive integer, or `0` | Yes, with warning | Hourly rows are the bulk of the stats store (about 13.7M rows, 4–5 GB total, in the modeled large case at 30 days); unlimited growth is linear in time. The `Stats:MaxSeriesPerHour` cap still bounds each hour |
| `Stats:DailyRetentionDays` | 400 | positive integer, or `0` | Yes | Daily rows are small (modeled as about 10k rows/day in the large case, top 10 domains), so this is the safest knob to leave unlimited |
| `Content:RetentionDays` (`History:Mode=Full`) | 7 | **6 to 30 only** | **No** | See below |
| Suppressions | no expiry | n/a | Already unlimited | Needed for correctness |
| `History:RecentEvents` | 1,000 | count, not time | n/a | A bounded ring by design |

**Why `Content:RetentionDays` stays 6–30 and has no unlimited value.** The floor of 6 exists because content must outlive the 5-day queue lifetime (otherwise the dashboard view and resend would vanish before the message is final). The ceiling of 30 is a safety bound, not a technical limit: content holds personal data (subjects, bodies, optionally attachments), so unlimited retention is a privacy and compliance liability, and it is the largest storage consumer (about 150 GB at 30 days with attachments in the modeled example, with a revisit threshold of roughly 200–300 GB). For operators who need to keep nothing, `Content:Mode=None` deletes content at the final state, and `History:Mode=StatsOnly` records no content at all. **OWNER-DECIDED:** the range stays 6–30 with no unlimited value and no override; `0` = unlimited is the convention for the other retention knobs only.

### 5.2 API behavior when history is not recorded or has expired (DESIGN-DECIDED)

The rules are the same on both backends. They reuse the earlier `body_expired` state (an expected state, as opposed to `body_missing`, which is an error).

| Situation | Response |
|---|---|
| `History:Mode=StatsOnly`: any per-message resource (`GET /messages/{id}`, `/events`, `/content`, `POST …/resend`) or message search/list | **`410 Gone`**, code `history_not_recorded` |
| `History:Mode=Full`, message found, content past `Content:RetentionDays` | `GET /messages/{id}` returns **`200`** with `content.state = "body_expired"` (metadata and events are still available); `GET /messages/{id}/content` returns **`410 Gone`**, code `body_expired`; resend returns `410` `body_expired` |
| `History:Mode=Full`, message id unknown or past `Retention:MetadataDays` | **`404 Not Found`**, code `message_not_found` |
| Resend of an attachment-free message that has no retained raw | Allowed, labelled as re-composed (§5); with attachments and no retained raw: **`409 Conflict`**, code `attachments_not_stored` |
| Content missing although it should exist | **`500`**, code `body_missing` (an error state, alerted) |

Why `410` and not `404`, `409` or `200`: in `StatsOnly` the server cannot tell an unknown id from a message it never recorded, so `404` would wrongly say "no such message"; `409` implies a conflict the client could resolve by retrying; `410` states that the resource is intentionally not available and will not appear, which is exactly the situation. Expired content is also `410` for the same reason, while the message resource itself stays `200` so dashboards can still show the timeline. `501` is not used because the capability is not missing. Clients can avoid the error by reading the capabilities endpoint (`history.mode`, `content.retentionDays`) first.

Error body: RFC 9457 problem details (`application/problem+json`, supported natively by ASP.NET Core), with extension members:

```json
{
  "type": "https://eggmail.example/problems/history_not_recorded",
  "title": "Per-message history is not recorded",
  "status": 410,
  "detail": "History:Mode is StatsOnly; per-message data is not stored.",
  "code": "history_not_recorded",
  "history_mode": "StatsOnly",
  "request_id": "01J…"
}
```

For `body_expired`, add `"expired_at"` and `"retention_days"`. The `type` URI is a placeholder (a proposal; no domain is registered for it).

## 6. Webhooks (identical on both backends)

- **Format:** [Standard Webhooks](https://github.com/standard-webhooks/standard-webhooks/blob/main/spec/standard-webhooks.md): headers `webhook-id`, `webhook-timestamp`, `webhook-signature`; HMAC-SHA256 over `id.timestamp.payload`; signature `v1,<base64>`; secrets `whsec_…`; rotation by signing with old and new keys (space-delimited). The event id is the idempotency key; delivery is at-least-once and unordered. The spec says only "some allowable tolerance" for replay; the default 5-minute window is Stripe's library convention.
- **Retry schedule (default):** immediately, 5 s, 5 min, 30 min, 2 h, 5 h, 10 h, 10 h (about 27 hours), identical to Svix and Resend. Other platforms differ (Postmark 6 retries, Mailgun 8 hours, Stripe up to 3 days).
- **Delivery rules:** success is 2xx within 15 s; `410` disables the endpoint; `429`, `502` or `504` throttle; redirects are not followed; an endpoint is disabled after 5 days of continuous failure and the tenant is notified; per-endpoint concurrency capped (default 4).
- **SSRF protection:** HTTPS required by default (`Webhooks:AllowHttp=false`). Resolve the host, validate resolved IPs against a denylist (loopback, private ranges, link-local, `169.254.169.254`, `fc00::/7`, `fe80::/10`, multicast), connect only to the validated addresses keeping the host name for SNI and `Host` (defeats DNS rebinding). A per-tenant allowlist overrides for internal endpoints.
- **Schema:** `webhook_endpoint` (config DB: id, tenant, url, wrapped secret, event types, enabled, disabled reason); `webhook_outbox` (in the queue store, `queue.db` on SQLite: id, endpoint, tenant, event type, event id, JSON payload, next_attempt_at, attempt count, state, lease), inserted in the same transaction that completes the delivery row so a crash cannot lose an event whose outcome is already durable; `webhook_attempt` (in the stats store, `stats.db` on SQLite: outbox id, time, status code, duration, error class, response snippet of at most 1 KB; losing a few rows on a crash is acceptable).
- **Retention:** finished outbox rows and the attempt log are kept 7 days by default, configurable to any positive number of days, and **`0` keeps them forever** (owner-decided; the earlier 30-day cap is removed). Unlimited retention means no cleanup: disk grows with event volume and the operator must clean up manually or externally (§5.1). `Webhooks:OutboxRetentionDays`, `Webhooks:AttemptLogDays`.
- **Writer interaction:** the dispatcher claims due rows through the queue writer and results flow back in the same group-commit batches; the load is small (a few events per message; about 12 events/s average at 1M messages/day).
- **Unverified:** Stripe's and Postmark's webhook timeouts; SendGrid's 24 h retry (search snippet only).

## 7. Network, TLS and ports

### 7.1 Listeners

| Public port | Container port | Mode | Default |
|---|---|---|---|
| 587 | 5587 | STARTTLS | on |
| 465 | 4465 | Implicit TLS (RFC 8314) | on |
| 2525 | 2525 | STARTTLS (last-resort for networks blocking 587/465) | on |
| 2587 / 2465 | 2587 / 2465 | STARTTLS / implicit | off |
| 25 | 2526 | **Bounce/DSN role**: unauthenticated, bounce domain only; STARTTLS offered, not required. With `Inbound:Enabled` the role is `Inbound`: the same, plus the recipients of inbound-enabled domains that have a route ([section 11](#11-inbound-mail)) | bounce role |
| any | any | Plain, loopback or internal network only, no AUTH | off |
| 8080 | 8080 | Dashboard/API HTTP (probes, internal, not published) | on |
| 8443 (optionally 443) | 8443 | Dashboard/API HTTPS | on |

Each listener is switchable. Proposed config shape: `Mail__Smtp__Listeners__<name>__Port|Mode|Role|AuthRequired|BindAddress|Enabled`. High container ports avoid root and capabilities; publish only enabled ports. Rate limits, connection caps and auth lockouts are keyed globally, not per port, and the listener name is logged on every event. The HTTP API on 443 is the escape hatch for networks that block every SMTP port. Check LoadBalancer limits per cloud (inbound 25 may not be available); add a NetworkPolicy allowing only enabled ports. The convention (587/465/2525, with 2587/2465 optional) follows SES, Resend, Mailgun, Postmark and SendGrid; SendGrid's full list is from a secondary source (**unverified**).

### 7.2 Outbound

Direct MX delivery uses port 25. A relay fallback chain on 587, 465 or 2525 is **opt-in per domain**; each route has host, port, TLS mode, credentials and health state. Move to the next route on connect timeout or refusal; retry the same route on 4xx; never fall through on a 5xx content rejection; use a circuit breaker with cooldown. Every delivery records which route was used (a relay changes sending IP, SPF, bounce path and alignment, so fallback must never silently change identity). This fall-through logic is the design authors' own, not from a source.

### 7.3 TLS

- **Certificates and ACME state live in the database** (the config store, on both backends; owner-decided): the ACME account key, issued certificates and chains, private keys, challenge state and renewal metadata (not-after, last attempt, ARI data, failures). Private keys and the account key are protected with Data Protection (§9.1). They are included in the switch bundle (§4.6). One certificate store serves SMTP and the dashboard through an own `ServerCertificateSelector`; TLS 1.2 minimum (1.3 on).
- **Hot reload from the database:** each replica holds the certificates in memory and polls the store every 30–60 s for a changed version or thumbprint (a cheap query), validates the new certificate (key match, `NotAfter`, SAN, chain) before swapping, and keeps the old one and alerts on failure. This replaces polling files (which was unreliable with Kubernetes' `..data` symlink swap). If the database is briefly unavailable, replicas keep serving the certificates already in memory.
- **Renewal lock for multiple replicas (Full):** renewal must run on one replica at a time. A long-running ACME flow (DNS-01 propagation takes minutes) cannot hold a database transaction or a pooled session-level advisory lock, so the design uses a **renewal lease row** (`lock name, owner, lease_until, fencing token`, renewed while working) that works on both backends; on PostgreSQL a short transaction-level advisory lock (`pg_try_advisory_xact_lock`) guards acquiring the lease. The owner suggested an advisory lock; this is the same idea adapted to a long flow (**DESIGN-DECIDED sub-choice**).
- **Sources and precedence:** certificate in the database (ACME-issued, or imported through the dashboard), self-signed on first run (stored in the database; the log says so at every start and the dashboard shows a persistent banner; replaced when the host name was chosen or changes, or shortly before it expires, and always outranked by any other certificate), or built-in ACME with Certes (pin 4.1.x behind an interface; **HTTP-01 on a built-in listener when no DNS credentials are configured, DNS-01 with Cloudflare otherwise or for wildcards**, pluggable DNS-provider interface; Let's Encrypt production by default, any CA by URL, external account binding; renew using ARI; decision 87, which supersedes "DNS-01 only" of decision 19). An **optional file or environment override** (mounted PEM/PFX, e.g. cert-manager under Kubernetes) takes precedence when configured, and the app then only watches those files. Let's Encrypt moves the default profile to 64-day certificates on 2027-02-10 and 45 days on 2028-02-16, and no longer sends expiry emails, so expiry must be monitored. Certes was dormant 2021–2026 with a single recent author; the fallback is an own client (6–12 weeks).
- **ACME challenges and fallback (decision 87):** with only `Hostname` and `Acme:Email` set the server orders a Let's Encrypt certificate over **HTTP-01**: its own minimal socket listener on `Acme:Http01ListenPort` (80) answers `/.well-known/acme-challenge/<token>` and refuses everything else; **DNS-01** (Cloudflare) is used when a token is configured and is the only way to prove a wildcard. The lease holder publishes tokens in the certificate's `challenge_state_json`, so whichever replica the CA reaches can answer. Until a certificate is issued, and while issuing or renewing fails, the first-run self-signed certificate (or the previous certificate) keeps serving, the log says why and the dashboard banner shows `acme_pending` / `acme_failing` with the last error and the next attempt. If port 80 cannot be bound no order is started (a failed validation counts against the CA's rate limit), the error says what to change (port, mapping, or DNS-01).
- **Bootstrap problem:** the app needs the database to read its certificates, so it cannot terminate TLS before the database is reachable. Startup order: connect to the database (the database connection has its own TLS, independent of these certificates); start the plain HTTP listener on 8080 (probes; reachable on loopback or the internal network for first setup); load certificates from the store (or the file/environment override); if none exist, generate and store a self-signed certificate so HTTPS (8443) and SMTP STARTTLS come up, and flag it in the dashboard. SMTP does not accept mail while the database is down (`451`), so no certificate is needed in that state. The certificate that protects the Data Protection key ring (`Secrets:KeyProtection=Certificate`) or the KMS credential is *deployment configuration outside the database*, otherwise the secrets could not be opened; it is not one of these TLS certificates.
- **Security note on keys in the database:** TLS private keys and the ACME account key are stored encrypted by Data Protection (AES-256-CBC with HMAC-SHA256 by default), and the key ring is protected by a certificate or KMS held outside the database. Anyone who can read the database *and* the key-protection certificate/KMS can recover the keys, and database backups, replicas and dumps contain the ciphertext, so protect the key-protection secret separately and restrict who can use it. Grant the read-only dashboard role no access to the secret tables. With `Secrets:KeyProtection=None` (dev only) the keys are effectively unprotected in the database.
- Outbound: opportunistic by default (Postfix `may` equivalent) with per-domain levels (none, may, encrypt, verify); MTA-STS enforce; DANE via the local validating resolver (a failing DANE result is not overridden by MTA-STS). In opportunistic mode, accept untrusted certificates but record the errors; revocation checks off for MX delivery.
- Record per delivery attempt: TLS used/version/cipher, peer certificate subject/issuer/validity/SHA-256, SSL policy errors, verified, policy applied (none, opportunistic, required, mta-sts-enforce/testing, dane), policy id, MX host, STARTTLS advertised, plaintext fallback, failure reason.
- MTA-STS: fetch `https://mta-sts.<domain>/.well-known/mta-sts.txt` with no redirects and only HTTP 200, cache until `max_age`, refetch when the `_mta-sts` TXT id changes, keep the cached policy if a fetch fails.

## 8. Domain verification

Records (decided): DKIM TXT with RSA-2048 (`<selector>._domainkey`, one selector per domain per key; the verifier must concatenate TXT strings since 2048-bit keys exceed 255 characters; CNAME delegation optional later), a return-path CNAME to the operator's bounce domain, SPF `include` optional (keep flat; `~all`), DMARC informational (never blocks sending). *Implemented onboarding additions (decision 88, DESIGN-DECIDED):* the same list also holds the bounce-domain MX, reverse-DNS advice and, when `Domains:MtaStsMode` serves the policy file, TLS-RPT and the MTA-STS TXT and host (both concern mail the domain receives); all of them are advice, only DKIM and the return-path CNAME decide verification; the check reports `ok`, `missing`, `invalid`, `mismatch` per record with the value found, and the list is also available as zone-file text (dashboard, API, log, `mta domains records`). Rotation: publish selector N+1, verify, switch signing, keep N at least 7 days, never reuse selector names.

State machine (**proposed** in earlier research; the decisions record is truncated at this item, so the exact machine is to be confirmed in implementation): `Pending → Verifying → Verified → TemporaryFailure → Failed`, plus sending `Paused` on failure. `Verified → TemporaryFailure` after two consecutive failed checks; `TemporaryFailure → Verified` when records return, or → `Failed` and pause after a configurable grace period (72 hours is a reasonable default following SES and Resend). Cadence: every 1–2 minutes for 15 minutes, every 15 minutes for 24 hours, then hourly until verified; daily once verified, hourly in `TemporaryFailure`; "Verify now" rate-limited to once per 30 s per domain. `Pending`, `Verifying` and `Failed` block sending; `TemporaryFailure` keeps sending with a banner and alert; a missing return-path record falls back to the shared bounce domain.

## 9. Security

### 9.1 Secrets
- API keys are shown once and stored as SHA-256 digests (high-entropy keys); constant-time comparison via `CryptographicOperations.FixedTimeEquals`.
- SMTP auth: PLAIN and LOGIN only, only after TLS, so passwords can be stored as hashes (CRAM-MD5 would need plaintext).
- DKIM private keys, webhook secrets, TLS private keys and the ACME account key are protected with ASP.NET Core Data Protection; the Data Protection key ring is persisted in the config store and itself protected by a certificate or KMS (`Secrets:KeyProtection = Certificate | Kms | None`; `None` is for dev only). That certificate or KMS credential is deployment configuration outside the database and comes from the `*_FILE` secret convention. Never delete old Data Protection keys. Backend switching re-protects secrets under the target's ring through a bundle-specific Data Protection key ring (§4.6).
  *Implemented:* `Kms` is a pluggable key-wrapping provider with a built-in file/environment key and no cloud service (decision 79).
- Dashboard passwords: PBKDF2 from the BCL (iteration count per current OWASP guidance, to be set) or an Argon2 library.
- Encryption at rest is a storage-layer responsibility (volume or database); application-level envelope encryption is deferred behind an interface.

### 9.2 In-house security review
STRIDE threat model per trust boundary (SMTP in, SMTP out, DNS, storage, dashboard, key store); OWASP ASVS L2 for API and dashboard, L3 for key and credential handling; written parser-review checklist plus SharpFuzz on every parser with crashers kept as regression tests; attack suites (smtpsmug, SMTP-Smuggling-Tools, EAST for STARTTLS, slowloris, connection flood, oversized DATA, MIME bombs with memory/CPU ceilings); port pen-tests (relay abuse, AUTH brute force, `testssl.sh`, Internet.nl); container hardening (non-root, read-only root filesystem, `cap_drop: ALL`, default seccomp, CIS Docker Benchmark, Trivy/Grype); a non-author reviews every security-relevant PR; quarterly "red hat" week; CVSS 4.0 with fix SLAs (e.g. critical 7 days, high 30, medium 90); every finding becomes a regression test.

An **external audit is recommended before first production-critical use** (2–4 weeks with 2–4 testers is a reasonable scope by inference from comparable audits; no cost figures found, get quotes). Publish `security.txt` and a disclosure policy before launch.

### 9.3 Dashboard supply chain
Preact + Vite recommended. Build in a Node stage of the Dockerfile and copy only `dist/`; `npm ci --ignore-scripts`, a minimum release age (about 7 days), `npm audit signatures`, OSV scanning, a strict CSP (`script-src 'self'`, no inline), and about 10 or fewer direct dependencies. Treat the dashboard as an admin surface with the same review as the SMTP stack.

- **PostgreSQL backend ("Full"):** app + managed Postgres via compose (app + `postgres:17` with a `pg_isready` healthcheck) or a Kubernetes Deployment. More than one replica is safe (no local blobs; `SKIP LOCKED` claims; advisory-locked retention job; the failed-login budget, the per-destination limits and what destinations told a replica are shared through the database, see decision 82 and [operations.md](operations.md#running-more-than-one-replica)).
- **SQLite backend ("Lite"), the default:** one container, one volume mounted at `/data` (ReadWriteOnce, local), one replica, recreate rollout. Characteristics of the backend (§4.2), not missing features.
- **Switching backends** is manual and symmetric (§4.6); the guided action cannot provision Postgres or change container topology.
- **Image:** **a single Docker image** that runs out of the box (SQLite backend, one volume at `/data`, the default ports of §7.1) and selects the PostgreSQL backend by configuration (`Storage:Backend=Postgres`) in the same image. Chiseled, with ICU (the `-extra` variant) plus a startup Unicode self-test (silent failure in invariant mode is a risk). ReadyToRun; no trimming (EF is not trim-safe). Pin versions. Release process, registry, tags and quick-start snippets: [release.md](release.md).

## 11. Inbound mail

EggMail started outbound-only: port 25 accepted bounce traffic and nothing else. The owner asked for inbound mail too. This section is the design of that feature. Everything in it is **DESIGN-DECIDED** (decision 95) unless marked otherwise; the coordinator fixed the shape (the authentication libraries are wired in, a per-domain flag, per-domain routes with four actions, no mailbox server) and this section decides the rest, with the reasons. Config key names marked *proposed* are final only when the pull request that reads them documents them in [operations.md](operations.md).

### 11.1 Scope and non-goals

**In:** accept mail on port 25 for domains a tenant enabled; verify SPF, DKIM, DMARC and ARC; add `Received` and `Authentication-Results`; route each recipient to one action (webhook, forward, store, discard); store, search, download and delete received mail through the API and the dashboard; retention; metrics; both backends; the backend switch.

**Out (this step):** an IMAP or POP3 mailbox server (a stored message is read through the API and dashboard, not with a mail client: **open question for the owner**, [open-questions.md](open-questions.md)); sending DMARC aggregate reports about received mail (`Mta.Auth.Reports` can write them; not wired); automatic replies of any kind; content filtering and spam scoring beyond the optional DNSBL hook; per-user mailboxes and quotas; the PROXY protocol (11.4, open question).

**Inbound mail is not history.** `History:Mode` (outbound per-message history) does not apply to it, `--skip-history` does not skip it, and it is stored on both backends in every mode. The consequence for a backend switch is size: stored mail travels with the queue part, so a deployment that keeps a lot of it (a long retention, the `store` action) makes the bundle, the export and the verification as large as that mail. Prefer finite retention and PostgreSQL for such a deployment ([operations.md](operations.md#inbound-mail)).

### 11.2 How a message flows

```
 sender's MTA --25--> RCPT: classify (signed bounce token, SRS, inbound domain with a route)   none of them: 550, nothing stored
                      DATA: size, smuggling and time limits (existing)                         over a limit: 552 / 554
                      verify: SPF, DKIM, DMARC, ARC (bounded time and concurrency)             DMARC reject on every recipient: 550
                      stamp:  Received + Authentication-Results                                (foreign Authentication-Results of ours removed)
                      store:  one row + one body per recipient, one atomic write                250 only after the commit
                              |
        route action (after 250, by a worker): webhook | forward (outbound queue, SRS) | store (done) | discard (no body)
```

Nothing after the `250` can produce a message to the sender: a failed action is visible to the tenant (state, webhook event), never to the sender (11.12). A client that loses the `250` (the connection drops after the commit) retries and the message is stored twice: SMTP gives no way to avoid it, and de-duplicating by `Message-ID` would drop mail that senders legitimately repeat.

### 11.3 Enabling a domain

- **A domain is inbound-enabled** when its `inbound_domain_settings` row says `enabled` (no row means off, which is the default). The flag is per domain, not per tenant, so a tenant can send from `example.com` without receiving for it.
- **The domain must be one of the tenant's registered domains and be `verified`** (or `temporary_failure`, as for sending) to be enabled; the API refuses `enabled: true` otherwise (`403 domain_not_verified`, reason `inbound_domain_not_verified`). *Reason:* an MX record pointing at EggMail proves nothing about who owns the domain, while the DKIM TXT record that verification looks for does. Without this check the first tenant to register `victim.com` could read the mail of its real owner as soon as the owner points an MX at the shared server. A domain name is unique across the server (existing rule), so the real owner cannot register it later either: verification is the only ownership proof there is.
- **A verified domain that stops being verified** (the records vanished and the 72 hours of `temporary_failure` ran out: status `failed`; or it was re-checked into `pending`) is no longer accepted for: the receive path answers `450 4.2.1` for it (temporary, so senders keep the mail while the operator repairs the records), never `550`, and never accepts. `temporary_failure` keeps receiving, as it keeps sending. The cached configuration carries the status (`InboundDomainConfiguration.DomainStatus`) and the tenant's enabled flag.
- **Inbound is refused on the bounce domain and on return-path hosts:** the API refuses to enable it for `Delivery:BounceDomain` and for a name that is the verified return-path host of any domain (the bounce-trust change, decision 92, binds bounce addresses to those hosts). Mail for those names has exactly one meaning (signed bounces), see the classification order in 11.4.
- **Master switch:** `Inbound:Enabled` (default `false`, *proposed*). Off, the server behaves exactly as before. On, the port-25 listener (listener name `bounce`, container port 2526) gets the new listener role `Inbound`, a superset of `Bounce`: it still accepts signed bounce addresses and now also the recipients of 11.4. Submission listeners are never affected: they accept no inbound mail. `GET /capabilities` reports it as `inbound: { enabled }` so the dashboard can show or hide its pages.
- **DNS:** the customer publishes `MX 10 <Hostname>` for the domain (an `A`/`AAAA` for `Hostname` already exists for TLS). The domain's record list gets one advisory record, purpose `inbound_mx` ([api.md](api.md#inbound-mail-inboundread-and-inboundwrite-scopes)), only when inbound is enabled for it, with the same status words as every record (`ok`, `missing`, `invalid`, `mismatch`, `pending`). Replicas on PostgreSQL may all receive; the load balancer decides.
- **Tenant suspended:** the receive path answers `450 4.2.1` for its domains, so senders keep the mail instead of bouncing it.

### 11.4 Listener behaviour (RCPT, DATA, limits)

Everything that can refuse a message does it **in the SMTP dialog**, before a `250`. Nothing is accepted and then bounced (no backscatter), and an address that no route handles is never accepted (no open relay).

**Classification of a recipient, in this order** (the first that applies decides; the rest is not consulted):

1. **A bounce recipient**, exactly what the bounce listener accepts today (decision 92): `b+<token>@<host>` with a valid signed token at the shared bounce domain or at the verified return-path host `bounce.<domain>` of a registered domain whose return-path CNAME is verified; and **`postmaster` and `abuse` at the shared bounce domain**, which the listener accepts without a token (they exist at the shared bounce domain only). A recipient at the bounce domain or at a return-path host that is none of these (an invalid token, any other local part) gets what the bounce listener answers today, **`550 5.1.1 No such user here`**: it is never an inbound recipient and none of the inbound policies run for it.
2. **A local part that starts with `SRS0=` or `SRS1=`** at an inbound-enabled domain: the SRS path (11.7); with a valid hash and age and the null sender `250` (the bounce is dropped), otherwise `550 5.1.1`.
3. **An inbound-enabled domain with a matching enabled route**, or `postmaster` (below): an inbound recipient.
4. **Anything else:** `550 5.7.1` (domain not served) or `550 5.1.1` (domain served, no route).

**Bounce and SRS recipients are not inbound recipients, so none of the inbound policies apply to them:** the DMARC reject, the DNSBL, the per-domain and per-remote rate limits, the stored-bytes limits and the suspended-tenant `450` do not touch them (a bounce for a suspended or flooded tenant must still arrive, and a DSN must never be rejected for its sender's DMARC). **A transaction has one kind, and there are three: bounce, SRS and inbound.** The first accepted recipient fixes the kind, and a later `RCPT` of another kind gets `452 4.5.3 Cannot mix these recipients in one transaction, send them separately` (a real sender retries it in its next transaction). *Why bounce and SRS are two kinds:* the end of DATA does different things (the bounce processor, or verify-and-drop), and a message addressed to both a token and an SRS address does not occur in practice. Several inbound recipients, of any domains and tenants, are one kind.

| Situation | Reply | When |
|---|---|---|
| Recipient domain is not inbound-enabled (unknown domain, inbound off, `Inbound:Enabled` off) and is not a bounce or SRS recipient | `550 5.7.1 Relaying denied` | RCPT |
| Domain enabled but no enabled route matches the local part (and it is not `postmaster`) | `550 5.1.1 Mailbox unavailable` | RCPT |
| Local part is `postmaster` (any case) and no route matches | accepted (RFC 5321 section 4.5.1): stored with the action `store` and no route id, visible in the dashboard; an explicit route for `postmaster` wins | RCPT |
| Domain status is neither `verified` nor `temporary_failure`, or the cached configuration says the tenant is suspended | `450 4.2.1 Mailbox disabled, try again later` | RCPT |
| Domain or remote address over its rate limit (below) | `450 4.7.1 Too many messages, try again later` | RCPT |
| More recipients than `Inbound:MaxRecipients` (*proposed*, default 20) in the transaction | `452 4.5.3 Too many recipients` | RCPT |
| The transaction would store more than `Inbound:MaxTransactionBytes` (*proposed*, default 256 MiB): declared size times accepted recipients, **and again at the end of DATA with the actual size** | `452 4.5.3 Too many recipients for this size` | RCPT, end of DATA |
| Stored bytes of the domain or of the tenant at their limit | `452 4.2.2 Mailbox full, try again later` | RCPT |
| `SIZE=` over the limit, or the body grows over it | `552 5.3.4 Message too big` | MAIL, DATA |
| DMARC fails under `p=reject` and **every** accepted recipient's domain has the action `reject` | `550 5.7.1 Rejected by the DMARC policy of <domain>` | end of DATA |
| **Every** accepted recipient's domain has the action `reject` and the DMARC verdict is `temperror` or the verification timed out | `451 4.7.0 Temporary authentication failure, try again later` | end of DATA |
| No verification slot is free (all slots, or the client's own share of them, are in use) | `451 4.7.0 Server busy, try again later` at once (no waiting in a queue) | start of DATA (a look at the free count, nothing reserved), end of DATA (the slot is taken here) |
| DNSBL hit with `Inbound:Dnsbl:Action=Reject` (*proposed*, off) | `554 5.7.1 Listed by <zone>` | RCPT: the first recipient that classifies as inbound (the lookup happens there, never at connect; a connection that only carries bounce or SRS recipients is neither queried nor refused) |
| Storage unavailable, configuration not loaded yet, disk full | `451 4.3.0` / `452 4.3.1` | any |
| Bare LF/CR, NUL, STARTTLS injection, line limits | existing `500`/`421` replies | any |

- **The decision uses a cache.** The receive path loads `LoadEnabledDomainsAsync()` (domains, status, tenant state, settings, enabled routes in evaluation order) and refreshes it every 30 s (jittered) and immediately after an API change on the same process; a replica that did not make the change sees it within 30 s. A cold or failed load answers `451 4.3.0`, never "unknown domain". The refresh is one set of queries per replica per interval, not per connection. Each `InboundDomainConfiguration` carries an `ETag` computed from its content, so the receive path rebuilds its derived structures (compiled route lists, limiter configuration) only for the domains whose tag changed; a cheaper "has anything changed" probe in the database was considered and not built (the load is one query set per 30 s per replica, and the metric `mta_inbound_config_age_seconds` shows a refresh that stopped).
- **The limiters are bounded and do not share eviction.** The per-domain and the per-remote counters live in memory (per process, like the other limiters of decision 82), **each kind in its own dictionary** with a fixed maximum number of entries (100,000) and entries that expire with their one-minute window; at the maximum, expired entries go first and then the oldest. Because the dictionaries are separate, a flood from many addresses can only make the per-remote limiter forget remote addresses; it can never evict a domain's counter and so never resets a domain's limit. **An IPv6 client is limited by its /64**, and an IPv4-mapped address (`::ffff:a.b.c.d`) is normalized to the IPv4 address before any limit, DNSBL query or SPF check.
- **The real client address matters.** SPF, the DNSBL and the per-remote limit need the address the sender connected from. Behind source NAT (a Kubernetes `Service` with the default `externalTrafficPolicy: Cluster`, a Docker published port from some setups, a load balancer that terminates TCP) every client appears as the NAT address: SPF then fails or passes for the wrong reasons and one sender can exhaust everyone's per-remote budget. The operator must preserve the client address (host networking, `externalTrafficPolicy: Local`, or a layer-4 load balancer that keeps it): [operations.md](operations.md#inbound-mail). **Publishing the container port as `-p 25:2526` does not always preserve it:** Docker Desktop (macOS and Windows), the rootless engine and the userland proxy (`docker-proxy`, used when the host cannot do the NAT in the kernel) deliver every connection from the gateway or loopback address, so SPF and the per-remote limit are then wrong for all senders; on a Linux host with the default engine the kernel NAT keeps the client address. The server cannot detect this at start, so it **warns once per hour** when an inbound connection arrives from a private, loopback or link-local address while the listener is not loopback-bound ("client addresses look internal; SPF and per-address limits are not meaningful behind NAT"). Supporting PROXY protocol v2 with a trusted-source list is an **open question** (not built now).
- **Normalization:** the domain is lower-cased and in A-label form; the local part is matched as received, ignoring case. `InboundRules.MatchRoute` (in `Mta.Storage`) is the one implementation of "which route handles this recipient", used by the receive path, the API's test endpoint and the tests.
- **STARTTLS is offered, never required.** A public MX that refuses plaintext loses mail (RFC 3207); `TlsUsed` is recorded on the message and the version in `Received`. Operators who want to force TLS from capable senders publish MTA-STS (decision 88), which is how that is done on the Internet.
- **Limits that already exist and apply:** line length, message size (`Inbound:MaxMessageSize`, *proposed*, default `Smtp:MaxMessageSize`; a domain can only lower it), errors per session, per-IP and global connection caps, the global in-flight bytes budget (`452`), read and total DATA timeouts, smuggling and STARTTLS-injection defenses. Inbound adds the recipient cap, the transaction budget, the rate limits and the stored-bytes limits above. **BDAT** is accepted on the inbound listener like on the others, with the line-ending rule of decision 93: the stored copy and the DKIM verification see one body rule whichever of DATA and BDAT delivered it.
- **A storage-full reply is `452`, an oversize message is `552`:** a full disk or a full quota is temporary for the sender (they retry after the operator or the retention frees space); a message that is too big will never fit, so it is permanent.
- **The transaction budget** (`Inbound:MaxTransactionBytes`) bounds what one transaction can store: the size the client declared (`MAIL FROM ... SIZE=`; **when the client declares none, 1 MiB is assumed** for the check at RCPT) times the recipients accepted so far, refused at the `RCPT` that would exceed it; and once the body has been received, **the actual size times the accepted recipients is checked again** and a transaction over the budget is refused as a whole with `452 4.5.3` (a client can declare a small `SIZE` and send a large body, or declare none; the second check is the one that cannot be talked around).
- **The quotas can be overshot by a bounded amount.** The stored-bytes check at RCPT reads usage that the receive path caches for a few seconds (`GetUsageAsync` is an indexed aggregate, not a counter), so the domain and tenant limits may be exceeded by what is accepted inside that window: at most the cache age times the rate limit times the size limit, plus the transactions in flight; the next check after the window sees the true figure and refuses. The limit is a guard against filling the disk, not an exact quota, and the bound is small against any realistic limit.
- **Several recipients:** one transaction can name recipients of several domains and tenants. Each accepted recipient gets its own row and its own copy of the body (11.6). The `Received` header carries a `for <recipient>` clause only when the transaction has exactly one recipient (it would otherwise disclose the others).
- **Null sender** (`MAIL FROM:<>`) is accepted for inbound recipients, as for any mail system that must receive the bounces of its customers' mail. **A `MAIL FROM` of one of the local domains without authentication** is an external sender claiming a local identity: it is accepted like any other, verified (SPF will fail unless the sender is authorized), and neither authenticated nor relayed; inbound sessions have no `AUTH`.

### 11.5 Verification

The libraries in `Mta.Auth` and `Mta.Dkim` (SPF, DKIM verify, DMARC, ARC validation, Authentication-Results builder) are wired into the receive path; nothing is re-implemented. All DNS goes through the existing resolver and its caches.

- **When:** after the end of DATA, before the commit, because DKIM and DMARC need the headers. SPF is evaluated for the MAIL FROM domain (the HELO name when the reverse-path is null) **and for the HELO name itself** (RFC 7208 section 2.3), with the client address the TCP connection shows; both verdicts are recorded (`spf`, `spfHelo`) and written to `Authentication-Results` (`smtp.mailfrom`, `smtp.helo`).
- **Budget:** one total timeout (`Inbound:Verification:Timeout`, *proposed*, default 20 s) and a concurrency limit (`Inbound:Verification:MaxConcurrency`, *proposed*, default 32) so a flood of messages cannot turn the receiver into a DNS load generator; the libraries bound lookups per check (SPF: 10 terms, 2 voids; DKIM: signatures per message). **The slot is taken after the end of DATA**, when the body has been received and its size checked, and held only for the verification (at most the timeout): a client that opens connections and trickles bytes holds no verification slot while it does. **A client's share of the slots is capped as well** (`Inbound:Verification:MaxConcurrencyPerRemote`, *proposed*, default 4, per IPv4 /24 and IPv6 /64), so one network cannot take them all. **When no slot is free the message gets `451 4.7.0` at once** instead of waiting: a waiting message holds its connection, its buffers and the in-flight bytes budget, which is the resource a flood is after. To avoid receiving a body that will be refused anyway, the server also looks at the free count at the start of DATA (reserving nothing) and answers `451` there when it is zero; the sender retries the whole message in both cases, which is the price of not queueing. A result that could not be obtained is `temperror`, and **a temporary error never rejects, except under the action `reject`**: there the mail is not accepted unverified, because its policy might have said reject; the sender gets `451 4.7.0` and retries (a stuck DNS server delays mail, it does not let spoofed mail through). **As with the `550`, the `451` is given only when every accepted recipient's domain has the action `reject`**: a transaction that also names a `record_only` or `flag` domain is accepted (the `temperror` is recorded, the disposition stays `none`), so a domain that wanted its mail never has it delayed by another domain's policy. Under `record_only` and `flag` a `temperror` is accepted and recorded.
- **SPF fail or DKIM fail alone never rejects.** DMARC decides (RFC 7489 section 10.1: receivers should not reject on SPF or DKIM alone). The verdicts are recorded and shown.
- **DMARC action per domain** (`dmarcAction`): `record_only` (default: record, never act), `flag` (a message that fails DMARC where the sender's policy is `quarantine` or `reject` is stored with `disposition = flagged`, gets the header `X-EggMail-Dmarc: flagged`, and the webhook payload says `dmarcFlagged: true`; the mail is **not** moved anywhere or dropped, nothing is quarantined, and the route's action still runs, so the consumer of the action decides), `reject` (`p=reject` failures get `550 5.7.1` in the dialog, `p=quarantine` failures are flagged as above). The policy used is the one the evaluator returns (`pct` and the subdomain policy are honored by it).
- **A transaction with several recipients** can be refused only as a whole (SMTP gives one reply to the end of DATA). The rule: **it is refused only when every accepted recipient's domain has the action `reject` and the policy says reject**; otherwise it is accepted, the copies of the `reject` domains are stored flagged (`disposition = flagged`), and nothing is lost for the domains that wanted the message. A sender who knows the policy sees one reply, never a partial acceptance.
- **ARC:** the chain is validated, the verdict recorded and written to `Authentication-Results`. **The chain is validated up to 10 instances**; a longer chain is `arc=fail` (reason `too_long`) without further work, so a hostile chain costs a bounded number of DNS lookups and signature checks. It does **not** change the DMARC outcome unless **all** of these hold: the chain validates (`cv=pass` at every instance), the **last** seal (the highest instance, the one that vouches for the earlier ones) has a `d=` that is listed in `Inbound:Arc:TrustedSealers` (*proposed*, empty by default), and that instance's own `ARC-Authentication-Results` shows `dmarc=pass` (or an aligned `spf=pass` / `dkim=pass` for the From domain). Then a failing DMARC verdict is treated as a pass for the action decision (the original verdicts stay recorded). A passing chain alone proves only that its sealers sealed it; trusting a sealer is an operator decision about someone else's reputation, so nothing is trusted by default, and a trusted sealer in the middle of the chain does not count.
- **Headers added** (prepended, in this order): `Received` (the server-generated header the SMTP layer builds), then `Authentication-Results: <authserv-id>; spf=...; dkim=...; dmarc=...; arc=...` (authserv-id: `Inbound:AuthenticationResultsId`, *proposed*, default `Hostname`). **Headers removed first:** every `Authentication-Results` whose authserv-id is ours (RFC 8601 section 5, so a sender cannot present forged verdicts) and every `X-EggMail-*` header (the namespace is ours: the flag must come only from us), **except** a loop marker whose signature verifies (11.7), which is kept so that the hop count survives.
- **Where the results live:** (1) the stored message carries the `Authentication-Results` header, the durable human-readable record, and it travels with a forward and with the raw download; (2) `inbound_message` has the structured verdicts (`spf`, `spf_domain`, `spf_helo`, `dkim`, `dkim_domain`, `dmarc`, `dmarc_policy`, `arc`, `disposition`) for search, the API and the dashboard; (3) the webhook payload carries them (11.7). The history store is deliberately not used: it is about outbound mail.
- **Reputation hook (optional, off by default):** `Inbound:Dnsbl:Zones` (*proposed*, empty = off) lists DNS blocklists queried for the client address **once per connection, at the first recipient that classifies as inbound** (11.4; the answer is cached for the connection, and a connection with only bounce or SRS recipients is never queried) with the existing resolver and a short timeout. IPv4 is queried as the reversed octets (`9.113.0.203.zone`); **IPv6 as the 32 nibbles of the full address, reversed, lower-case hex, dot-separated, no zero compression** (`1.0.0.0. ... .8.b.d.0.1.0.0.2.zone`), the form the IPv6 lists document (they aggregate prefixes themselves; the /64 grouping is for our own limiter only). An answer is a hit only when it is in `127.0.0.0/8` and **not** `127.255.255.0/24`, the range the common lists use for "your resolver is blocked or over quota" (that is an error: never a hit, logged and counted). `Inbound:Dnsbl:Action` is `Flag` (header `X-EggMail-Reputation: dnsbl=<zone>`, default) or `Reject`. A lookup failure never blocks. **A hit under `Reject` is a `554 5.7.1` at that first inbound `RCPT`** (the recipient is refused; bounce and SRS recipients in the same connection are not, and are exempt as in 11.4); under `Flag` the header is added at the end of DATA. **Every list query discloses the client addresses that connect to this server to the list operator**: that is a privacy decision for the operator, documented where the key is. EggMail ships no list and endorses none; listing policies differ and a wrong list rejects legitimate mail.

### 11.6 Data model

Two groups, in two parts of the storage model (4.1): configuration in the **config** part and received mail in the **queue** part. All of it exists on both backends, in both history modes (`History:Mode` is about outbound history and does not matter here), and moves in a backend switch (11.10). Contracts: `Mta.Storage/Contracts.Inbound.cs` (`IInboundStore` = `IInboundConfigStore` + `IInboundMessageStore`, reached as `IStorage.Inbound`).

**Operator ceilings and per-domain settings.** The operator's server-wide limits (`Inbound:*`, 11.13, the `InboundCeilings` record) are both the default and the ceiling of the matching domain setting: **a tenant can only lower a limit, never raise it**, and the API refuses a value above a ceiling (`validation_failed`, naming the key). A setting the domain leaves `null` inherits the server value. If the operator lowers a ceiling later, the receive path and the retention job apply `min(domain value, ceiling)` (`InboundRules.Effective` is the one implementation, used by the receive path, the retention job and the API's `effective` object), so a stale stored value never exceeds what the operator now allows. **A change through the API is held to the ceilings only for the members it names:** a request that turns the domain off or changes one setting never fails because another stored value is now above a lowered ceiling. **The server default is checked once, at start:** `Inbound:RetentionDays` above `Inbound:MaxRetentionDays` (or `0` under a ceiling) is a configuration error that stops the start (the operator contradicts themselves), while a *stored* domain value above a ceiling lowered later is cut at run time (the tenant did nothing wrong).

**Per-domain settings** (`inbound_domain_settings`, one row per domain, deleted with the domain):

| Member | Meaning | Ceiling / default when null |
|---|---|---|
| `enabled` | the domain accepts mail (11.3) | off |
| `dmarcAction` | `record_only` \| `flag` \| `reject` (11.5) | `record_only` |
| `maxMessageBytes` | largest message | `Inbound:MaxMessageSize` (ceiling and default) |
| `maxMessagesPerMinute`, `maxMessagesPerMinutePerRemote` | accepted messages per minute for the domain, and per client address (IPv6: per /64) for the domain | `Inbound:MaxMessagesPerMinute` (600), `Inbound:MaxMessagesPerMinutePerRemote` (60) (*proposed*; ceilings and defaults) |
| `maxStoredBytes` | total body bytes kept for the domain, each recipient's copy counted; at the limit RCPT answers `452 4.2.2` | `Inbound:MaxStoredBytesPerDomain` (*proposed*, 2 GiB; `0` = unlimited; ceiling and default). A finite ceiling also refuses `0` |
| `retentionDays` | how long a message is kept, from receipt; **`0` = keep forever** | default `Inbound:RetentionDays` (7); ceiling `Inbound:MaxRetentionDays` (*proposed*, `0` = none); a longer value is refused and "forever" is refused under a ceiling |

Besides the domain limits there is one **tenant-wide** cap, `Inbound:MaxStoredBytesPerTenant` (*proposed*, default 10 GiB, `0` = unlimited): the sum of the stored bytes of all of a tenant's domains. Without it a tenant could multiply the per-domain limit by registering more domains (200 are allowed). The receive path enforces both with `452 4.2.2`.

**Routes** (`inbound_route`; at most 100 per domain): `{ id, domainId, name, order, enabled, match: { kind: catch_all | address | wildcard, localPart, plusAddressing }, action: { kind: webhook | forward | store | discard, webhookEndpointId, webhookFormat: json | raw_mime, forwardTo: [..] } }`.

- **The first enabled route that matches wins** (lowest `order`, then lowest id). There is no specificity ranking: it is predictable and the same rule everywhere; a catch-all belongs last.
- `address`: the whole local part, ignoring case. `wildcard`: a pattern in which `*` matches any run of characters including none (`billing-*`, at most 3 stars, not only stars). `plusAddressing`: the local part is also compared without everything from the first `+` (`support+billing` reaches the route for `support`); an exact route for `support+billing` still wins by its `order`. Local parts are compared ignoring case: RFC 5321 allows case-sensitive local parts, but no mail system relies on two mailboxes that differ only in case, and treating them as equal avoids losing mail to `Support@`.
- A webhook route names one of the tenant's webhook endpoints (the endpoint is reused as the registered, SSRF-checked, signed target; the route does not carry a URL). **Deleting an endpoint that a route uses is refused (`409 conflict`) by the storage write itself** (`IConfigStore.DeleteWebhookEndpointAsync` raises `StorageConflictException`; the check and the delete are one write), and **creating or changing a webhook route checks in its own write that the endpoint exists for the route's tenant** (`IInboundConfigStore.UpsertRouteAsync`, same exception), so neither a route created at the same moment as a delete nor an endpoint of another tenant can slip through; the schema has no foreign keys by design (4.1), so these two checks are the integrity rule on both backends. A forward route has 1 to 10 addresses, **none in the route's own domain and none in a domain that is inbound-enabled on this server** (the API refuses them, naming `action.forwardTo[i]`; domains are compared in A-label form, so `bücher.example` and `xn--bcher-kva.example` are the same domain): the loop is closed at configuration time wherever it can be seen, and at run time by the hop marker (11.7).
- **The action that runs is the route's current one, read when the action runs** (by `routeId`), not a copy taken at receipt: an operator who fixes a wrong webhook endpoint and retries wants the fix to apply. A deleted route fails a pending action with `route_deleted`. **Disabling a route stops it matching new mail; actions already pending for it still run** (the message was accepted under the route and is owed its action). Changing the action of a route changes what its pending messages do, with one rule for the case where the route became `store` or `discard` while a message waited for its webhook or forward: **the action completes `done` with the note `route_is_now_store` or `route_is_now_discard`** (nothing is delivered, and no received mail is deleted because a route was edited: the body stays until retention). **The API makes the staleness explicit:** a message's `action.kind` is the kind it was given at receipt; the detail endpoint adds `action.currentKind`, what its route does now (absent when the route is gone or for a list entry), and `action.note` shows the completion note.

**Inbound messages** (`inbound_message` + `inbound_message_raw`, one pair of rows **per accepted recipient**): `{ id (UUIDv7), tenantId, domainId, domain, receivedAt, remoteAddress, helo, tlsUsed, envelopeFrom, envelopeTo, subject, size, auth: { spf, spfDomain, spfHelo, dkim, dkimDomain, dmarc, dmarcPolicy, arc }, disposition, routeId (null for the implicit postmaster delivery), actionKind, actionState: pending | done | failed, actionAttempts, retryGeneration, actionNextAttemptAt, actionFinishedAt, actionLastError, actionNote, forwardMessageId, hasRaw }`. `envelopeFrom` and `envelopeTo` are stored **lower-case** (the contract and both backends normalize them on write; the sender's own case is in the message headers), and the client-supplied text (HELO name, remote address, the domains and policy in the verdicts) is stored without control characters and cut at 255 characters, because it reaches the dashboard and the webhook. The body (`inbound_message_raw`, the stamped message, CRLF lines) is a separate row so list and claim queries never read it, as with the spool.

- **One row and one body per recipient, not one shared body.** A transaction to two recipients of two tenants must not leave a shared object that one tenant's delete or retention touches and the other's still needs; the stamped copy also differs per recipient (the DMARC flag depends on the domain's settings). **The amplification is bounded and accounted:** at most `Inbound:MaxRecipients` copies, the transaction budget of 11.4 (`MaxTransactionBytes`), and **every copy counts against the domain and tenant quotas at its full size** (the usage queries sum the bodies that exist), so a sender cannot store more than the quotas allow by addressing many recipients. Typical inbound mail has one recipient. Sharing one body per (transaction, tenant) would save space but make deletion and quotas depend on a reference count; it is the first thing to revisit if measured volumes show the cost.
- **A mixed-tenant transaction is stored atomically:** `AcceptAsync` takes the drafts of the whole transaction and commits all or none. If the commit fails the sender gets one `451` and nothing is stored (it retries all recipients later); there is never a partial acceptance across tenants.
- `subject` is the decoded Subject, control characters removed, at most 256 characters, kept for the list view and search (it follows the message's retention, which already covers the body that contains it).
- **Initial state** (`InboundRules.InitialActionState`): webhook and forward start `pending`, due at `receivedAt`; store starts `done` with its body; discard starts `done`, **stores no body**, and the metadata row stays for the retention so the dashboard can show that something arrived and was dropped.
- **Search** is by tenant (always: `InboundMessageQuery.TenantId` is required, there is no all-tenants search; an administrator acts as a tenant with `X-Tenant-Id`), domain, recipient and sender (exact, case-insensitive), subject substring, route, action kind and state, DMARC verdict, DMARC-flagged, and a time range; newest first (UUIDv7 order, the same on both backends); cursor paging. The subject filter lower-cases the column in SQL and the term in the same ASCII-only way on every backend (SQLite's `lower()` and PostgreSQL's under the `"C"` collation change ASCII letters only); no `LIKE` is used, so there are no wildcard characters to escape. A search is a bounded page (at most 200 rows); an unbounded scan of a large table is not offered.
- **Erasure:** `DeleteMatchingAsync` deletes everything of the tenant that matches a filter (a sender, a recipient, a domain, an age) in batches; it requires at least one filter besides the tenant. This is the tool for a data-subject erasure request.
- **Usage** (stored bytes, pending and failed counts, oldest pending) is computed by indexed aggregates over the tenant's or domain's rows that have a body, and cached by the receive path for a few seconds; maintained counters would be faster but are one more piece of state that can drift, and are the first optimization if the measured cost matters.

### 11.7 Route actions (executed by a worker after the `250`)

A worker pool claims pending actions (`ClaimActionsAsync`: `FOR UPDATE SKIP LOCKED` on PostgreSQL so several replicas split the work, the queue writer on SQLite), runs them with a lease, and records the result with `CompleteActionAsync`, which only succeeds for the lease holder of **that claim** (the runner passes back the claim token the claim returned, `ClaimToken`: it grows with every claim of the row and never goes back down, so a completion from a claim whose lease ran out or was released and which was taken again, even under the same owner name, is refused; the attempt count cannot serve, because a release and a retry take it down). **The claim counts the attempt:** `actionAttempts` goes up when the row is claimed, not when it is completed, so a runner that dies in the middle of an attempt has used it up, and a message that kills its runner every time (a poison pill) reaches the end of the ladder instead of being claimed for ever; a graceful release (shutdown, quiesce) gives the attempt back. Attempts and retry follow the webhook ladder by default (`Inbound:Action:RetrySchedule`, *proposed*) and end in `failed` with `actionLastError`. **A deferral is an attempt:** when an action cannot be carried out now for a reason that is not the message's (a webhook endpoint that is disabled, storage that is busy) the runner records it as a failed attempt with a `Pending` outcome and the next rung, exactly like a failure, so it counts against the ladder and the action ends `failed` (about 27 h after receipt, with the last reason in `actionLastError`) instead of waiting for ever. (A tenant's sending cap or warm-up is **not** a deferral of the action: the forward is queued and the delivery engine paces it, 11.7.) **Pending rows when inbound is switched off:** with `Inbound:Enabled` off, or while the tenant is suspended, the runner carries out nothing; each action it finds is recorded as a deferral (`actionLastError` `inbound_disabled` or `tenant_suspended`), so it counts against the ladder like any other and ends `failed` if the switch stays off, and `retry` brings it back once the operator or the tenant has re-enabled it. This is the bound on the retention exemption of pending mail (11.8): no action can stay pending for longer than the ladder, whatever kept it waiting. A manual `retry` starts a new ladder. `retry` in the API puts a failed (or finished) webhook or forward action back to pending with its attempts reset and its **retry generation** increased. Delivery is at-least-once.

- **Webhook.** Signed with the endpoint's secret exactly like every other event (Standard Webhooks headers), through the same SSRF-guarded sender; sent whatever event types the endpoint subscribes to (the route is the subscription). Success is a 2xx within the webhook timeout; the existing disable-on-410 and continuous-failure rules apply to the endpoint.
  - **`webhook-id` is `evt_<inbound id>` for the first generation and `evt_<inbound id>-<generation>` after a manual retry**: automatic retries repeat the id (the receiver deduplicates them), a manual retry is a new event (the operator asked for it again, and a receiver that already processed the first must not drop it).
  - **A disabled endpoint:** the attempt fails with `endpoint_disabled` without sending and follows the retry ladder, so re-enabling the endpoint inside the ladder delivers the message; after the ladder the action is `failed` and `retry` brings it back.
  - Two formats:
  - `json` (default): the standard envelope `{ id, type: "inbound.message.received", timestamp, data }` with `data` =

    ```json
    { "inbound_id": "…", "domain": "example.com", "route_id": "…", "received_at": "…", "size": 12345, "dmarc_flagged": false,
      "connection": { "remote_ip": "203.0.113.9", "helo": "mail.sender.test", "tls": true },
      "envelope": { "from": "alice@sender.test", "to": "support@example.com" },
      "auth": { "spf": { "result": "pass", "domain": "sender.test" }, "spf_helo": { "result": "pass" }, "dkim": { "result": "pass", "domain": "sender.test" },
                "dmarc": { "result": "pass", "policy": "reject" }, "arc": { "result": "none" } },
      "message": { "message_id": "<…>", "subject": "…", "from": "…", "to": ["…"], "cc": [], "reply_to": null, "date": "…",
                   "in_reply_to": null, "references": [], "text": "…", "html": "…", "truncated": false,
                   "headers": [ { "name": "…", "value": "…" } ] },
      "attachments": [ { "index": 0, "filename": "a.pdf", "content_type": "application/pdf", "size": 1234, "content_id": null,
                         "disposition": "attachment", "url": "/api/v1/inbound/messages/<id>/attachments/0" } ],
      "raw_url": "/api/v1/inbound/messages/<id>/raw" }
    ```

    Text and HTML are each cut at `Inbound:Webhook:MaxTextBytes` (*proposed*, 256 KiB; `truncated: true`), headers are all unfolded and decoded header fields up to a total cap, **attachments are never inlined**: the payload lists them with a path (`Inbound:ApiBaseUrl`, *proposed*, is prefixed when set, otherwise the receiver knows its server) and the receiver fetches them with an API key that has the `inbound:read` scope. *Reason:* a webhook body of tens of megabytes would break receivers, retries and the signature window, and a pre-signed public URL would make a leaked payload equal to leaked mail (open question: signed expiring URLs).
  - `raw_mime`: the body is the stored message as is, `Content-Type: message/rfc822`, signed over those bytes; the envelope and verdicts travel in headers (`EggMail-Inbound-Id`, `EggMail-Envelope-From`, `EggMail-Envelope-To`, `EggMail-Remote-Ip`, `EggMail-Spf`, `EggMail-Dkim`, `EggMail-Dmarc`, `EggMail-Arc`, `EggMail-Dmarc-Flagged`). **Header values are ASCII: an address or name with other characters is percent-encoded (UTF-8)**, so a hostile envelope cannot inject a header or break the framing. **The size is capped per endpoint:** a message over `Inbound:Webhook:MaxRawMessageBytes` (*proposed*, 10 MiB) cannot be sent in this format: the action fails at once with `too_large_for_raw_webhook` (no retry would help) and the tenant is told to use the `json` format or the download endpoint.
  - A final failure also publishes `inbound.action.failed` (`data`: `inbound_id`, `route_id`, `action`, `error`) to the tenant's endpoints that subscribe to it.
- **Forward** goes **through the outbound queue**, so it gets the delivery engine's retries, TLS policy, throttling, suppression list and sending caps, and appears in the outbound message history with source `Forward`.
  - **The forward intake path** (decision 95): the forward is queued with `IMessageIntake.AcceptAsync` and `Source = Forward`, which differs from an API or SMTP submission in what it keeps and what it skips. *Kept:* the tenant's sending caps and warm-up, which the delivery engine applies **at delivery time, as for any queued mail** (there is no peek at the caps before queueing: the forward is queued, the action completes `done`, and a tenant at its cap simply sees the forwarded copy paced, exactly like its other mail); **the suppression list, which the runner itself consults before queueing**: it calls `IConfigStore.IsSuppressedAsync` for each target and queues only the others (suppressed targets are not an error), and when **every** target is suppressed nothing is queued and the action completes `done` with the note `all_targets_suppressed` (`InboundActionOutcome.Note`, shown in the API as `action.note`); the engine's retries, TLS policy and throttles; and the stored copy. *Skipped:* the sender policy (the From domain is the original sender's, not the tenant's, so "the From domain must be a verified domain of the tenant" cannot apply), header repair and the submission recipient limit (the route has at most 10 targets). *The body is delivered byte for byte:* no header repair, no added `Message-ID`/`Date`, and **no 8-bit downgrade or conversion** on the way out (it would break the original DKIM signature, which is what carries DMARC for the forwarded copy): to a server that does not offer `8BITMIME` (or `SMTPUTF8` where the message needs it) an 8-bit message is a permanent failure of that target (`5.6.1`/`5.6.9`), recorded on the outbound message, not rewritten. Only headers are added on top (`Received`, `Authentication-Results`, the loop marker, our signature and ARC set). *No bounce message of any kind is generated for source `Forward`:* neither a failure notice nor a delay notice, whatever `Delivery:GenerateDsnFor*` says; the tenant learns of a failed forward from the outbound message (`forwardMessageId`) and its `message.bounced` webhook.
  - **The idempotency key** is `inbound:<inbound id>` (`InboundRules.ForwardKey`), set with `AcceptedMessage.IdempotencyKeyLifetime` of 30 days (`InboundRules.ForwardKeyLifetime`), **not** the 24-hour API window: the retry ladder runs for about 27 hours and a manual retry can come days later, so a key that expired would queue a second copy. A retry after a crash between "queued" and "done" returns the same outbound message; its id is stored as `forwardMessageId`, and the body is freed when the action is `done`. **A forward carries no request fingerprint** (`AcceptedMessage.IdempotencyFingerprint` stays unset): the fingerprint exists to tell a safe API retry from reuse of a key with another body, which for a forward would only turn a legitimate retry after the operator edited `forwardTo` into a conflict. With the fingerprint unset, a retry with changed targets finds the key and returns the existing outbound message: the copy that was queued is the copy that exists, **the new targets are not sent to**, and the action completes `done` with that message's id. (To send a received message to other addresses the tenant uses the download endpoint; a forward is at most once per received message by design.)
  - **The key prefix is reserved, and a key that belongs to something else is a failure.** `Idempotency-Key` values that start with `inbound:` (or `eggmail-`) are refused by the public API (`400 validation_failed`): a caller who registered `inbound:<id>` first would make the forward complete `done` with its body freed and nothing queued. Where such a key already exists (it was registered before the prefix was reserved), the forwarder looks at the message it points at when history keeps a summary of it, and when that message is not a forward of this route (its envelope sender is neither the null one nor an SRS0 address at the route's domain) the action fails with `forward_key_conflict` and the body is kept. Where history keeps no summary (`StatsOnly`, or aged out) nothing can be told and the key is taken as ours.
  - **The queued backlog is capped (`Inbound:Forward:*`).** The copy is freed from the inbound store when it is queued, so the inbound quotas (11.4) stop seeing it, and the shared queue keeps it for `Queue:MaxLifetime` (5 days) whenever delivery stalls. Anyone who can send mail to the domain could grow the queue by the inbound rate limits times that lifetime. Before it queues a copy the forwarder counts, through the partial index on the queue rows of source `Forward` (schema version 10), the tenant's forwards still waiting (`MaxQueuedMessagesPerTenant`, default 5000; a message with several recipients counts once), their bytes (`MaxQueuedBytesPerTenant`, 1 GiB) and the ones sent from the route's domain (`MaxQueuedMessagesPerDomain`, 1000; a route lives in one domain, so this is the per-route bound without a column of its own on the queue row). Over a cap the action is a retry with `forward_backlog_full` (a deferral on the ladder, 11.7), the body stays in the inbound store and its quotas keep applying, and `mta_inbound_forward_refused_total{reason="forward_backlog_full"}` counts it; `0` is no cap. The count and the insert are not one atomic step, so the caps can be overshot by at most `Inbound:Action:MaxConcurrencyPerTenant` messages per replica for one tenant. The caps bound a thing that already existed: forwards are outbound mail of the tenant and share its sending counters and warm-up (below), so a flood of forwards can slow the tenant's own sending, and a copy that waits the whole `Queue:MaxLifetime` expires without any notice (a forward never produces a bounce); the caps keep that backlog small, and a separate counter scope for forwards is recorded as a follow-up in [open-questions.md](open-questions.md).
  - **The outcomes of a forward that is not queued** (each counted in `mta_inbound_forward_refused_total{reason}`, shown to the tenant as `actionLastError`): `forward_target_is_local` (a target is in the route's domain, in a domain this server receives for, or in the bounce domain: the loop closed at run time as well as at write time), `loop_detected` (the message proves three hops already; counted in `mta_inbound_forward_loops_total`), `unauthenticated_local_sender` (decision 98(d): the From is in the route's own organizational domain and DMARC did not pass, so the SRS envelope and our signature would make a spoof of the tenant's own domain pass SPF and DMARC at the final receiver; a From that cannot be read, and every From header of a message with several, count; DMARC `temperror` at receipt is not a verdict: the action records `dmarc_unsettled` as a deferral, but the verdict is the stored one and is not evaluated again, so the action runs its ladder (about 27 hours) and ends failed with that code, never forwarded), `invalid_forward_target`, `srs_failed` (the stored envelope sender cannot be read or no SRS address can be made: the forward never goes out with a null sender in its place), `forward_key_conflict` (above), and `forward_backlog_full` (above, a retry). The final delivery outcome of the queued copy is on the outbound message (events, webhooks, history) and is not copied back onto the inbound action, which is `done` when the copy was queued.
  - **Envelope:** `MAIL FROM` is an **SRS0** address at the recipient domain: `SRS0=<hash>=<timestamp>=<original domain>=<original local part>@<domain>`; a message that arrived with the null reverse-path is forwarded with the null reverse-path (a bounce is not turned into a message from us, and never gets an SRS address). The recipients are `forwardTo`. *Why SRS:* the final receiver checks SPF against the envelope sender, and our address is not in the original sender's SPF record; with the envelope at our domain SPF passes for it and DMARC alignment is carried by the original DKIM signature, which stays valid because the forward adds headers only on top and never changes the body or signed headers.
  - **The delivery engine keeps that envelope.** The engine replaces the envelope sender of outbound mail with a signed VERP address at `Delivery:BounceDomain` when one is configured; for source `Forward` it must not (one condition in `ChooseEnvelopeFromAsync`), because the forward's envelope domain is the route's domain, the one whose SPF the final receiver checks and the tenant verified. The consequence is stated in the API: a forward route on a domain whose last `spf` record check is not `ok` is created with a warning `spf_not_ok`, since SPF at the final receiver will not pass for it (the original DKIM signature may still carry DMARC). *Considered and not chosen:* leaving the VERP rewrite on for forwards. It would route async bounces through the existing attributed bounce path with no new code, but the final receiver would then see the operator's bounce domain, not the tenant's, in the envelope, and the owner asked for SRS.
  - **Hash and key:** the first 8 characters (40 bits) of Base32 of HMAC-SHA256 over `lower-case(timestamp "=" original domain "=" original local part)` (implementation: `=` between the fields, so a character moved from one field to the next changes the hash; decision 103), key derived by HKDF from the bounce-token key with the purpose `EggMail.Srs.v1` (so no new secret to deploy or back up). **Signing uses the active key of the VERP key ring and verification tries every key id of the ring** (`VerpCodec` holds up to 16 keys by id; an SRS address carries no key id, so the hash is checked against each derived key in turn, each comparison constant time): rotating the bounce key therefore does not invalidate SRS addresses in flight. The hop marker is verified the same way; the timestamp is the day number modulo 1024 in two Base32 characters; verification is constant time and accepts the current and previous 20 days (`Inbound:Srs:MaxAgeDays`, *proposed*, 21).
  - **Long addresses:** the SMTP local part is limited to 64 octets, and the original domain (up to 255) and local part (up to 64) together can be far longer. When `SRS0=<hash>=<tt>=<domain>=<local>` is longer than 64 octets, the domain and the local part are **both** replaced by one token: `SRS0=<hash>=<tt>=x=<first 32 hex digits of the SHA-256 of lower-case(domain + "=" + local)>` (5 + 8 + 1 + 2 + 1 + 2 + 32 = 51 octets, so the result is at most 64 whatever the original). The hash covers the original domain and local part through the digest (the hash input of the shortened form is `tt=x=<digest>`), so the shortened form is as hard to forge as the long one. A local part or domain that is not plain (lower-case ASCII letters, digits and `. _ + -`) also gets the shortened form, and the 64 octets are counted in octets. This is safe because **we never reverse an SRS address** (next bullet); the cost is that a human reading the shortened form cannot tell who the original sender was, which the headers and the stored message still say.
  - **SRS bounces are not relayed (DESIGN-DECIDED, owner-level, see open questions).** A DSN for a forwarded message returns to the SRS address on port 25. The receive path accepts it (verifying the hash and age, only from the null sender, size-limited), counts it (`mta_inbound_recipients_total{outcome="srs_bounce"}`), logs it without addresses, and **drops it**. Classic forwarders relay it to the original sender; that is backscatter to what is usually a forged sender, and it makes a forged SRS address an open relay. Not relaying removes both. The tenant, who owns the route, learns that a forward failed from the outbound side: the forwarded copy is an ordinary outbound message of the tenant (`forwardMessageId`), so a refusal during delivery is a `bounced` event in its history and a `message.bounced` webhook event. A bounce that arrives later, after the target accepted the message, cannot be attributed to a message (an SRS address names the original sender, not the inbound message) and is only counted.
  - **Loops are stopped three ways.** (1) *At configuration time* the API refuses a target in the route's own domain or in any domain that is inbound-enabled on this server (11.6). (2) *A signed hop marker survives header stripping.* The marker is the header `X-EggMail-Hops: <n>; <signature>` where `signature` is the first 16 hex digits of `HMAC-SHA256(key, "EggMail.Hops.v1\n" + n + "\n" + hex(SHA-256(body)))`, `body` being the message body bytes after the first empty line exactly as stored (CRLF lines), and `key` derived from the bounce-token key with the purpose `EggMail.Hops.v1` (signed with the active key of the ring, verified against every key of the ring). **The input has no header in it** (no `Message-ID`, no `Date`, no `From`): headers are what senders, lists and the next hop rewrite, the forward delivers the body byte for byte, so a body hash is the one thing that survives an honest forward and that a forger would have to know to produce a valid marker. *Rules on receipt:* every `X-EggMail-Hops` header is checked; those with an invalid signature are removed (forged, or the body changed on the way: the count restarts at zero, which is the safe direction for mail, and the config-time checks still apply); among the valid ones only the **highest `n`** is kept, the others are removed, so a message never carries two markers. A message arriving with `n >= InboundRules.MaxForwardHops` (3) is **not forwarded** (the action fails with `loop_detected`; webhook, store and discard still work). *Rules on forward:* the forward **removes the old marker** and writes exactly one new one with `n + 1` (or `1` when there was none). A sender cannot lower the count (it would have to forge the signature), cannot raise it to block a victim's forwarding (a forged high count is removed as invalid), and cannot add a second marker to confuse the count. (3) **A `Received`-count limit on the Inbound role** (agent B, Mta.Smtp.Server): a message with more than 25 `Received` headers is refused at the end of DATA with a permanent `554 5.4.6 Too many hops`. The marker is dropped by a forwarder that changes the body (a footer, a list manager), so a loop through one is not counted by it; that loop is bounded by this limit, the tenant's sending caps and the configuration-time checks. (The `MaxReceivedHeaders` of 100 in `Mta.Mime` belongs to submission validation and does not run on this role.)
  - **Signing: a forward is never DKIM-signed with the original From domain (DESIGN-DECIDED).** The forwarded message keeps the original `From` of someone else's domain, which the tenant does not own and has no key for; signing it with `d=` that domain would be impossible, and signing it with `d=` the tenant's domain while the `From` says another would be a valid-looking signature that proves nothing and teaches receivers to ignore ours. So the delivery engine, for source `Forward`: **keeps every DKIM signature the message arrived with** (they stay valid because headers are only added on top and the body is untouched, which is what carries DMARC for the forwarded copy); **adds one signature, with the key of the route's domain** (the tenant's own domain and key, `d=` that domain; **always the route's domain, also for a forward with the null reverse-path, which has no SRS envelope domain**), and never one with `d=` the original From domain; and adds an ARC set (below) with the same key. If the route's domain has no active key the forward is unsigned and unsealed rather than signed with anything else. *What the added signature is:* an **unaligned, reputation-scoped** signature. It does not align with the `From` domain, so it contributes nothing to DMARC (the original signatures carry that); it ties the copy to the tenant's sending domain, so a receiver can score the tenant's forwarding separately from the tenant's own mail and from the original sender. This is a rule of the outbound signer, not of the receive path, and it needs a regression test (11.15): *a forward of a message `From: x@other.test` has no `DKIM-Signature` with `d=other.test` added by us, and the original one is byte-identical*.
  - **Abuse limits:** forwarded mail is outbound mail of the tenant: the tenant's `Sending:PerHour`/`PerDay` caps and warm-up apply. ARC: when the route's domain has an active DKIM key, the forward is ARC-sealed with that key (continuing the chain we validated, bounded as in 11.5) so the next receiver can see the verdicts we recorded. **When the chain we received failed validation the new seal carries `cv=fail`** (RFC 8617 section 5.1.1: a sealer that cannot validate the chain says so and does not vouch for it); with no chain it is `cv=none`, with a valid one `cv=pass`.

- **Store** keeps the message (`done` at once) for `retentionDays`, readable through the API and the dashboard (11.9). **Discard** keeps only the metadata row.

### 11.8 Retention

- A message (row and body) is deleted when `receivedAt` is older than its domain's retention (`retentionDays`, else `Inbound:RetentionDays`, default 7, both cut to `Inbound:MaxRetentionDays` when that is set; **`0` keeps forever** unless a ceiling forbids it, with the usual warning and health entry, 5.1). The convention is the one of every other retention knob. The clock is `receivedAt`, which is also the time embedded in the UUIDv7 id (both are the instant of acceptance), so retention by time and the day of the id agree.
- **The cutoff is read from the current settings when the job runs, not stored on the message.** Shortening a domain's retention frees old mail at the next run and lengthening keeps it, which is what an operator changing the setting expects. A domain with no settings row any more (deleted) uses the server default.
- **A message whose action is `pending` is never deleted by retention.** Pending is bounded by the retry ladder (about 27 hours; a deferral counts as an attempt, 11.7), so this cannot keep mail forever, and it prevents silently losing mail that was never delivered to a webhook. A `failed` message follows the normal retention like any other row (it is the tenant's record of what failed and the source for `retry` until it expires).
- A completed forward and a discard have no body to expire; their rows follow the same cutoff. The API's `DELETE` removes one message at once, `DeleteMatchingAsync` many.
- **Mechanism:** the job `inbound_retention` of `IStorageMaintenance.RunAsync` (idempotent, safe on several replicas): per domain with a finite retention, delete in batches ordered by `(domain_id, received_at)` with the same batch size and pauses as the other retention jobs, bodies first then rows, then `incremental_vacuum` on SQLite. **Batched deletes on both backends; PostgreSQL does not use partition drops for inbound (DESIGN-DECIDED).** *Reason:* retention differs per domain and can be unlimited for one domain, while a partition holds mail of all domains of a day: dropping a partition is only correct when every row in it has expired, which with mixed retention would need a per-partition scan anyway; inbound volume is far below the history volume the partitions were designed for; the batched delete is the same code path on both backends. Revisit if inbound volume is large (4.3's thresholds).
- Unlimited retention with the `store` action grows the database without bound; the stored-bytes limits (domain 2 GiB, tenant 10 GiB by default) are the guard, and a domain at its limit refuses new mail with `452 4.2.2` instead of filling the disk.

### 11.9 Retrieval API, dashboard and rate limits

- **API** ([api.md](api.md#inbound-mail-inboundread-and-inboundwrite-scopes)), two scopes instead of one: **`inbound:read`** (settings and routes `GET`, the route test, search, one message, raw, attachments, usage) and **`inbound:write`** (`PATCH` of settings, route create/change/delete, delete one or many messages, retry). They are separate from `read` because reading received mail exposes other people's mail, and separate from each other so an application that only fetches mail cannot change routes or delete mail. A key may hold both; `write` does not imply `read`. **`inbound:write` is not a harmless scope:** a key that can create routes controls where *future* mail goes (a `webhook` or `forward` route sends every matching message to an address the key chooses), so holding it is the ability to read the mailbox from now on without ever calling `inbound:read`. Two consequences: the documentation says so where the scope is described, and **a route whose action is `forward` also needs the `send` scope** (the forward is outbound mail of the tenant, and `send` is the scope that means "this key may make the server send mail"); creating or changing the action of a `webhook` route needs the tenant's own endpoint, which is already a `webhooks`-scope object. Tenant isolation as everywhere: a message of another tenant is a `404`. **Deleting a domain that still has stored inbound messages is refused (`409`, reason `inbound_messages_exist`) unless the request says `purgeInbound=true`** (which needs `inbound:write` as well as `domains`): the messages belong to the domain, a deleted domain would leave them unreachable but kept and counted until retention, and an erasure request is the case where "deleted" must mean deleted. With the flag, receiving is switched off for the domain first (its settings say `enabled: false`), then the messages and bodies are deleted in batches, then the domain with its settings and routes; the 409 names the number of messages only to a key that may read them. **Erasing by filter** (`DELETE /inbound/messages` with filters) needs at least one filter besides the tenant (`domainId`, `recipient`, `sender`, `subject`, `route`, `action`, `state`, `dmarc`, `dmarcFlagged`, `from` or `to`); there is no "delete all mail of the tenant" call, which a mistyped query could trigger (delete the domain with `purgeInbound=true` for that). Raw and attachment downloads are served as `Content-Disposition: attachment`, `X-Content-Type-Options: nosniff`, `Cache-Control: no-store`, with a sanitized file name; nothing received is ever served inline.
- **Dashboard:** inbound messages (list, search, view with verdicts, sandboxed HTML rendering as in 5, headers, attachments, raw download, retry/delete), routes per domain, inbound settings, and the MX record in domain onboarding. Same pages on both backends. It reads `capabilities.inbound.enabled` to show or hide them.
- **Rate limits** (per process, not shared between replicas, like the other in-memory limits of decision 82): domain-wide and per-remote-address messages per minute from the settings, counted at RCPT, in bounded dictionaries (11.4); at the limit the reply is `450 4.7.1`, which well-behaved senders retry. A shared exact count would need a database round trip per RCPT for little gain.

### 11.10 Storage layout, switch and operations

- **Config part** (`config.db` on SQLite): `inbound_domain_settings`, `inbound_route`. **Queue part** (`queue.db`): `inbound_message`, `inbound_message_raw`. *Reason for the queue part:* a forward is queued in the same file as the action's state change (no second ordering story), the claim is the same single-writer / `SKIP LOCKED` machinery as deliveries and webhook outbox rows, and the switch holds these rows with `transfer_switch_id` exactly like deliveries. The cost is that stored mail grows `queue.db`, the hot file, the same trade-off the webhook outbox documents (5.1); the quotas and a finite retention keep it bounded, and a deployment that stores a lot of mail should use PostgreSQL.
- **Schema versions:** a new SQLite schema version (next free at merge time) and a PostgreSQL migration. Four new tables, no change to existing ones.
- **Switch bundle:** the four tables are transfer tables (bundle format minor bump; an importer that knows the older minor imports a bundle without them and starts with no inbound data). Settings and routes move with config; messages and bodies move with the queue part, with the body streamed like spool bodies; pending actions are held on the source until the switch finishes, so no message is acted on twice. Inbound mail is **not** history (11.1): `--skip-history` does not skip it, and the size warning of 11.1 applies.
- **Backup/restore and quarantine** need no change: they work per file.
- **Health:** a warning entry for `Inbound:RetentionDays` = 0 and gauges of pending and failed actions (11.11).

### 11.12 Security considerations

- **Open relay.** Three independent layers: (1) the listener role `Inbound` accepts a recipient only for an inbound-enabled domain **with a matching enabled route**, the bounce domain's signed addresses and SRS addresses (11.4, 11.7); everything else is `550 5.7.1` at RCPT; (2) inbound-listener sessions can never authenticate or send, and the only path from inbound to outbound is a forward route that an authenticated tenant created, to targets fixed in the route (never taken from the message); (3) the outbound queue applies the tenant's sending caps and suppression list to forwards. Regression tests: unknown domain, enabled domain with no route, disabled route, `RCPT` to an external address after a valid one, a `MAIL FROM` of a local domain without authentication (accepted as an external sender, verified, never relayed), a forward whose target the message tries to change, and a bounce recipient and an inbound recipient in one transaction (the second gets `452`).
- **Backscatter.** No bounce, auto-reply, vacation reply, read receipt or "forward failed" mail is ever generated for inbound mail. Refusals happen in the dialog; a failed action is recorded and published to the tenant only; SRS bounces are dropped and a forward never produces a bounce message of any kind (11.7). The existing rule that an outbound bounce goes only to a verified sender is unchanged.
- **SRS forging.** An attacker who guesses an SRS address gains nothing, because an SRS address is accepted only from the null sender, is only verified-then-dropped, and is never mapped to a destination. The 40-bit hash and 21-day window still stop noise; the key is derived (no extra secret) and compared in constant time.
- **A spoofed From with a passing SRS envelope is inherent to forwarding.** A message from `ceo@bank.example` that failed DMARC at receipt is still forwarded to the route's targets when the From is foreign: the copy carries our SRS envelope (SPF passes at the route's domain) and the original, now failing, signatures, and the final receiver's DMARC decision on `bank.example` is what protects the recipient, as for any forwarder. The one case that would turn a failure into a pass, the route's own organizational domain, is refused (`unauthenticated_local_sender`). Owner-level options, not built: confirmation of each forward target by the target's owner before the first copy (as Cloudflare Email Routing does), and forwarding only mail that did not hard-fail DMARC ([open-questions.md](open-questions.md)).
- **Forwarding and reputation.** A forward is never signed with the original From domain (11.7): our signature says "this tenant's server handled it", nothing more, so a receiver's view of the tenant's domain is not spent on mail the tenant did not write. The original signatures stay valid because the body is untouched.
- **Forwarding loops and amplification.** The signed hop marker (3 hops, dropped by body-modifying forwarders, which the `Received` limit of 25 then bounds), the refusal of own-domain and local inbound-domain targets, the cap of 10 targets per route, the tenant's sending caps, and the fact that one inbound message produces at most one outbound message of at most 10 recipients.
- **Spam and abuse.** The server is a receiver for customer domains, so it receives spam. Recorded SPF/DKIM/DMARC verdicts and the DMARC action are the first defense; per-domain and per-remote rate limits and connection caps bound the load; the DNSBL hook is optional; greylisting is not built in. Forwarding multiplies abuse into outbound reputation, which is why forwards are subject to the sending caps, warm-up and the suppression list, are ARC-sealed and SRS-rewritten, and why a tenant that forwards spam can be suspended (a suspended tenant's inbound answers `450`, its forwards stop). Operators should publish an abuse contact (10).
- **Denial of service.** Existing connection caps, per-IP caps, the in-flight bytes budget, timeouts and the errors-per-session limit; plus the recipient cap and the transaction byte budget, the rate limits (bounded dictionaries, IPv6 by /64), the per-domain and per-tenant stored-bytes limits and the per-domain size limit under the operator's ceilings, a bounded verification time and concurrency with an immediate `451` when the slots are taken, and bounded MIME work (the extraction used for `subject` and the webhook payload runs with the parser's part, depth and header limits, and a message that exceeds them is stored without extracted fields rather than rejected). A full disk answers `452 4.3.1` as for submission.
- **Storing hostile content.** The body is untrusted bytes and is never interpreted by the server beyond headers and bounded extraction. The API serves raw mail and attachments only as downloads with `nosniff`; the dashboard renders HTML only in a sandboxed iframe under the strict CSP with remote content blocked (a tracking pixel would tell the sender when the tenant read the mail) and plain text as the default; file names are sanitized for download headers; webhook receivers are told in the documentation that every field is attacker-controlled. Control characters are stripped from the stored subject. Header injection is not possible through the extraction (values are JSON strings) or through the raw webhook headers (percent-encoded ASCII).
- **Attachments by reference.** The webhook payload names attachments and gives an authenticated path; it carries no credential and no pre-signed URL, so a leaked payload does not leak the attachment.
- **Route control is mailbox control.** `inbound:write` decides where future mail goes (11.9); a forward route needs `send` as well, and a leaked key with `inbound:write` is as serious as one with `inbound:read`.
- **Tenant isolation.** Every inbound query takes the tenant (required by the type); a recipient domain belongs to exactly one tenant; bodies are not shared between recipients; the `inbound:*` scopes are separate from `read`.
- **Domain squatting.** Enabling needs a verified domain (11.3), and a domain that lapses is not served (`450`).
- **Recipient enumeration.** `550 5.1.1` reveals which local parts have a route, as every MX does; a catch-all route removes the signal, and the errors-per-session limit and connection caps slow harvesting.
- **Header spoofing.** Our `Authentication-Results` and `X-EggMail-*` headers (except a validly signed hop marker) are removed from the incoming message before ours are added (11.5).
- **Client address integrity.** SPF, the DNSBL and the per-remote limits are only as good as the address the server sees (11.4): source NAT must be avoided, the server warns when addresses look internal, and an IPv4-mapped IPv6 address is normalized.
- **Privacy.** Received mail is personal data kept for 7 days by default; `0` (forever) shows the warning and the operator can forbid it with a ceiling; `DELETE`, the erasure endpoint and retention remove body and metadata. A domain's mail goes to its tenant only. A DNSBL query discloses connecting addresses to the list operator.
- **Inherited:** smuggling defenses, STARTTLS-injection defense, SSRF guard on webhook endpoints, Data Protection for secrets (nothing new is stored encrypted: the webhook secret stays with the endpoint).

### 11.15 Test plan (for the receive path and the security tests)

The tests run against real listeners on loopback with **a fake remote MTA** (a scripted SMTP client that connects from a chosen source address; the tests use a seam for the client address, because the real one is always loopback) and **a DNS seam** (`IDnsResolver` with scripted SPF, DKIM, DMARC, ARC and DNSBL answers, including SERVFAIL and timeouts). Both backends and the in-memory store run the same storage contract (`InboundConformance` in `Mta.Storage.Tests` is the abstract base class any backend or test double must pass; `InMemoryStorage` is the reference store the other suites build on). Cases: valid and invalid recipient, unknown domain, domain with no route, disabled route, `postmaster`, plus addressing, wildcard; SPF/DKIM/DMARC/ARC pass and fail, `temperror` under each action, the multi-recipient reject rule, mixed bounce/inbound recipients (`452`), SRS accept and drop; oversize at MAIL and DATA, recipient cap, transaction budget, quotas; rate limits including IPv6 /64 and the mapped address; slots full (`451`); smuggling and STARTTLS injection (the existing suites on the new role); open-relay and backscatter regressions of 11.12; every action (webhook json and raw_mime with a fake receiver, forward through a fake outbound target, store, discard) with retries, manual retry (new webhook id), a disabled endpoint, a deleted route, loop marker forged/valid/at the limit; retention with pending exemption and ceilings; the switch carrying pending actions. Regressions the review made necessary: **a `Reject` DNSBL hit refuses the first inbound `RCPT` and leaves bounce and SRS recipients of the same connection alone**; `postmaster@<bounce domain>` and `abuse@<bounce domain>` are accepted as bounce recipients, an invalid token at the bounce domain and at a return-path host answers `550 5.1.1`; **a forward of a message whose From is another domain carries no new `DKIM-Signature` with `d=` that domain, keeps the original one byte for byte, and carries one with `d=` the route's domain**; a client that declares no `SIZE` or a small one and sends a large body is refused at the end of DATA with `452` when the transaction budget is exceeded; a client that trickles a body holds no verification slot, and one /24 cannot take all the slots; `reject` plus `temperror` is `451` only when every accepted recipient says `reject`; the hop marker with two markers, with a forged one, with a changed body, and a forward that replaces the old marker; a long original address gives an SRS local part of at most 64 octets; a retry of a forward after `forwardTo` was edited returns the existing outbound message; a deferral (disabled endpoint) counts against the ladder, a crashed attempt is counted at the claim, and a forward of a tenant at its cap is queued and paced by the engine; a route that became `store` completes with `route_is_now_store`.

### 11.16 Dependencies on other changes and who changes what

The bounce-trust change (decision 92: verified return-path hosts, bounce addresses bound to the destination domain, `postmaster` and `abuse` at the shared bounce domain) and the BDAT line-ending fix (decision 93) are in `main`; the classification order of 11.4 and the single body rule of 11.4 rely on them.

**Agent B (the receive path) owns every change in `Mta.Smtp.Server` and `Mta.Host/Ingest`:**
- **A start-of-DATA hook** in `ISmtpServerHandler` (next to `OnRcptToAsync` and `OnMessageAsync`): the server has no hook between the last `RCPT` and the end of the message today. The Inbound role uses it for the look at the free verification slots (11.5) and the early budget answer, and the hook returns a reply to refuse DATA.
- **`ListenerRole.Inbound`**, a superset of `Bounce`, and the role checks in `IngestHandler` (today `session.Role == ListenerRole.Bounce` at three places): a session of any role other than `Submission` must never reach the submission path (AUTH, relay, sender policy), so those checks are written `Role != Submission` for the "not a submitter" side and `Role == Inbound` / `Role == Bounce` for the dispatch to the bounce processor or the inbound handler.
- **The message size limit per domain.** The session-wide limit is the operator's ceiling (`Inbound:MaxMessageSize`, the largest any domain may have). The per-domain `maxMessageBytes` (`InboundRules.Effective`) is enforced at two points: **at each `RCPT`, a declared `SIZE=` above the lowest effective limit among the recipients accepted so far and this one is refused with `552 5.3.4` for that recipient** (the earlier recipients stay accepted; a client that wants the others sends the message again without that recipient), and **at the end of DATA, an actual size above the lowest limit among the accepted recipients is refused with `552 5.3.4` for the whole transaction**.
- The `Received`-count limit of 25 (`554 5.4.6`, 11.7), the transaction budget re-check at the end of DATA (11.4), the verification slots (11.5), the DNSBL at the first inbound `RCPT` (11.5), and the BDAT behaviour of decision 93.

**Agent C (the route actions) owns the delivery-engine changes for `Source = Forward`, all in `Mta.Delivery` and its signer:**
1. `ChooseEnvelopeFromAsync` (`DeliveryProcessor`): source `Forward` keeps its envelope (SRS0, or the null reverse-path) and gets no VERP rewrite.
2. A **byte-exact flag** on `OutboundTransaction` for `Forward`: no 8-bit downgrade, no `Message-ID`/`Date` repair; a server without `8BITMIME`/`SMTPUTF8` is a permanent failure of that target.
3. **`ArcSealer` wired into the forward path**, sealing with the key of the route's domain and `cv=fail` when the chain we received failed validation (`cv=none` without a chain).
4. **Signing with the route's domain, always** (also for the null reverse-path, which has no SRS domain), keeping the original signatures, never `d=` the original From domain (11.7).
5. **No bounce of any kind for `Forward`**: `DsnService.Applies` already returns false for it, and the test `ForwardDsnTests` (in `Mta.Delivery.Tests`) pins that whatever `Delivery:GenerateDsnFor*` says; the delay notice path must go through the same method.
6. The runner side (11.7): `IsSuppressedAsync` before queueing, `IdempotencyKeyLifetime` of 30 days with no fingerprint, the hop marker and the SRS address.
