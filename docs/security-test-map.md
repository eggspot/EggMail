# Security test map

**This is not an independent audit.** It is the in-house security review turned into regression tests: every threat in [security.md](security.md) and the design, and every finding of our own reviews (the plan-coverage audit, the review rounds recorded in the pull requests, the `Security` entries of the [changelog](../CHANGELOG.md)), has at least one automated test. Most of them fail when the control they guard is removed; a few only pin an outcome (a documented limit, a source check, a map row marked as such) and are named for what they are. A test that passes shows that the attacks we thought of do not work today; it says nothing about the ones we did not think of. An external audit is still recommended before production-critical use ([security.md](security.md#known-gaps)).

How to read the table: *Id* is stable (tests refer to it in their summary comment). *Status* is `new` (written for this map), `existing` (written earlier, mapped here), `fixed` (the new test found a defect, fixed in the same change, decision 101) or `gap` (not tested or not fixed, see [Gaps](#gaps-and-open-questions)). Test names are `Project / Class / Method`; a class name alone means every test of the class.

Run them all with `dotnet test EggMail.slnx -c Release`; the PostgreSQL parts run when `EGGMAIL_TEST_POSTGRES` or local PostgreSQL binaries are available (CI always has them). No test asserts how long something took (a few use short real timeouts of a second or less to make a server give up, and wait for that, which is not the same).

## Findings fixed while writing these tests

1. PostgreSQL refused NUL (and unpaired surrogates) in any text: a NUL in a query value, a user name, or text a remote server controls (a certificate name, a host name) made the query fail (HTTP 500, or a delivery result that could not be recorded). SQLite stored them. Now a write never fails and a lookup with such text matches nothing on either backend; the stored text of a write still differs (PostgreSQL stores U+FFFD in their place; see `StorageText`).
2. Three independent address classifiers (webhooks, MTA-STS/TLS-RPT, MX) disagreed (documentation ranges, IPv4-compatible and IPv4-translated IPv6, Teredo, site-local, the local-use NAT64 prefix). One classification, `Mta.Core.NetworkAddresses`, now serves all three (the MX guard is its own question on the same classification: everything that is not public is refused for a recipient-controlled host, except the documentation ranges, which are kept on purpose and tested both ways).
3. A recipient domain could point its MX at `10.x`, `192.168.x`, `169.254.169.254` or `fd00::` and the SMTP client connected (`operations.md` said such MX hosts are excluded unless `Delivery:AllowPrivateMxAddresses`; the code only excluded loopback and reserved ranges). Recipient-controlled hosts now exclude every non-public address; relay hosts the operator chose still may be internal. A domain whose only addresses are refused is held (temporary `AddressesRefused`, 4.4.4, retried until the message expires and the bounce then names the setting); it is not a permanent failure and its recipients are never suppressed.
4. A webhook URL could be registered with a trailing dot on a loopback or metadata address (`https://169.254.169.254./`), as `x.localhost`, or with line breaks and spaces inside (stored as text). Delivery was safe (the guard checks the connection), the registration was not.
5. Names accepted line and paragraph separators, text direction overrides and unpaired surrogates (key, tenant, user, relay login, tags, attachment file names); internationalized local parts accepted the same.
6. `BundleReader.PathOf` did not check containment (the manifest was checked when opened).

## Gaps and open questions

* **Not an audit.** The tests were written by the same team that wrote the code, from the same understanding of the threats.
* Timing side channels are not measured (no wall-clock assertions by rule); constant-time comparison is guarded by a source test and review.
* Hostile DNS answers against the real resolver, TLS interoperability with other stacks, container hardening, `testssl.sh`, and the design's external attack suites (smtpsmug, EAST) were not run: see [security.md](security.md#known-gaps).
* **Domain names are first come, first served.** A tenant can register a domain name it does not own, and the real owner then cannot register it ("This domain is already registered"). Sending needs the domain to be verified, so this is a denial of onboarding, not of sending, and: (1) the operator can free a name by deleting the registration as an administrator; (2) the "already registered" answer tells any tenant that some other tenant registered the name (an enumeration oracle, small because the names are public DNS names); (3) a *verified* name keeps blocking a new owner, for example after a domain changes hands, until the old tenant deletes it. **Owner decision needed.** A possible later fix: the name is unique only among *verified* domains and the first to verify wins (an unverified registration never blocks, and a verification evicts the others); this needs a change in the domain model and the verification service, so it is not done here.
* The session cookie is `Secure` unless the request is plain HTTP from a loopback peer; behind a reverse proxy on the same host the cookie is not `Secure` unless the forwarded headers are enabled or `Api:CookieSecure=Always` (documented in `components/api.md`; the dashboard should be reached over HTTPS only).
* `Delivery:AllowPrivateMxAddresses` now covers internal networks for recipient domains. Deployments that delivered to a mail server on a private address through its MX record must set it, or use a relay route for that domain (relay hosts may be private). **Setting it to true re-admits everything for recipient-controlled MX hosts, loopback and 169.254.169.254 included**; there is no allowlist of networks. The per-domain relay route is the narrow alternative; a CIDR allowlist option is the other way and is not built.
* Explicit text direction controls (LRE, RLE, PDF, LRO, RLO, LRI, RLI, FSI, PDI) and the line and paragraph separators are refused in names, tags, file names, filters, URLs and local parts as a set (`UnsafeTextRuleTests`, both directions); the direction marks (LRM, RLM, ALM), joiners and every script are accepted. The switch bundle containment check does not resolve symbolic links; the manifest hashes are what notice a changed file.
* Inbound forwarding (decision 98, [security.md](security.md#inbound-forwarding)):
  * *Laundering and signing:* `InboundForwardPipelineTests.A_spoofed_from_of_a_domain_that_also_holds_a_dkim_key_here_is_never_signed_with_that_domain` (the From domain holds a key of its own, same tenant and another tenant: only `d=` the route's domain on DKIM and ARC, SRS envelope at the route's domain), `ForwardDeliveryTests.A_forward_is_signed_with_the_route_domain_only_and_the_original_signature_stays_byte_identical`, `InboundForwarderTests.A_spoof_of_the_routes_own_domain_that_failed_dmarc_is_not_forwarded_but_authenticated_mail_of_it_is` (every From header, groups, unreadable From), `A_dmarc_result_that_could_not_be_settled_for_the_own_domain_waits_on_the_ladder_instead_of_failing_for_good`, `A_sealer_is_only_ever_taken_from_the_tenant_that_owns_the_domain`.
  * *Unusable From (decision 106):* `InboundForwarderTests.A_from_the_receive_path_judged_unusable_is_never_forwarded_and_is_counted_while_a_foreign_from_that_failed_dmarc_still_is`, `InboundForwardSenderCheckTests` (INB-29).
  * *SRS and the envelope:* `ForwardMarkingTests` (long, non-ASCII and awkward original addresses give at most 64 plain-ASCII octets that verify; forged and foreign addresses do not), `InboundForwarderTests.An_envelope_sender_that_cannot_be_read_fails_the_forward_instead_of_going_out_with_a_null_sender`, `The_null_reverse_path_stays_null_and_is_never_turned_into_an_srs_address`; the receive path drops SRS bounces (`InboundReceiveTests`).

  * *Not covered:* the final receiver's treatment of a forwarded spoof of a foreign domain (inherent, see security.md); the sending-counter sharing between forwards and the tenant's own mail (follow-up).
