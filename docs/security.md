# Security model

Status of the security work, written to be checked against the code and the tests. **No independent audit has been done.** Items marked *gap* are not implemented or not verified. [security-test-map.md](security-test-map.md) maps every threat below and every finding of our own reviews to the automated test that guards it; it is the in-house review as regression tests, **not** an independent audit.

## Trust boundaries and what protects them

| Boundary | Threats (STRIDE) | Controls implemented | Evidence |
|---|---|---|---|
| **SMTP in (submission and bounce listeners)** | Spoofing, tampering, DoS, elevation (open relay) | Only CRLF ends a line and `.` terminator is recognised by a state machine, so smuggling variants are refused (`DataScanner`); bare CR/LF refused; commands sent behind `STARTTLS` are discarded (injection guard); `BDAT` chunks are inert; AUTH PLAIN/LOGIN only after TLS; per-IP and global connection caps, in-flight byte budget, line/size/recipient/error limits, timeouts; no path from an unauthenticated session to the delivery queue (the bounce listener accepts only signed bounce addresses and never queues mail for delivery); sender domain must belong to the tenant and be verified (`SenderPolicy`) | `Mta.Smtp.Protocol.Tests` (smuggling vectors, chunk independence), `Mta.Smtp.Server.Tests` (STARTTLS injection, limits, garbage fuzz), `Mta.Host.Tests` (`IngestTests`: auth, unowned sender domain, relay attempts on the bounce listener, forged bounce token) |
| **SMTP out (delivery)** | Tampering (downgrade), information disclosure | STARTTLS stripping/injection guard in the client; MTA-STS and DANE policy resolution per MX, enforced validation; per-domain TLS level overrides; `possible_duplicate` marking; DKIM signing at delivery; envelope sender is a signed VERP token | `Mta.Smtp.Client.Tests`, `Mta.Tls.Tests`, `Mta.Delivery.Tests` |
| **DNS** | Spoofing, DoS | Random IDs and source-port randomisation by the OS, answer must match the question, optional 0x20, bounded CNAME chains, response size and record limits, DNSSEC/AD bit only trusted when configured; MX hosts of a recipient domain that resolve to special-use or internal-network addresses (loopback, private, link-local including the cloud metadata address, CGNAT, unique-local, and the IPv6 forms that embed them) are excluded by default (`Delivery:AllowPrivateMxAddresses=false`; decision 101) | `Mta.Dns.Tests` |
| **Hostile message content (MIME, DKIM, SPF, ARC parsers)** | DoS, crashes | Explicit limits on header bytes/count, nesting depth, parts, decoded size, parameters, addresses; parsers never throw on input and set anomaly flags; allocation budgets; seeded mutation fuzzing and exhaustive prefix/deletion sweeps; differential tests against MimeKit; coverage-guided fuzzing (see [Fuzzing](#fuzzing)) | `Mta.Mime.Tests`, `Mta.Dkim.Tests`, `Mta.Auth.Tests`, `Mta.Fuzz.Tests`, `.github/workflows/fuzz.yml` |

| **Credentials** | Spoofing, brute force | Passwords: PBKDF2-SHA256, 600,000 iterations, per-password salt, constant work for unknown users; API keys: 256-bit random, only a SHA-256 digest is stored, constant-time comparison; failed-login throttling shared between SMTP AUTH and the API, and between replicas on PostgreSQL (one budget, keys stored as HMAC-SHA256 digests under a Data Protection-protected key; per process on SQLite, which is one process), and applied to the current-password check of `POST /me/password` (a side effect: someone holding a stolen session who guesses wrong there locks that user and that address out of sign-in and SMTP AUTH for the rest of the 15-minute window, so a session thief can deny the owner access for a while; the lockout is the price of not letting a session be used to guess the password); dashboard users are managed by administrators only: disabling, demoting, resetting or deleting a user ends their sessions in the same storage write, a sign-in that was verified before such a change gets no session (the session insert checks that the user is unchanged), a password change ends the other sessions, the last enabled administrator cannot be removed (atomic check), generated passwords are shown once and never logged | `Mta.Host.Tests` (`SecurityTests`, `IngestTests`, `AuthThrottleSharedTests`, `ApiUsersTests`), `Mta.Integration.Tests` (`MultiReplicaTests`: two runtimes over one PostgreSQL) |
| **Secrets at rest** | Information disclosure | DKIM private keys, webhook secrets, TLS private keys, ACME account key and relay passwords are protected with ASP.NET Core Data Protection (one purpose string per kind); the key ring lives in the config store and is encrypted with a certificate (`Secrets:KeyProtection=Certificate`) or wrapped with a key held outside the database (`Kms`, AES-256-GCM, a mounted key file); a ring that does not match the configuration stops the start; `None` is allowed for development and logs a warning; backend switch bundles never contain clear-text secrets (separate bundle key ring, passphrase-protected PKCS#12) | `Mta.Host.Tests` (`SecretsTests`), `Mta.Storage.Portability.Tests` |
| **Storage** | Tampering, data loss | Integrity check at start and quarantine of a corrupt SQLite file, ordered and idempotent cross-file writes, crash-recovery tests including SIGKILL in every sync mode; per-tenant scoping on every query *(HTTP layer: see the API PR)* | `Mta.Storage.Sqlite.Tests`, conformance suites |
| **Dashboard and HTTP API** | XSS, CSRF, session theft | Strict CSP (`script-src 'self'`, no inline script or style, no `eval`), `nosniff`, `no-referrer`, frame denial, HSTS over HTTPS; HttpOnly + SameSite=Strict cookies and a CSRF header for cookie-authenticated writes; dashboard has about 8 direct dependencies, exact versions, lockfile, `ignore-scripts` | `dashboard` tests (CSP checker, lint rules), API tests *(in the API PR)* |

## Parser review checklist (used for every new parser)

1. Every length, count and nesting depth has an explicit limit and a test at the limit and above it.
2. Hostile input never throws out of the parser, never allocates proportionally to a claimed (not actual) size, and never loops without consuming input.
3. Text that comes from the network is sanitised before it reaches a log, a header, a DSN or a webhook payload (control characters, CR/LF).
4. Round trip and differential tests against a reference implementation exist where one is available.
5. The parser has a fuzz target in `fuzz/Mta.Fuzz.Targets` (with invariants, not only "does not throw"), seeds in `fuzz/corpus`, and runs in `Mta.Fuzz.Tests`; every crasher, hang or invariant violation found by a fuzzer is fixed, covered by a unit test, and kept as an input in `fuzz/regressions/<target>/`.

**1. In every `dotnet test`** (`tests/Mta.Fuzz.Tests`): the built-in seeds, the checked-in corpus (`fuzz/corpus`), every past finding (`fuzz/regressions`), every prefix of every seed, and a fixed number of seeded mutations per target (the mutator is deterministic, the seed is a constant). Nothing asserts elapsed time: a hang is caught by a 10 minute limit per test, unbounded allocation by a byte budget measured on the running thread, a crash or broken invariant by the exception. About ten seconds in total (26 s on the CI runner).

**2. Coverage-guided, scheduled** (`.github/workflows/fuzz.yml`, weekly and `workflow_dispatch`, one job on `ubuntu-latest`): the harness is published, the protocol assemblies and the SMTP client are instrumented with SharpFuzz (`SharpFuzz.CommandLine` 2.3.0, the same version as the `SharpFuzz` package) and each target runs under libFuzzer through `libfuzzer-dotnet` (release `v2025.05.02.0904`, SHA-256 verified) for `seconds_per_target` (default 200, so that 16 targets cost what 11 did at 300; decision 72's billing rule), starting from `fuzz/corpus` and `fuzz/regressions`, with a dictionary generated from the mutator tokens. Crash, timeout and out-of-memory inputs are uploaded as the `fuzz-findings` artifact (30 days), the grown corpus as `fuzz-corpus`, a summary table goes to the job summary, and the job fails when any target has a finding. The fuzzed process runs with a 2 GiB GC heap limit so runaway allocation is an `OutOfMemoryException`, not an OOM kill.

Reproduce a finding locally (no fuzzer needed): `dotnet run --project fuzz/Mta.Fuzz.Harness -c Release -- replay <target> <file>`. After the fix add a unit test next to the parser and copy the input to `fuzz/regressions/<target>/<what-it-was>`; the next `dotnet test` replays it. New seeds: add them to the target and run `... -- export-corpus fuzz/corpus` (a test fails when the checked-in corpus lacks a built-in seed). Longer local runs of the same mutator: `... -- mutate <target> <iterations> <seed>`.

**What the fuzzers found so far** (each fixed, with a unit test and a regression input):

| Target | Finding | Fix |
|---|---|---|

## Inbound mail (the port-25 receive path)

Design: [design.md section 11.12](design.md#11-inbound-mail); decisions 95, 96 and 103. What is enforced in code and pinned by tests (`tests/Mta.Host.Tests/Inbound`):

- **Open relay.** Three independent layers: the `Inbound` listener role accepts a recipient only for an inbound-enabled domain with a matching enabled route (everything else is `550 5.7.1` at `RCPT`); inbound sessions offer and accept no AUTH; and the only path from a received message to the outbound queue is a forward route that an authenticated tenant created, with targets fixed in the route. Regression tests: unknown domain, registered-but-not-enabled domain, domain with no route, disabled route, an external recipient after a valid one, an unauthenticated `MAIL FROM` of a local domain (accepted as an external sender, verified, never relayed), AUTH refused even on a TLS session.
- **Backscatter.** Nothing is accepted and bounced. Every refusal is a reply in the dialog; a message refused after DATA (DMARC reject, size) produces no message of any kind; SRS bounces are verified and dropped, never relayed.
- **Smuggling and injection.** Bare LF/CR and NUL in `DATA` and in `BDAT` chunks close the connection, the end-of-data scanner never accepts `\n.\r\n`, `\r.\r\n` or `\r\n.\n`, and plaintext behind `STARTTLS` is never executed; the same suites run on the new role. Hostile values never reach a header unescaped: the HELO name is validated by the parser and sanitized in `Received`, verdict fragments go through the Authentication-Results builder, reply texts built from message content are reduced to letters, digits, dots and hyphens.
- **Forged verdicts.** Every `Authentication-Results` that claims our authserv-id (or cannot be parsed) and every `X-EggMail-*` field except a validly signed hop marker is removed before ours is added; a header block too large for the parser to record in full is refused rather than trusted.
- **Anonymous senders and submission.** The port-25 listener has its own connection cap (`Inbound:MaxConnections`), its own share of the in-flight message memory (`Inbound:MaxInFlightBytes`) and a share of that per client network (`Inbound:MaxInFlightBytesPerRemote`), so a flood of anonymous senders cannot take the connections and memory submission needs (the difference to `Smtp:MaxConnections` and `Smtp:MaxInFlightBytes` stays available to it); the copies the receive path makes of a message are reserved from the same budget before they are made; the per-address connection cap counts an IPv6 client by its /64; a session is closed after `Inbound:MaxSessionDuration` (NOOP and empty BDAT chunks do not keep it alive); a message to a bounce address from any sender but the null sender is limited to 1 MiB, and a report is read from its first 256 KiB; the `bounce.<name>` lookups need a valid token and are budgeted per client (10 a second) and for the process (200); the memory a message takes while it is handled (about four times its size) is the sizing rule that the in-flight shares are checked against at start. The session age is checked between commands and while a `BDAT` sequence waits for its next chunk; a message being received by `DATA` is finished (at most `Smtp:MaxDataDuration`, 15 minutes).
- **Denial of service.** Per-domain and per-remote (IPv6 /64) message rates in separate bounded dictionaries (a flood from many addresses cannot reset a domain's counter), a recipient cap, a transaction byte budget checked at RCPT and again with the actual size, per-domain size limits under the operator's ceiling enforced while reading, bounded verification (total timeout, concurrency limit, per-/24 and /64 share, `451` at once instead of queueing, slot taken only after the body is in), at most 10 ARC sets and 3 From domains, per-domain and per-tenant stored-bytes limits.
- **Cross-tenant.** A transaction may name recipients of several tenants; each gets its own row and its own copy of the body, stored in one atomic write; the DMARC flag is per recipient domain; the `Received` header names a recipient only when there is exactly one.
- **Client address integrity.** SPF, the DNSBL and the per-remote limit use the connecting address; behind source NAT they are meaningless, which the operations guide explains and the server warns about once an hour. A mapped IPv6 address is normalized.
- **DNSBL.** Off by default; every query discloses connecting addresses to the list operator; `127.255.255.0/24` answers are errors, never hits; a lookup failure never blocks.

| **Loss and duplication** | `250` only after the commit; one atomic write for all recipients; at-least-once actions | `InboundCrashTests` (a stop with no flush while 6 senders are sending, a graceful restart, a database that drops every connection), `InboundSwitchTests` (SQLite to PostgreSQL and back with every column and the hash of every body compared; a switch in the middle of traffic) |
| **Stale configuration** | A tag per domain; a cache that cannot be refreshed for 5 minutes answers `451`, never "unknown domain" | `InboundConfigurationChangeTests` |

**Spam and abuse considerations.** The server is an MX for customer domains, so it is sent spam, and what the tests prove is that it cannot be *used* (relay, backscatter, forwarding as a reflector) and that it cannot be *overwhelmed* by one sender or one tenant. They do not prove that it keeps spam out: there is no content filter, no greylisting and no reputation service built in. The first defences are the recorded SPF, DKIM, DMARC and ARC verdicts and the per-domain DMARC action (`flag` or `reject`), the optional blocklist (off by default; each query tells the list operator which addresses connect), and the rate limits. **Forwarding multiplies abuse into outbound reputation**: a tenant that forwards spam to a mailbox provider spends the reputation of its sending domain and of the server's addresses; the sending caps, warm-up, suppression list, SRS and ARC limit and attribute that, and suspending the tenant stops it (see [operations.md](operations.md#inbound-mail), "Abuse handling"). Operators publish an abuse contact (design section 10): `postmaster` and `abuse` at the **shared bounce domain** are accepted and dropped, so the contact people write to must be an ordinary mailbox on another domain.

## Inbound route actions

Received mail is attacker-controlled input that the server hands to customer systems. The route actions ([components/delivery.md](components/delivery.md#inbound-route-actions-mtahostinbound), design section 11.7):

* **SSRF.** An inbound webhook goes through the same `WebhookTransport` as every event: the address actually connected to is validated (public ranges only, DNS rebinding cannot swap it), per-tenant allowlists apply, no redirects, no proxy, no cookies, no trace headers. A test posts through the real handler with a name that resolves to loopback and expects `webhook_ssrf_blocked`.
* **Cross-tenant.** The route names an endpoint; the runner re-checks that the endpoint belongs to the message's tenant before sending and reads the route by tenant. Another tenant's receiver never gets a message even if a write path bug let the route through.
* **Injection.** The JSON payload is written by a JSON writer (everything escaped, unpaired surrogates replaced, so a hostile message can neither break the document nor make it unbuildable). The `raw_mime` envelope and verdicts travel in `EggMail-*` headers as percent-encoded ASCII; a CR, LF or non-ASCII character in an address cannot add a header. Nothing from a message is placed in a URL, a header name or a log line (`actionLastError` holds codes only). Receivers must treat every field as attacker-controlled (documented in the API guide).
* **Secrets and leaks.** The webhook secret is unprotected only to sign; errors recorded for the tenant carry no URL, address or response body (the outbox attempt log keeps a snippet for outbound events; inbound deliberately does not, so a receiver cannot be used to read internal services through the failure text). Attachments are listed by path, never inlined and never with a pre-signed URL: a leaked payload does not leak the attachment.
* **Amplification and DoS.** One received message produces at most one webhook attempt stream (eight attempts over 27 h) per matching route (the first enabled route only); payloads are bounded (`Inbound:Webhook:MaxTextBytes`, 256 KiB of headers, 200 listed attachments, `MaxRawMessageBytes` for the raw format); the pool is bounded per replica and per tenant. **Tenant starvation** is closed in the claim itself: at most the per-tenant share of rows per call, and none for a tenant that already has attempts in flight on the replica, so a large backlog for a dead receiver does not delay other tenants; the per-domain rate limits and stored-bytes limits bound how fast a backlog can grow.
* **Failure notices.** A failed action is visible to the tenant (state, `inbound.action.failed`), never to the sender of the received mail.

## Inbound forwarding

* **Laundering a spoof.** A forward whose From is in the route's own organizational domain would carry an aligned SRS envelope and an aligned signature of the tenant's domain; a spoof of `ceo@tenant.com` would pass DMARC at the final receiver. The forwarder refuses such a message unless it passed DMARC when it was received (`unauthenticated_local_sender`). Messages from other domains get the unaligned route-domain signature only, which proves "this tenant's server handled it" and nothing about the From domain.
* **A From that names no clear identity is never forwarded** (decision 114). The check above reads the From leniently, so `ceo@tenant.com <x@evil.test>` looked like foreign mail of evil.test and was forwarded, while a reader of the copy (a mail client, Python's `email.policy`) sees the tenant's own address. The receive path already judges such a field unusable (design section 11.5) and stores `dmarc=permerror` for it; the forwarder refuses every message with that stored verdict (`unusable_from`, counted in `mta_inbound_forward_refused_total{reason}`), whatever domain it names, a message without a From included. Tests: `InboundForwarderTests.A_from_the_receive_path_judged_unusable_is_never_forwarded...`, `InboundForwardSenderCheckTests` (through the real receive path, SQLite and PostgreSQL).
* **Signing.** The engine signs a forward with the key of `SendingDomain` (the route's domain) and never with the From domain; the original signatures are untouched (headers are added on top only); a regression test compares the bytes. No key: unsigned, never signed with anything else.
* **Loops.** The target check at run time (route's domain, any inbound-enabled domain, the bounce domain), the signed hop marker (3 hops; forged markers count as zero; one marker only), the cap of 10 targets and the tenant's sending caps. The marker is dropped by a body-changing hop, which the `Received` limit of the receive path then bounds.
* **SRS.** An SRS address is accepted only from the null sender with a valid hash and age, then dropped (no relay, no backscatter, no open relay by forging); the hash is 40 bits and comparisons are constant time over every key of the ring; the local part never exceeds 64 octets whatever the original address.
* **A backlog of forwards is capped.** The copy of a forwarded message leaves the inbound store when it is queued, so the inbound quotas (stored bytes, rates) no longer see it, and the shared outbound queue keeps it for `Queue:MaxLifetime` when delivery stalls. Without a limit, anyone who can send mail to the domain could fill the queue at the inbound rate. `Inbound:Forward:MaxQueuedMessagesPerTenant` (5000), `MaxQueuedBytesPerTenant` (1 GiB) and `MaxQueuedMessagesPerDomain` (1000) are counted before every copy is queued; over a cap the forward waits on its ladder as `forward_backlog_full` and the message stays in the inbound store under its quotas. Tests: `InboundForwarderTests`, `InboundConformance` (the count on every backend).
* **The idempotency key cannot be squatted.** The forward of an inbound message is queued under the key `inbound:<id>` (30 days). A caller of the public API could have registered that key first (any 1 to 255 printable characters were accepted) and made the forward complete `done` with its body freed and nothing sent. The API now refuses keys that start with `inbound:` or `eggmail-`, and a forward whose key belongs to a message that is not a forward of this route fails with `forward_key_conflict` and keeps its body. Tests: `ApiSendingTests`, `InboundForwarderTests`.
* **Forwards share the tenant's sending counters.** A forward is outbound mail of the tenant: it counts against the tenant's and the domain's hourly and daily caps and warm-up, so a flood of received mail that is forwarded can use up what the tenant needs for its own sending, and a copy that waits out the whole `Queue:MaxLifetime` expires with no notice to anyone (a forward never produces a bounce). The backlog caps above bound how much can wait; a separate counter scope for forwards is a follow-up ([open-questions.md](open-questions.md)).
* **A spoofed From with a passing SRS envelope is inherent to forwarding.** Mail from a foreign domain that failed that domain's DMARC at receipt is still forwarded: the copy carries our SRS envelope and the original signatures, and the final receiver's DMARC decision on the foreign domain is what protects the recipient. Only the route's own organizational domain is refused, because there our envelope and signature would make the spoof pass. Owner-level options, not built: confirming each forward target with its owner before the first copy (as Cloudflare Email Routing does), and forwarding only mail that did not hard-fail DMARC ([open-questions.md](open-questions.md)).
* **ARC on a hostile chain.** The chain a forward is sealed over is the sender's. Validation is bounded by the validator's own limits (10 sets, 25 key lookups) and by 5 seconds (`ArcValidationTimeout`); a chain that is not validated in time is sealed over as `cv=fail`, so a runner slot is never held for longer. A newest seal that already says `cv=fail`, or a chain at the maximum, is not sealed over.
* **Targets come from the route only**, never from the message (`Reply-To`, `Bcc`, `Resent-*` are ignored; a test pins it).

## Inbound mail in the dashboard

Received mail is hostile content. The dashboard shows every field of a message (subject, addresses, header values, the text part) as text nodes of a framework that escapes them; the HTML part only in the sandboxed frame used for outbound mail (empty `sandbox`, `default-src 'none'` in its own CSP, remote images and styles blocked, so a tracking pixel does not report that the mail was read); the raw message and attachments are never opened, only saved (a Blob and a `download` attribute with a file name reduced to letters, digits and `. _ - ( )`). The e2e spec for hostile mail checks that nothing of a message becomes an element of the page, that no script of it runs, and that no CSP violation is reported. Deleting by filter needs a filter and the typed word; there is no button that empties a tenant.

## Operational guidance

- Run the container as the non-root user it is built with, read-only root file system, drop all capabilities, publish only the ports you enable (`docs/design.md` section 7).
- Use `Secrets:KeyProtection=Certificate` (a certificate that is not stored in the database) or `Kms` (a wrapping key from a mounted secret; see [operations.md](operations.md)). Keep the database backups and the key-protection certificate separate.
- Put the dashboard/API behind TLS (the built-in HTTPS listener serves the certificate from the database or from a file override).
- Review webhook allow-lists: internal addresses are denied unless explicitly allowed per tenant.

## Known gaps

- **No external audit.** Recommended before production-critical use ([plan.md](plan.md)).
- Coverage-guided fuzzing runs weekly and on demand ([Fuzzing](#fuzzing)), not on every pull request, and only for minutes per target; a clean run is evidence, not proof. A long campaign (hours per target) has not been done.
- Container hardening, Trivy/Grype scans, `testssl.sh` and Internet.nl checks, and the SMTP attack suites from the design (smtpsmug, EAST, slowloris tooling) have not been run against a deployed instance.
- ACME has not been verified against a real certificate authority.
- With several replicas, a hard sending cap can be overshot by what the other replicas send in one 10 s flush interval, and the SMTP per-address connection limit is per replica ([decision 82](decisions.md)). The per-destination limits and the failed-login budget are shared. If the database is unreachable the failed-login budget falls back to each process's own count until it is back.
