# Mta.Dkim: DKIM signing and verification

`src/Mta.Dkim` implements DKIM ([RFC 6376](https://www.rfc-editor.org/rfc/rfc6376)) with the algorithm and key rules of [RFC 8301](https://www.rfc-editor.org/rfc/rfc8301): `rsa-sha256` only, RSA keys of 1024 bits or more (2048 recommended and generated by default). It is part of the hand-written, BCL-only stack (decision 4): no package references, crypto is `System.Security.Cryptography` only. It references `Mta.Core` (`IClock`) and `Mta.Dns` (`IDnsResolver`); it does not use `Mta.Mime`, because DKIM needs the exact raw header bytes and splits headers itself (internally, over raw bytes).

Scope cuts (see [decisions.md](../decisions.md) item 4 and [plan.md](../plan.md)): Ed25519 (RFC 8463) is not implemented; a signature using it is reported as `neutral` with the reason `unsupported algorithm ed25519-sha256`. `rsa-sha1` is never accepted.

## Public API

| Type | Purpose |
|---|---|
| `DkimSigner`, `DkimSignerOptions` | Create `DKIM-Signature` headers for a raw message |
| `DkimVerifier`, `DkimVerifierOptions` | Verify every `DKIM-Signature` of a raw message, per signature |
| `DkimVerificationResult`, `DkimStatus`, `DkimFailure` | Result model (status maps one to one onto RFC 8601 `dkim=` values) |
| `DkimKeyRecord` | Parsed DNS key record (`v= k= p= h= s= t= n=`) |
| `DkimKeyTools` | Key generation, PEM/DER import and export, TXT formatting and splitting, selector suggestion |
| `DkimAuthenticationResults` | `dkim=pass header.d=... header.s=... header.b=...` fragments for RFC 8601 headers |
| `DkimCanonicalization`, `DkimException` | Enum (`Simple`, `Relaxed`) and the exception for invalid signer configuration or unsignable input |

### Signing

```csharp
using var key = DkimKeyTools.GenerateRsa2048();               // or DkimKeyTools.LoadPrivateKeyPem(pem)
var signer = new DkimSigner(new DkimSignerOptions
{
    Domain = "example.com",
    Selector = DkimKeyTools.SuggestSelector(DateTimeOffset.UtcNow),   // egg202610
}, key);

string header = signer.Sign(rawMessage);    // "DKIM-Signature: v=1; ...\r\n", folded, CRLF terminated
// prepend `header` to the message; for several domains use one signer per domain and prepend each header
```

- Overloads: `string Sign(ReadOnlySpan<byte>)`, `ReadOnlyMemory<byte> SignToBytes(ReadOnlySpan<byte>)`, and `int Sign(ReadOnlySpan<byte>, IBufferWriter<byte>)` (no intermediate string or array). `DkimSigner.FromPem` / `FromDer` create a signer that owns its key (dispose it).
- Defaults: `rsa-sha256`, `relaxed/relaxed`, `t=` from `IClock`, never `l=`, optional `x=` (`SignatureLifetime`) and `i=` (`Identity`, must be inside `d=`).
- Signed headers: From, To, Cc, Subject, Date, Message-ID, Reply-To, In-Reply-To, References, MIME-Version, Content-Type, Content-Transfer-Encoding and the `List-*` family (`DkimSignerOptions.DefaultSignedHeaders`). From is always signed. Repeated headers are all signed, bottom-up (RFC 6376 section 5.4.2).
- **Oversigning** (default on, RFC 6376 section 5.4 and 8.15): every listed header name appears in `h=` once more than the number of instances in the message. Adding another `From`, `Subject`, `Cc`, `Reply-To`, `List-Unsubscribe`... after signing then breaks the signature. Consequence: the message must already carry every header it is meant to have (Date, Message-ID) when it is signed; a later hop that adds a missing `Date` or `Message-ID` would invalidate the signature.
- The input must be a complete message with CRLF line endings containing a From header, otherwise `DkimException`.
- `DkimSigner` is safe for concurrent use. Its RSA key is used from several threads at once, so create the key (or load it) before sharing the signer; the constructor performs one test signature, which also forces lazily generated keys into existence.

### Verification

```csharp
var verifier = new DkimVerifier(dnsResolver, new DkimVerifierOptions());
IReadOnlyList<DkimVerificationResult> results = await verifier.VerifyAsync(rawMessage, ct);
string fragment = DkimAuthenticationResults.Format(results[0]);   // dkim=pass (2048-bit key) header.d=... header.s=... header.b=Xb4F5k6S
```

- One result per `DKIM-Signature` header, in message order; an unsigned message yields a single `DkimStatus.None` result. Signatures are independent: one bad signature does not affect another.
- Status mapping: `Pass`; `Fail` (body hash mismatch, signature mismatch, expired, revoked key, key below the minimum size, `rsa-sha1`, `l=` rejected by policy, `t=s` identity violation); `Neutral` (syntax errors, unsupported version/algorithm/query method, From not signed, `i=` outside `d=`, too many headers, over the signature limit); `TempError` (any DNS failure: SERVFAIL, refused, timeout, `DnsException`, any exception from the resolver); `PermError` (NXDOMAIN or no key record, malformed key record, key type mismatch, key does not permit sha256/email, key above the maximum size).
- `DkimFailure` gives the machine readable reason (for example `BodyHashMismatch` vs `SignatureMismatch`); `Reason` is a short safe string for logs and `reason=` properties.
- Also reported: `Domain`, `Selector`, `Identity`, `Algorithm`, `KeyBits`, `WeakKey` (accepted but below 2048 bits), `Testing` (key record `t=y`; the result is still the real cryptographic result), `HeaderBPrefix` (first 8 characters of `b=`), `BodyLengthLimited` / `BodyPartiallySigned` (`l=`), canonicalization, `SignedAt`, `ExpiresAt`.
- Key lookup: TXT at `<s>._domainkey.<d>` (the resolver follows CNAMEs and concatenates character-strings). If several TXT records exist the first one that parses as a key record is used. The parsed key is cached for the duration of one message only; response caching is the resolver's job.
- `l=` is **verified** (the body hash is computed over the first `l` canonical bytes) but never emitted. A signature with `l=` lets anyone append unsigned content, so it is flagged; set `RejectBodyLengthLimit` to fail such signatures. An `l=` larger than the canonical body fails.
- `x=` expiry honours `ClockSkew` (default 5 minutes). A `t=` in the future is not rejected.
- Cancellation: only the caller's `CancellationToken` surfaces as `OperationCanceledException`; everything else (including a resolver that throws) becomes a result. A last-resort handler turns an unexpected internal exception into `TempError` with `DkimFailure.InternalError`; the tests assert this never happens for fuzzed input.

### Key tooling and rotation

`DkimKeyTools`: `GenerateRsa2048`, `ExportPrivateKeyPem` (PKCS#8), `ExportPublicKeyBase64` (SubjectPublicKeyInfo), `FormatDnsTxtValue` (`v=DKIM1; k=rsa; p=...`), `SplitTxtValue` / `FormatDnsTxtQuoted` (character-strings of at most 255 characters for DNS panels, a 2048-bit key needs two), `JoinQuotedStrings` / `TryParseDnsTxtValue` (parse a panel or `dig` rendering back), `GetDnsName`, `SuggestSelector` (`egg` + `yyyyMM` in UTC), `LoadPrivateKeyPem` / `LoadPrivateKeyDer` (PKCS#8 or PKCS#1).

Rotation procedure (documentation only, the scheduler/UI belongs to domain verification, [design.md section 8](../design.md#8-domain-verification)):

1. Generate a new key and publish it under a new selector N+1; wait until it resolves.
2. Switch signing to N+1.
3. Keep the record for N published for at least 7 days (mail signed with N may still be queued, retried or being verified), then remove it.
4. Never reuse a selector name.

## Limits and hostile input

| Limit | Default | Where |
|---|---|---|
| Signatures verified per message | 5 (the rest are reported `neutral`, no DNS query) | `DkimVerifierOptions.MaxSignaturesVerified` |
| Header fields per message | 1024 (verifier: `neutral`; signer: `DkimException`) | `DkimVerifierOptions.MaxHeaderCount` |
| DKIM-Signature header length | 16384 bytes | `MaxSignatureHeaderLength` |
| Tags per signature / names in `h=` / decoded `b=` | 32 / 512 / 512 bytes | `DkimSignatureHeader` constants |
| Key record text / decoded `p=` | 8192 characters / 1024 bytes (checked before any key import) | `DkimKeyRecord` constants |
| RSA key size accepted | 1024 to 4096 bits; below 2048 flagged weak | `MinimumKeyBits`, `WeakKeyBelowBits`, `MaximumKeyBits` |
| Clock skew for `x=` | 5 minutes | `ClockSkew` |
| Single-token tags (`d s v a c q l t x`) | no embedded whitespace | parser |

Parsers (`TagListParser`, `DkimKeyRecord`, `DkimSignatureHeader`, `HeaderTable`) never throw on any input, reject duplicate tags and control or non-ASCII bytes, and are fuzzed with deterministic seeds. DNS names are built only from validated labels (`[A-Za-z0-9_-]`, at most 63 characters per label, 253 in total).

## Security notes

- **Signature validity is not authorization.** A passing signature proves that `d=` signed the covered content. Whether `d=` matches the From domain is DMARC alignment (`Mta.Auth`), not this component.
- **`rsa-sha1` and keys below 1024 bits never validate** (RFC 8301). Keys of 1024 to 2047 bits validate but are flagged; policy code can downgrade on `WeakKey`.
- **Oversigning** protects against header-addition replay (an attacker prepending a second From/Subject to a validly signed message). Without it the plain signature still verifies. Both behaviours are covered by tests, including against MimeKit.
- **`l=`** is accepted for verification only; see above. EggMail never emits it.
- **Testing mode** (`t=y`) is reported, not acted on, as RFC 6376 section 6.1.2 says verifiers should not treat such mail differently.
- **Key material**: private keys are never logged; `DkimKeyTools.ExportPrivateKeyPem` returns an unencrypted PKCS#8 PEM and the caller must protect it (the host stores DKIM keys wrapped by Data Protection, [design.md section 4.6](../design.md#46-switching-backends-manual-and-symmetric)).
- **Line endings**: only CRLF terminates lines. A message with bare LF line ends is hashed as written; normalize before signing (the SMTP server hands over CRLF data).
- **Allocation**: signing a 50 KB message allocates well under 1 KB besides the returned header (measured 64 bytes; the test budget is 1024 bytes, `PerformanceTests`). Headers and body are canonicalized and hashed incrementally over spans with pooled buffers and a per-thread cached `IncrementalHash`. Verification allocates the result objects, the parsed signature and one key per distinct selector.

## Measured (indicative)

BenchmarkDotNet `--job short`, Apple M4, .NET 10.0.12, RSA-2048, relaxed/relaxed, single thread (a one-off local run, not a published benchmark):

| Operation | 1 KB message | 50 KB message | Allocated |
|---|---|---|---|
| `Sign` | about 0.97 ms | about 0.97 ms | 64 B |
| `Verify` (key from a static resolver) | about 0.06 to 0.1 ms | about 0.26 ms | about 7 KB |
| Relaxed body canonicalization + SHA-256 | 3.5 us | 165 us | 0 |
| Simple body canonicalization + SHA-256 | 0.7 us | 28 us | 0 |

Signing time is the RSA private key operation; everything EggMail adds around it is a few microseconds and allocation free.

## Tests

`tests/Mta.Dkim.Tests` (xUnit, MimeKit 4.18.1 as an oracle only):

- Canonicalization: RFC 6376 section 3.4.5 example, folded headers, trailing whitespace, empty body, missing final CRLF, multiple blank lines, `l=` truncation, 3000+3000 randomized cases against an independent naive string/regex implementation, body hash known answers (`bh=2jUSOH9NhtVGCQWNr9BrIAPreKQjO6Sn7XIkfJVOzv8=` from RFC 6376 / RFC 8463 sample message, empty-body hashes for both algorithms).
- Signer: header shape and folding, oversigning on and off, repeated instances, options validation, PEM/DER loading, determinism, concurrency.
- Verifier: all four canonicalization pairs, every tampering class (body, signed header, unsigned header, signature, `bh=`, key, selector, expiry, revoked/testing/weak/oversized/malformed keys, DNS failures), header-instance selection, multiple and nested signatures, limits, truncated and randomly mutated messages.
- Differential against MimeKit in both directions for 11 message shapes x 4 canonicalization pairs, plus 100 random messages signed and verified by both.
- Performance and allocation guards and the BenchmarkDotNet class `bench/Mta.Benchmarks/Dkim/DkimBenchmarks.cs` (sign, verify and canonicalize for 1 KB and 50 KB messages).

## Known gaps

- Ed25519 (RFC 8463) is out of scope; the RFC 8463 sample is used only for its RSA-independent body hash value. Complete RFC 6376 / 8463 signed sample messages could not be fetched offline, so end-to-end vectors come from MimeKit and from the in-test reference implementation instead.
- The message must be one contiguous buffer; chunked or streaming input is not supported.
- Internationalized domain names must be given as A-labels; `i=` UTF-8 local parts are decoded but not otherwise validated (RFC 8616 is not implemented).
- Only the first parseable TXT record is used; DNSSEC status (`AuthenticatedData`) is not used.
- No ARC, no DKIM-delegated key reporting (`r=`, `ra=`), no `z=` handling (ignored).
- On macOS the RSA implementation generates keys lazily on first use, which races when a freshly created key is first used from several threads at once; `DkimSigner` avoids this by test-signing in its constructor. Tests warm their shared keys for the same reason.
