# ACME and the certificate store (`Mta.Host/Tls`)

How EggMail gets and serves its own TLS certificates (SMTP STARTTLS/implicit TLS and the dashboard/API HTTPS listener). Outbound TLS policy (MTA-STS, DANE, TLS-RPT) is a different component: [tls.md](tls.md). Decisions: K, 19 (superseded in part), 81 and 87 in [decisions.md](../decisions.md); design: [design.md §7.3](../design.md).

## Parts

| Type | Job |
|---|---|
| `AcmeRenewalService` | Decides when a certificate is due, takes the renewal lease, runs one order through an `IAcmeOrderRunner`, stores the result, records failures with back-off. `CheckOnceAsync` (scheduled, hourly in `RunAsync`), `RequestAsync` (the dashboard's "request a certificate": ignores the schedule and the back-off). |
| `CertesOrderRunner` (`IAcmeOrderRunner`) | One order with Certes 4.1: account (with external account binding when configured), new order, **HTTP-01 or DNS-01** challenges, validation, finalize, download. The constructor takes an optional `HttpMessageHandler` (tests trust a private CA with it; deployments behind an egress proxy can use it). |
| `AcmeHttpChallengeListener` | The built-in HTTP-01 responder: a tiny HTTP/1.1 server on its own socket (not Kestrel, not the dashboard) that answers `/.well-known/acme-challenge/<token>` and refuses everything else. Binds `Acme:Http01BindAddress`:`Acme:Http01ListenPort`, retries a failed bind every minute, runs on every replica (started by `CertificateService`). |
| `Http01Challenges` (`IHttpChallengePublisher`, `IHttpChallengeResponder`) | The tokens of the orders in flight: in memory in the process that ordered, and in the config store (`challenge_state_json` of the certificate's renewal row) for every other replica; the listener's source of answers, and the place that knows whether the listener could bind. |
| `AcmeNames` | Normalises names for the CA (lower case, no trailing dot, `xn--` labels) and rejects IP addresses and single labels. |
| `IDnsChallengeProvider` | Creates and deletes `_acme-challenge.<name>` TXT records. Must hold several values at one name (wildcard plus base name). `CloudflareDnsChallengeProvider` is the only production implementation. |
| `DatabaseCertificateProvider` | Holds the certificates of the store in memory, polls the store version (`Tls:PollInterval`) and swaps the set in atomically; first-run self-signed certificate; optional file override. Serves SMTP (`IServerCertificateProvider`) and HTTPS. |
| `HttpsCertificateSelection.UseCertificateStore` | Configures the Kestrel HTTPS listener from the provider (see below). |
| `CertificateMaterial` | Record to `X509Certificate2` (private key through Data Protection) and the self-signed bootstrap certificate. |

## Challenge types: HTTP-01 and DNS-01 (decision 87)

Decision 19 said DNS-01 only; decision 87 supersedes that, because the owner's target is "set the host name and an email and get a Let's Encrypt certificate", which has to work without DNS access. `Acme:Challenge` is `Auto` (default), `Http01` or `Dns01`:

| Setting | Challenge | Needs |
|---|---|---|
| `Auto`, no Cloudflare token | HTTP-01 | Inbound port 80 reaching the built-in listener; no wildcard names |
| `Auto`, token configured | DNS-01 | The Cloudflare token; no inbound port; wildcards work |
| `Http01` | HTTP-01 | As above; a wildcard name is a configuration error |
| `Dns01` | DNS-01 | The token (configuration error without) |

One type per order. `AcmeRenewalService.ChooseChallenge` makes the choice from what the service was given (a DNS provider or not), so a wildcard requested later through the API without DNS-01 available is a recorded failure ("wildcard ... only DNS-01 can prove ... Acme:CloudflareApiToken") and the CA is not asked; the runner checks the CA's authorization (`wildcard: true`) as well. TLS-ALPN-01 is not implemented.

### The HTTP-01 flow

1. The service checks `Http01Challenges.WaitUntilReadyAsync`: the listener's first bind attempt has happened (up to 30 s after the start) and succeeded. If it could not bind, **no order is started**: the CA is never asked (a validation that fails there is rate limited), the renewal row becomes `failed` with the bind message, the next attempt is five minutes away and the renewal loop wakes then. The message says what to do (port in use: free it, or `Acme:Http01ListenPort` plus forwarding, or DNS-01; not allowed: root/`CAP_NET_BIND_SERVICE`, the container sysctl, or a high port published as 80).
2. For each pending authorization the runner takes the `http-01` challenge, computes the key authorization with the account key, and `PublishAsync` stores it (memory and store). Authorizations the CA already considers valid are skipped as with DNS-01. There is no propagation delay.
3. The runner asks the CA to validate. The CA connects to port 80 of the name (IPv6 first when there is an AAAA record) and the listener answers `200` with the key authorization as the body (`application/octet-stream`).
4. After validation, failure or cancellation every token is removed (`RemoveAsync`), in `finally`. A CA explanation of an invalid authorization is part of the error, with a hint about port 80 and `Acme:Http01ListenPort`.

### The listener

It reads at most 8 KiB of request head (more: `431`) that must arrive within 2 seconds (a slower client is dropped without an answer), a connection lives at most 5 seconds in all, and it serves at most 128 connections at once and 8 per client address (more are closed at once; IPv4-mapped addresses count as IPv4). A lookup that fails unexpectedly is a `503` (the CA retries) and a line in the log; the listener itself never stops the host: an unforeseen error in the bind/serve loop is logged, marks the listener unavailable and is retried, and a socket that dies after a successful bind does the same (orders wait instead of asking the CA to connect to a closed port). Logged request targets are printable ASCII only. Only `GET` and `HEAD` are accepted (`405` with `Allow` otherwise; malformed request line or HTTP version: `400`), only the exact path prefix with a token of plausible shape (16 to 256 characters of base64url; anything else, including a query string, a trailing slash, percent escapes, `..` and an absolute-form target, is `404`) and only a token an order currently waits for (otherwise `404`). Responses carry `Connection: close`, `Cache-Control: no-store` and an explicit `Content-Length`; the request body is never read as such (what the peer still sends is drained, bounded, so the answer is not lost to a connection reset). No redirects, no static files, no other virtual path: opening port 80 exposes nothing but the token. Logging: an answered challenge is an Information line, a refused request only Debug (port 80 is scanned all day).

The listener binds `::` with dual mode (every IPv4 and IPv6 address; `0.0.0.0` where the host has no IPv6), `Acme:Http01BindAddress` overrides it. It is independent of the dashboard's HTTP port: configuration validation refuses `Acme:Http01ListenPort` equal to `Dashboard:HttpPort`, `Dashboard:HttpsPort` (while enabled) or an enabled SMTP listener's port.

### Several replicas

Only the lease holder orders, but the CA reaches whichever replica the load balancer picks. Every replica runs the listener, and `Http01Challenges.PublishAsync` writes the token into the certificate's renewal row (`SetAcmeRenewalChallengeStateAsync` updates that column only, so the status, back-off and advice another replica wrote are not overwritten). A replica that does not know a token reads all tokens from the store as one snapshot, by one request at a time, at most every 50 ms (`RefreshInterval`; the snapshot answers only while it is that fresh, and a failed read is logged once a minute). `PublishAsync` returns two intervals after the write, so a replica that read the store just before cannot answer 404 to the CA's request for a token published a moment ago: a flood of requests with made-up tokens costs one small read per interval, not one per request, and tokens of implausible shape never reach the store. A token stays valid for two hours after it was published at the longest (a crashed replica cannot leave an answer behind forever). The replica that ordered answers from its own memory first. Route port 80 of the name to all replicas, or to any one of them.

### External account binding

`Acme:EabKeyId` with `Acme:EabHmacKey` or `Acme:EabHmacKeyFile` (a base64url key, as ZeroSSL and Pebble give it) is passed to Certes' `NewAccount` (HS256) when the account is registered, and only then: once the account is stored for the directory it is not needed. A directory whose `meta.externalAccountRequired` is true and has no binding configured fails the order with a message that names the settings, before anything is sent. Key id and key must be configured together (configuration validation).

## Flow of one order

1. Lease `acme-renew:<certificate name>` (20 minutes; works on both backends). Another replica holding it makes this replica skip the order.
2. Renewal row set to `ordering`.
3. Account: the stored account for the directory in use (`Acme:Directory` resolved, else `Acme:DirectoryUrl`) is used (its key is unprotected with purpose `AcmeAccountKey`). Without one, the runner registers a new account and the service **stores it immediately** (before the order can fail), Data Protection protected.
4. New order (for the names as the CA wants them: `AcmeNames`). An authorization the CA hands back already valid (RFC 8555 lets servers reuse valid authorizations of an account; Let's Encrypt and Pebble do) is skipped: no TXT record, no challenge request (posting to a valid challenge is refused). For each pending authorization one challenge answer: with DNS-01 one TXT record (a wildcard authorization is for the base name, so `*.example.com` and `example.com` put two values at `_acme-challenge.example.com`), `Acme:PropagationDelay`, validation requests, polling of the authorizations (200 ms growing to 3 s, about two minutes at most; the CA's explanation of an invalid authorization is part of the error), finalize with a fresh ES256 key, download of the chain. TXT records are removed in every case.
5. The certificate row is **replaced** (same name, same id, new version) so the poller of every replica sees one change and no old certificate stays active next to the new one. The chain is stored as sent by the CA (leaf plus intermediates), the private key as PKCS#8 protected with Data Protection.
6. Renewal row `issued`, failures 0.

Renewal is due when the CA's advice says so (ARI, next section), when a third of the lifetime is left (`Acme:RenewAtRemainingFraction`) if there is no advice, or when the configured names changed. A failed attempt of any kind (the CA refusing, unreachable or too slow; the DNS provider failing; an unbindable HTTP-01 port; an unreadable chain) is recorded in the renewal row (`failed`, failure count, last error, next attempt) and backed off 10, 20, 40 minutes, … up to 6 hours (five minutes when the CA was not asked because the port could not be bound); it is never thrown, so the renewal loop survives, and the loop wakes at the next attempt time (never later than `Acme:CheckInterval`). The old certificate, or the first-run self-signed one, keeps being served.

When the CA rejects the anti-replay nonce (`badNonce`; they expire and are per front end), the order is repeated up to four times in total, keeping an account that an earlier attempt registered.

## Renewal timing: ACME Renewal Information (ARI, RFC 9773)

Design §7.3 says "renew using ARI". `Acme:UseRenewalInfo` (default true) turns it on; `CertesOrderRunner.GetRenewalInfoAsync` asks the CA, `AcmeRenewalSchedule` (pure rules) decides, `AcmeRenewalService` persists.

* **Asking.** When the CA's directory has `renewalInfo`, the service GETs `<renewalInfo>/<certID>` where certID is `base64url(Authority Key Identifier)` `.` `base64url(serial)` of the certificate in use (Certes builds it; a stub-CA test pins the format). No account is needed. A directory without `renewalInfo` is looked at again after a day (the lifetime rule applies). Answers are limited to 1 MiB, the explanation URL must be an https URL of at most 2 KB, errors are kept to 1 KB.
* **Window.** The answer is a suggested window; times in any UTC offset are read as instants. The service picks **one random time inside it** the first time it sees that window and keeps it while the CA repeats (about) the same window, that is both ends within five minutes (a CA that computes the window from the current time would otherwise drift to the end of it at every poll). A different window picks again. A window or pick that has passed (what a CA answers for a revoked certificate or after an incident) means renew at the next check.
* **Due.** The chosen time is due when it falls before the next check (`now + Acme:CheckInterval`, RFC 9773 section 4.2 step 5). **Minimum age** (DESIGN-DECIDED): ARI alone never renews a certificate younger than the larger of one day and a twentieth of its lifetime (4.5 days for 90 days), so a CA that keeps answering "renew now" cannot cause an order at every check and hit the duplicate-certificate rate limit. The price is that a revoked certificate is replaced up to 4.5 days late, which the CA's own revocation already makes the client's problem.
* **Polling.** `Retry-After` is honoured within one minute and one day (no header: 6 hours); a stored wait further away than a day (clock stepped back, damaged value) is ignored. The CA is therefore asked about once per `Retry-After`, at least daily, and never faster than the hourly renewal check. Certes exposes `Retry-After` of successful answers only, so the one of a 429 or 503 is not honoured; the error back-off applies instead.
* **Failure** (RFC 9773 section 4.3.3). After a server error (5xx) or a network failure the CA is asked again after 5 minutes, doubling per consecutive failure up to 6 hours; after any other error (a 404 for an unknown certificate, an unparsable answer, a window that ends before it starts) after 6 hours. Meanwhile the lifetime rule decides, or the earlier window of the same certificate if there is one. The count of failures is part of the stored advice. The CA being unable to answer never blocks a renewal.
* **Safety limit** (DESIGN-DECIDED): whatever the advice says, a certificate with a sixth of its lifetime or less left is renewed (never later than `Acme:RenewAtRemainingFraction` would, if that is smaller), so a wrong or stale window cannot let it expire. The names-changed rule applies first and needs no advice.
* **`replaces`.** An order that renews a certificate sharing a name with it carries the certificate id in `replaces` (RFC 9773 section 5) when the CA advertises ARI, so it can treat the order as a renewal (rate limits) and mark the old certificate replaced. If the CA refuses the link itself (`alreadyReplaced`, `malformed`, `conflict`, `unauthorized` for a certificate of another account, 404) the order is repeated without it, with a Debug log line. Other errors (rate limits, server errors, bad nonce handling) are not retried that way: asking again at once makes them worse and the plain order would meet the same.
* **State.** Stored as JSON in the existing `acme_renewal.ari_json` column of the certificate's row (window, chosen time, last/next check, explanation URL, error, failure count, directory-has-no-renewal-info flag; keyed by the certificate's thumbprint, so advice for an older certificate is ignored). No schema change; it moves with the switch bundle with the rest of the row. It is written with `IConfigStore.SetAcmeRenewalAdviceAsync`, which updates that column only, so a replica that was waiting for the CA cannot overwrite the status or back-off another replica wrote meanwhile (all backends; conformance test). A database error while saving is logged and the advice in hand is still used. The renewal row is read again under the lease before an order, so a back-off set during the question is honoured. A failed order keeps the advice; a new certificate clears it.

## Serving

* SMTP: `SmtpServer` asks the provider per handshake (`GetContext(sni)`), which returns the cached `SslStreamCertificateContext` with the intermediates, so a renewed certificate is used by the next connection and strict peers receive the full chain.
* HTTPS: `Cli.ServeAsync` calls `listen.UseCertificateStore(runtime.Certificates)`. Kestrel's `ServerCertificateSelector` returns a bare leaf and the intermediates are then not sent (found by the Pebble tests: the dashboard served a chain a strict client could not verify); the helper uses the handshake callback instead and returns the same context, TLS 1.2 minimum.
* Banner: `CertificateHealthContributor` turns the stored renewal state into the warnings of `/api/v1/capabilities` and `/readyz`: `acme_pending` (ACME is configured and no ACME certificate is active, no failure recorded yet) and `acme_failing` ("... failed N times in a row: <category>. Next attempt: ... UTC. Until one is issued the server uses a self-signed certificate." or "The previous certificate stays in use until ..."), cleared by the next issuance. One warning per state, from the database, so every replica says the same. **Only a category** (`AcmeFailureCategory`: the port could not be bound, the CA could not validate the challenge, the CA could not be reached, the CA refused the request, external account binding, a wildcard needs DNS-01, or "the order failed"), never the error text, the directory URL or a certificate name, because those endpoints are unauthenticated. The full `last_error` stays in the renewal state: `GET /api/v1/admin/certificates/acme`, the dashboard's ACME renewals, the server log. Only certificates the renewal service retries by itself count (the configured one and the active ACME certificates); a failed record of names that were requested once and never issued is visible in the admin view and nowhere else, and does not make replicas wake up every 30 seconds. `self_signed_certificate` stays as before.
* Reload: the poller notices a new store version within `Tls:PollInterval`; a certificate that cannot be loaded or is expired is skipped with a log line and the previous set stays.

## Bugs the Pebble tests found (fixed)

* The dashboard HTTPS listener sent only the leaf certificate (above).
* A failed first order stranded the ACME account: the key was stored only after a successful order, so every retry registered another account at the CA (rate-limited at real CAs). The account is now stored the moment the CA creates it.
* An HTTP timeout surfaced as a cancellation, was not caught by the renewal service and ended the renewal loop silently until restart. Every failure of an attempt is now recorded with back-off.
* `badNonce` from the CA failed the whole attempt (Certes retries it only for some requests); the order is now repeated.
* Transport errors reached the renewal record as "One or more errors occurred"; they now say what happened.
* An already valid authorization was challenged anyway and the CA refused ("Cannot update challenge with status valid, only status pending"); it showed up as CI flakes because Pebble reuses authorizations at random even with `PEBBLE_AUTHZREUSE=0`. The runner now checks the authorization and challenge status first, and CI pins reuse to always (`=100`) so both paths are deterministic.
* Authorization polling checked every 3 s; it now starts at 200 ms and grows to 3 s, so a quick CA no longer costs a multiple of 3 s per order.

## Known gaps

* **Not verified against a production CA.** Pebble follows RFC 8555 but is not Let's Encrypt: rate limits, CAA checks, the real DNS propagation of Cloudflare and the real profiles are not exercised. See [operations.md](../operations.md#tls-certificates-and-acme) for the staging run.
* DNS-01 only with Cloudflare as provider; no TLS-ALPN-01. HTTP-01 and EAB are verified against Pebble only (Let's Encrypt's multi-perspective validation, rate limits, IPv6-first fetching and ZeroSSL's real EAB are not), and binding port 80 as the non-root user of the image is verified neither in a real container nor under Kubernetes. Pebble resolves names through the test DNS server, so "the name's A record points here" is not exercised.
* The HTTP-01 listener does not follow the dashboard's reverse-proxy settings: behind a load balancer that terminates port 80, forward `/.well-known/acme-challenge/` to it unchanged. Its own request limits (8 KiB, 5 s, 128 connections) are fixed, not configuration.
* ARI is verified against Pebble's draft-03 implementation and a stub CA only (the certificate id format is the same as in RFC 9773); Let's Encrypt's production answers are untested. Certes does not expose `Retry-After` of error answers, so 429 and 503 use the error back-off. The directory is fetched again for every ARI question and every order (a few small requests a day). Revoking a certificate ourselves is not implemented.
* No certificate profile selection (Let's Encrypt `classic`/`tlsserver`/`shortlived`).
* The ACME account email is only used at registration; changing `Acme:Email` does not update an existing account.
