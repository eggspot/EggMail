# HTTP API (`Mta.Host/Api`)

ASP.NET Core Minimal APIs implementing [api.md](../api.md). It lives in `Mta.Host` (a Web SDK project) as an extension, not as a composition root: the host that owns `Program.cs` (not built yet) calls two methods.

```csharp
builder.Services.AddEggMailApi(loadedConfig);        // or AddEggMailApi(new ApiOptions { ... })
var app = builder.Build();
app.MapEggMailApi();                                  // /api/v1/** plus /healthz, /readyz, /metrics
```

## Wiring into `mta serve`

`Hosting/ApiHosting.cs` connects the API to the runtime built by `EggMailRuntime`: it registers the runtime's `SubmissionService`, `ISecretProtector`, `AuthThrottle` (the instance the SMTP ingest uses), `IDnsResolver` and `AcmeRenewalService`, calls `AddEggMailApi(loadedConfig)`, maps the routes (`/healthz` moved here from `DashboardHosting`), gives the webhook dispatcher the tenants' SSRF allowlists (`SettingsService.GetWebhookAllowlistSnapshot`) and creates the first administrator when no admin exists (`Hosting/FirstAdministrator.cs`): from `Dashboard:BootstrapAdminPassword`, else the password file `Dashboard:BootstrapAdminPasswordFile`, else a generated password that `Cli.ServeAsync` prints once to the console (decision 90); a password that cannot be used is a `Problem` result and stops the start. `Cli.ServeAsync` has three calls into it.

## What the host must provide

Registered by the host (the API registers none of them): `IStorage`, `StorageOptions`, `ISecretProtector` (Data Protection in production), `SubmissionService`, `IDnsResolver` (for domain verification). Optional: `IClock`, `AuthThrottle` (**share the instance with the SMTP ingest** so the failed-login lockout is shared), `IStorageSwitchService` (the engine; without it the endpoints answer 503 `not_ready`), `AcmeRenewalService` (without it `POST /admin/certificates/acme` answers 503), `PrometheusTextExporter` (for `/metrics`), `IStoragePressureSource`. `AddEggMailApi` registers the API services, the `DomainVerificationService` hosted service, two health contributors (storage warnings, certificate warnings), `HealthService` and defaults for the optional services above. `ApiOptions` (`AddEggMailApi(LoadedConfig)` derives limits, the bounce domain, the locked configuration keys, webhook options and `MetricsEnabled` from the deployment configuration) holds every limit with its default.

Deployment notes: behind a reverse proxy configure the forwarded-headers middleware, otherwise the session cookie decision, the login throttle and the `/metrics` allowlist see the proxy's address (`/metrics` refuses any request that still carries `X-Forwarded-For`). The dashboard origin and the API are the same origin, so there is no CORS.

## Design decisions

**Handlers throw, a filter answers.** Endpoint code throws `ApiException(status, code, detail, errors?, extensions?, headers?)`; one endpoint filter on the `/api/v1` group turns it into problem+json. Anything else becomes a generic 500 (logged with the request id, never echoed). Request bodies are read by the API itself (not by minimal-API binding) so the limit is enforced while streaming, the body can be hashed for idempotency, unknown members (`JsonUnmappedMemberHandling.Disallow`) and bad base64 become `validation_failed` with the member path as `field`, and base64 attachments are decoded straight into `byte[]` by the JSON reader (no intermediate string).

**Authentication.** A bearer key is looked up by the SHA-256 digest of the token (`IConfigStore.FindApiKeyAsync`), compared again in constant time, rejected when revoked or when its tenant is suspended; `LastUsedAt` is written at most once a minute per key. A session cookie is a 256-bit random secret whose digest is the primary key of `dashboard_session`; it is checked for absolute expiry and idleness, the user and (for tenant users) the tenant must still be enabled, and for mutations the `X-CSRF-Token` is compared in constant time with the token stored in the session. If an `Authorization` header is present it is the only credential considered (no fallback to the cookie). Sign-in verifies PBKDF2 (a dummy hash for unknown users), counts failures in the `AuthThrottle` under the keys SMTP AUTH uses (`<ip>` and `user:<name>`), upgrades old hashes, replaces the session of the presented cookie and purges expired sessions at most every ten minutes. `Secure` is set on the cookie except for plain HTTP from loopback (`CookieSecureMode.Auto`).

**User management** (`UsersApi`, decision 84). Every route starts with `RequireAdminAsync` (a tenant user or an API key never gets past it; the authenticator also enforces the CSRF token for cookie mutations) except `POST /me/password`, which takes any session. Changes go through `IConfigStore.UpdateDashboardUserGuardedAsync(id, change, endSessions, keepSessionHash)` and `DeleteDashboardUserGuardedAsync(id)`: one config write that reads the stored row, applies a pure `change` function to it (so a password change made from an older copy cannot undo a concurrent disable), refuses a result with no enabled administrator (`WouldRemoveLastAdmin` becomes `409 conflict`, `reason: last_admin`), writes the row and deletes the user's sessions (all, or all but the caller's own for a password change). Config writes are serialized on both backends (the SQLite writer thread, the PostgreSQL advisory lock), which is what makes the check race-free; the conformance suite runs two administrators removing each other at once on InMemory, SQLite and PostgreSQL. Passwords are hashed off the request thread (`Task.Run`, PBKDF2 600,000 iterations); a generated password is 18 random bytes in base64url. The current password of `/me/password` is verified after `AuthThrottle.IsLockedOut(ip, user:<name>)`, a wrong one records a failure for both keys and a right one clears the user's key, exactly like sign-in. The throttle calls are the async ones of the shared store (`CheckAsync`, `RecordFailureAsync`, `RecordSuccessAsync`), exactly as `SessionService.SignInAsync` uses them, so on PostgreSQL the budget is shared with the other replicas; the host tests run two servers over one in-memory coordination store. `PATCH` derives every member from the row it reads inside the write (the closure sees the stored user, not the copy the handler read for validation), and `/me/password` changes the hash only if it is still the verified one (`409` otherwise). **Sign-in cannot outlive a change:** after the password is verified the session is stored with `IConfigStore.TryAddDashboardSessionForVerifiedUserAsync`, which inserts only if the stored user is still enabled and has the verified password hash, role and tenant (check and insert are one write); a reset, role or tenant change, disable or delete that landed in between makes the sign-in answer 401 and stores nothing. The hash upgrade at sign-in is a guarded write conditional on the verified hash. `ApiOptions.PasswordHashIterations` (internal) lets the tests lower the cost, and two internal seams (`UsersApi.AfterReadForTest`, `SessionService.AfterPasswordVerifiedForTest`) let the tests run a concurrent change at the exact moment, so the race tests are deterministic. Disabling or demoting does not wait for the session lifetime: `AuthenticateSessionAsync` reads the user on every request and drops the session when the user is missing or disabled, and the role comes from that same row.

**Domain onboarding** (`Mta.Host/Domains`, `Hosting/DomainBootstrap.cs`, `Hosting/DomainsCommand.cs`, decision 88). `DomainRecordPlanner.Plan` (a pure function of the domain, its published DKIM keys and `DomainRecordOptions`) lists everything a domain needs: DKIM, return-path CNAME, SPF (only when there is something to authorize), DMARC and, when `Hostname` is fully qualified, the bounce MX and reverse-DNS advice, and with `Domains:MtaStsMode` TLS-RPT, the MTA-STS TXT and the `mta-sts.<domain>` CNAME. Each record has a purpose, a `Required` flag and a one-sentence note. `DomainChecker` looks each up with its own rule and reports `ok`, `missing`, `invalid` (malformed or duplicated) or `mismatch` (well-formed, other value) with the found text; a lookup that fails is `pending`, and only required records decide the domain state. `ZoneFile.Render` writes the same list as zone-file text (also what `GET /domains/{id}/records`, the log and `mta domains records` show). `MtaStsPolicyMiddleware` (added by `app.UseMtaStsPolicy()` only when `Domains:MtaStsMode` is on) answers `Host: mta-sts.<registered domain>` on `/.well-known/mta-sts.txt` from the same `DomainRecordOptions`, so the policy file and the `id` of the `_mta-sts` TXT (a hash of the file) cannot disagree; the registered-domain lookup is cached for 30 s, bounded, so anonymous requests with invented host names do not each reach the database. `DomainBootstrap.RunAsync` (after storage opens and the bootstrap administrator exists, only in `StartupMode.Normal`) takes the lease `domains-bootstrap`, picks the oldest tenant or creates `Default`, registers each missing listed domain through `DomainRegistration` and logs its records one line per record; a replica that does not get the lease does nothing.

**Inbound mail** (`InboundApi`, decision 95). Needs the `inbound` scope; every handler resolves the tenant with `RequireTenantAsync` and finds the domain, route or message through a tenant-keyed lookup, so another tenant's is a plain `404`. `PATCH` of the settings reads a number with `JsonElement` so that an absent member (unchanged), `null` (back to the server default) and a value can be told apart; enabling a domain needs `Verified` or `TemporaryFailure` (an MX record proves no ownership). Route validation is `InboundRules.ValidateRoute` of `Mta.Storage` (the same rules the tests and the receive path use) with its member names mapped to the nested request names (`match.localPart`, `action.forwardTo[1]`); the webhook endpoint must belong to the tenant, and `DELETE /webhooks/{id}` refuses an endpoint a route still uses. A forward route comes back with the warning `spf_not_ok` while the last check of the domain's SPF record was not `ok`. The detail view parses the stored copy with `InboundContentReader`: bounded by `MimeLimits`, bodies cut at 256 KiB, at most 200 headers, and the **same walk and classification as `MessageContentExtractor`** (into multiparts only; a test compares the attachment list of both), so the index of an attachment is the same wherever it is quoted. Raw messages and attachments are written by `DownloadResult` as `Content-Disposition: attachment` with a sanitized ASCII name, `nosniff`, `no-store`, and attachments always as `application/octet-stream` (the claimed type is only in `X-Original-Content-Type`). The server defaults behind the `effective` values come from `ApiOptions.Inbound` (`Inbound:*`).

**Tenant isolation.** `RequireTenantAsync` resolves the effective tenant once per request (the caller's own; for an admin the `X-Tenant-Id`), and every storage call that follows takes that tenant id: history queries, suppressions, API keys, SMTP credentials, statistics and settings are tenant-keyed in storage; domains and webhook endpoints are fetched by id and checked (`TenantId == caller`) before use, answering `404` otherwise. The tests (`tests/Mta.Host.Tests/Api`) cover every group with two tenants.

**Sending** composes JSON with `MessageBuilder` (header injection is rejected, denied headers cannot be set) or takes a raw message, then calls `SubmissionService` like the SMTP ingest does: sender policy, header repair, content extraction, durable intake, idempotency. The idempotency fingerprint (SHA-256 of the endpoint and the exact request bytes) is stored with the key by storage; a duplicate whose stored fingerprint differs is 409. A byte budget (`SendBudget`) limits the memory of send bodies in flight.

**Cancel** (`MessagesApi.CancelAsync`, decision 86). Needs the `send` scope and no history. Order: authenticate and authorize, validate the optional body (an empty `recipients` list is refused so that it can never mean "all"; addresses are parsed and echoed in their parsed form), then one `IDeliveryStore.CancelAsync(tenant, message, recipients, now, webhookEvent)`, which keys every row by tenant as well as message id, so another tenant's message is indistinguishable from an unknown one. The webhook callback builds the `message.cancelled` draft (`WebhookEventFactory.ForCancelled`, only when `IWebhookOutbox.MayHaveSubscribers`) and storage writes the outbox rows in the cancelling transaction. When something was cancelled the answer is `200` (the status afterwards is read with one `IHistoryStore.GetAsync`, only under `History:Mode=Full`). When nothing was: `inFlight` or `transferHeld` rows give a `409` with the matching text; otherwise, under `StatsOnly`, no waiting row at all is a `404` (a finished message cannot be told from an unknown one) and a named-but-not-waiting recipient a `409`; under `Full` the message is loaded once (unknown or foreign: `404`), and a repeated request whose work is done (every named recipient has a `cancelled` event, or, without names, the status is `cancelled`) is `200` with nothing cancelled, anything else `409`. There is no scan of the queue in the API: the storage lookup uses the `delivery_queue (message_id)` index. No audit log exists; the `cancelled` events in the message history are the record (they do not name the actor), and no secret or message content is logged.

**Domain verification** (`DomainVerificationService`). Every 15 s (configurable) it takes the domains due (`GetDomainsDueForCheckAsync`), at most four in parallel, and runs `CheckAsync`, which is also what "Verify now" calls (guarded by `VerificationSchedule.CanVerifyNow` and `TryLockAsync`: a per-domain in-process set plus a lease `domain-verification:<id>` of the config store, five minutes, released when the check ends; DKIM rotation takes the same lock, so neither runs twice at once across replicas): plan the records (`DomainRecordPlanner`) from the published DKIM keys, look them up (`DomainChecker`), apply the result to the fresh domain row with `VerificationSchedule.Apply` (statuses, failure counts, the 72-hour grace, `SendingPaused`, next check), persist (the per-record results too: `domain_record_check`, replaced as a set by each check and kept for the records a DNS outage could not look up), and switch signing to a rotated-in key whose record was found. Only the signing key's DKIM record and the return-path CNAME (when a bounce domain is configured) are required; a pending next key, a retired key within its 7-day grace, SPF, DMARC, TLS-RPT, the MTA-STS records, the bounce MX and the reverse-DNS check are advice (see "Domain onboarding" below). Unexpected checker exceptions count as a DNS failure so a bug cannot degrade a domain. `SenderPolicy` (existing) enforces the resulting status at submission time: `Pending`/`Verifying`/`Failed` and `SendingPaused` refuse, `TemporaryFailure` sends.

**Rotation.** `rotate` adds an inactive key; the delivery engine signs with the newest `Active` and not retired key, so signing is unchanged until `SetActiveDkimKeyAsync` runs (which retires the previous key with `RetiredAt = now`). Published keys are the active one, pending ones and retired ones for 7 days. Selector names are `egg<YYYYMM>` (`DkimKeyTools.SuggestSelector`) with `-n` suffixes, never reused.

**Webhook secrets** are stored as one protected string of one or two space-separated `whsec_` secrets, newest first, which is what the dispatcher signs with. SSRF: `WebhookUrlValidator` at registration (allowlist from `SettingsService.GetWebhookAllowlistAsync`, which the host should also give to `WebhookDispatcher.AllowlistProvider`), the dispatcher's resolver guard at delivery.

**Settings.** The catalog in `SettingsService` is the single list of what can be changed through the API. Tenant `Content:StoreAttachments` is the tenant-scoped settings row of that key (absent = the tenant never chose and inherits the operator default; the tenant record's `StoreAttachments` flag mirrors the last choice and, when true without a row, counts as a choice of yes; `AttachmentStoragePolicy`); other values are `SettingRecord`s (tenant-scoped or global) with a JSON scalar. Locked means deployment-only, fixed by a configuration key the deployment sets (`ApiOptions.LockedKeys`), administrator-only (tenant view), or (attachments) disabled by the operator.

**Relay routes and TLS policies** (`RoutingAdminApi`). Both are global records (`RelayRouteRecord`, `TlsPolicyRecord` have no tenant), so every handler starts with `RequireAdminAsync` (a tenant user, an API key and an anonymous caller are refused before anything is read; a session also needs the CSRF token). The API validates the whole record after a `PATCH` has been merged into the stored one, not the patch alone, so a change of `tlsMode` cannot leave credentials on a plaintext route. Names are unique case-insensitively and checked against the list before the write (the table has no unique index on the name, because a unique index would need a schema version and a bundle change on both backends; the admin-only, 50-route scale makes a lost race a cosmetic duplicate); the TLS pattern has a unique index in the store, and a conflict that slips past the check is reported as a validation error on `domainPattern`. The relay password is protected with `ISecretProtector` (`SecretPurposes.RelayPassword`, the same purpose the delivery engine unprotects with and the backend switch re-protects with) before it reaches the store and is not part of any response, log line or exception message; responses carry `hasPassword`. Every change logs one structured line through `ILogger` (actor, record, what changed, password `set`/`none`); there is no audit table. After a successful write the handler calls `IRoutingConfigNotifier.Changed()`; `mta serve` registers a notifier that calls `DeliveryEngine.RequestConfigRefresh()` ([delivery.md](delivery.md)), a host without an engine registers none and the change is picked up by the engine's refresh interval.

**Uploads.** A PEM upload must contain a key that belongs to the first certificate; the key is exported as PKCS#8, protected with `SecretPurposes.TlsPrivateKey` and stored like the ACME ones, so `DatabaseCertificateProvider` serves it at its next poll. ACME requests run in the background through `AcmeRenewalService.RequestAsync`; certificates requested for other names than the configured set are stored as `acme:<first name>` and renewed by `CheckOnceAsync` with the configured one.

## Limits (defaults)

JSON body 1 MiB (sending endpoints 40 MiB), message 25 MiB, 50 recipients, 50 attachments, 50 custom headers, 10 tags; 200 domains, 100 API keys, 100 SMTP credentials, 50 webhooks per tenant; list pages 200 (suppressions 500); statistics 50,000 rows, 35 days (hourly) / 800 days (daily); sessions 12 h absolute / 2 h idle; capabilities and readiness cached 5 s; send bodies in flight 512 MiB.

## Tests

`tests/Mta.Host.Tests/Api` runs the real endpoints in process (TestHost) over `InMemoryStorage` and, for a smoke subset per group, SQLite in a temp directory, with a controllable clock and DNS. Groups: authentication and sessions (cookie flags, CSRF, throttle shared with SMTP AUTH, expiry, roles, `X-Tenant-Id`), errors and limits, capabilities and operational endpoints, sending and idempotency, messages and resend, `StatsOnly` (410s), domains (state machine, rate limit, rotation), suppressions, webhooks (SSRF refusals, secrets, test/attempts/replay), credentials, statistics, settings, admin (tenants, status, settings, certificates, ACME with a fake authority, maintenance, switch with a fake engine), accounts, user management (`ApiUsersTests`: roles and tenant isolation, CSRF, session invalidation, the throttle, last-admin protection including concurrent removals on in-memory and SQLite, races that must not undo or outlive a change, the exact log lines; the API test fixture runs on in-memory and SQLite only, so the HTTP-level `last_admin` tests do not run on PostgreSQL: the storage conformance suite (including two administrators removing each other at once) does, and the HTTP layer adds no storage-specific logic), and cancel (`ApiCancelTests`: scope, CSRF for sessions, tenant isolation, validation, in-flight and transfer-held conflicts, idempotent retry, `StatsOnly`, the webhook event), and `ApiContractTests`, which checks real responses against the TypeScript types in `dashboard/src/api/types.ts` (a small reader of the `.ts` file, no Node needed) and that every request member the dashboard sends is accepted.

## Known gaps

- The automated tests run in process (TestHost). `mta serve` was smoke-tested on Kestrel by hand (curl); a reverse proxy, TLS in front of the API and a browser were not exercised, and the dashboard's own Vitest suite runs against its mock, not against this API.
- A verified domain from before check results were stored shows its required records as `ok` and the rest as `pending` until its next check (daily).
- The lease that serializes checks and rotations across replicas is taken with the config store's lease facility, so it is as exact as the store is; a replica whose clock is more than the lease length (five minutes) ahead could take the lease early. Cancelling a rotation (`DELETE .../dkim/rotate`) does not take the lock (it only deletes a key that never signed, atomically).
- Statistics queries load the rows of the range (bounded by the range limits and the storage series cap) before the row cap and the `domain` filter apply.
- Behind a reverse proxy set `ASPNETCORE_FORWARDEDHEADERS_ENABLED=true` (the built-in switch of the ASP.NET Core host) so client addresses are seen; there is no EggMail setting for it.
- A domain name can be registered by one tenant only, first come first served, with no proof of ownership beyond the DNS records the owner must publish; there is no admin transfer.
- Global settings are stored in the config store and applied at the next start through the stored-settings layer (`SettingsLayering`); each is flagged `requiresRestart`. No global setting is applied live: the design asks for none (decision N), and the three per-tenant settings that change at runtime (`Sending:PerHour`, `Sending:PerDay`, `Webhooks:AllowedNetworks`) are already live. `mta admin create` exists (`AdminCommand`, offline account creation through `DashboardAccounts`, see [operations.md](../operations.md)).
- `recipient_suppressed` is reserved. `tags` (`POST /messages`) are stored with the history (`History:Mode=Full`), returned as `tags` by the list and the detail and searched with `?tag=`; `/messages/raw` takes none.
- Relay route names are unique by a check before the write, not by an index: two administrators creating the same name at the same moment can both succeed. Relay delivery with credentials is covered end to end through the real engine over a loopback server that accepts only the right login after STARTTLS (protected password, rotation, refusal); it has not been run against a real relay provider.
- No audit log table of administrative actions (user management and relay route and TLS policy changes write one structured log line per change, with the actor and the target and no secret; other admin changes write none), and no per-tenant request rate limit (only the failed-login throttle, which also guards `POST /me/password`, the verify limit and the send byte budget).
- Dashboard users have no "must change password at next sign-in" flag, no password history and no composition rules: the policy is the length (10 to 1,024). A password reset by an administrator is a secret the administrator sees and passes on, which is why the user can change it at once on the Account page.
- The switch endpoints run on the real engine in `mta serve` (`StorageSwitchService` over `IStorageSwitchEngine`, [switch.md](switch.md)); the API tests use a fake engine, and the engine has its own end-to-end tests. Without a registered engine (a host that does not wire one) they answer 503 `not_ready`.
