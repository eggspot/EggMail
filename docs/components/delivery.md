# Delivery engine (`Mta.Delivery`) and ingest (`Mta.Host/Ingest`, `Mta.Host/Submission`)

## Outbound

`DeliveryEngine` leases due deliveries (`IDeliveryStore.ClaimAsync`), groups them by (message, recipient domain) and runs each group through `DeliveryProcessor` concurrently (`MaxConcurrentGroups`). A group is one SMTP transaction (at most `MaxRecipientsPerTransaction` recipients).

Per group, in order:

1. Expired deliveries are recorded as `Expired`; suppressed recipients as `Suppressed` (nothing is sent).
2. The raw message is read from the spool; a missing message is a permanent failure.
3. `SendingLimits.TryReserve`, then `DestinationThrottle.TryAcquire`. A refusal holds the deliveries (`Deferred` with `CountAttempt=false`: no attempt is counted, no event, no webhook).
4. DKIM: `IDkimSignerProvider` (config store: the domain or its nearest registered parent, newest active key; cached) supplies the signer. No key means the message goes out unsigned. The signature is made later, per server, over the bytes that are actually transmitted (step 6).
5. Envelope sender: a signed VERP bounce address when a bounce domain is configured (not for bounces themselves), else the original sender. The host after the `@` is the sending domain's own return-path host (`bounce.<domain>`) once its CNAME to the bounce domain has been verified (`SenderPolicy.SelectReturnPath`, looked up at most once a minute per domain), otherwise the shared bounce domain; the first lets SPF, which is checked against the envelope sender, align with the From domain. The token is bound to the destination domain of the delivery group, so a report that names an address elsewhere is ignored (decision 92). A bounce domain written as a U-label is accepted and goes on the wire as its A-label.
6. Routes from `RoutePlanner`: direct MX, then opted-in relays. For direct delivery MX hosts are tried in order (circuit breaker per host); each host gets a TLS decision from `OutboundTlsPolicyResolver` (MTA-STS, DANE, per-domain level overrides from `TlsPolicyTable`). A blocked or failed TLS negotiation moves on to the next MX host; a connect failure moves on to the next address; once a server answers, the answer decides. What is sent is decided per connection, after the EHLO, by `OutboundTransaction.Plan` (see "8-bit and internationalized mail").
7. Per recipient the reply is classified (`ReplyClassifier`): 2xx at end of data delivers, permanent classes fail (only `PermanentRecipient` suppresses), the rest are deferred with `RetrySchedule` or expire when the next retry would pass the delivery's lifetime.
8. Results are recorded with `RecordAttemptAsync` (storage writes the event, statistics and webhook outbox rows in the same commit). For permanent failures and expiries of SMTP-submitted mail a bounce message (RFC 3464) is queued **before** recording, because recording the last recipient frees the stored message.

A connection lost after the end of data was sent is deferred with the `possible_duplicate` flag. A delivery whose lease ran out while its holder was still sending is claimed again by another replica (or the same engine), which sets the row's flag; when the first holder reports, the attempt planner also reads the row's flag, so the report carries `possible_duplicate` too (decision 83). `QuiesceAsync` stops claiming, waits up to the timeout, cancels what is left (recorded as `AbortedBySwitch`, requeued unchanged, flagged possible duplicate only when the end of the message data had begun to be written, see `SmtpClientConnection.EndOfDataStarted`) and releases the leases (decision R).

### Relay routes, TLS levels and how a change reaches the engine

`RoutePlanner` and `TlsPolicyTable` hold the relay routes and the per-domain TLS levels in memory. `DeliveryEngine` reloads both from the config store every `ConfigRefreshInterval` (30 s; `RefreshConfigAsync`) and immediately after `RequestConfigRefresh()`, which the admin API calls (through `IRoutingConfigNotifier`) after it changed either list; a failed reload keeps the previous lists and logs a warning. `ConfigRefreshCount` counts completed reloads (tests wait on it instead of sleeping). A reload replaces the lists as a whole, so a delivery attempt sees either the old or the new set; the next attempt of a queued, deferred message uses the new one. Other replicas reload within the interval.

Relay `TlsMode` (case-insensitive) maps to the client policy in `DeliveryProcessor.RelayTlsPolicy`: `none` no TLS; `starttls` STARTTLS when offered, any certificate, plaintext otherwise; `required` STARTTLS required, certificate not validated; `verify` STARTTLS required with the chain and the relay's host name validated (`SslPolicyErrors.None`); `implicit` TLS from the first byte, validated the same way. (Before this was written, `verify` and `implicit` accepted any certificate: a relay with credentials could be impersonated. The pool key now carries the security a connection was made under, so an idle connection is only handed to a target that asked for the same: for relays whether the certificate is validated and a keyed fingerprint of the password with the user name (a rotated secret or a second route with another password never reuses an authenticated connection, and the key never holds the password); for direct delivery `TlsPolicyDecision.PoolIdentity`, which covers the rule (encrypt, verify, MTA-STS enforce or testing, DANE), the validation mode and whether it is enforced, the expected host name and a hash of the TLSA records. A connection made without validation is therefore never served to a `verify` domain, and a policy raised to `verify` is not bypassed by idle connections.) A relay that refuses the login (stage AUTH, whatever the reply code) is treated as a temporary failure of the route (`454 4.7.0`, the mail waits and is retried): the credentials are configuration, and a permanent reply would bounce every message for the relay's domains. Credentials are unprotected just before the connection (`SecretPurposes.RelayPassword`; the decrypted bytes are zeroed once the string is built) and the client refuses to send them on a connection without TLS.

The per-domain TLS level (`TlsPolicyTable.For`: exact name, longest `*.suffix` (every subdomain at any depth, not the domain itself), `*`, else the default `may`) is the configuration handed to `OutboundTlsPolicyResolver`; MTA-STS and DANE then apply on top as described in [tls.md](tls.md) and [../api.md](../api.md#relay-routes-and-tls-policies-role-admin-addition): only level `none` bypasses them.
### Cancelling a queued message

`IDeliveryStore.CancelAsync` (`POST /messages/{id}/cancel`, [../api.md](../api.md)) finishes the *waiting* recipients of one message as `DeliveryOutcome.Cancelled`, with the same consequences as a recorded attempt (`AttemptPlanner`): queue row deleted, a `cancelled` event (under `History:Mode=Full`), the message status recomputed, the spool freed with the last recipient (a retained raw message moves to history like for any final outcome), and the `message.cancelled` webhook rows in the same commit. It adds no statistic counter and no bounce message.

**In-flight rule (decision 86).** A delivery is *in flight* while it is leased (`lease_until` after the time the cancel runs); a row marked by a backend switch is *transfer-held* and is reported under its own name. A cancel only ever takes deliveries that nothing holds, and it takes them in the same serialized step that `ClaimAsync` uses (SQLite: the single queue writer; PostgreSQL: one transaction with `FOR UPDATE` on the message's rows, while claim uses `FOR UPDATE SKIP LOCKED`; in-memory: the state lock; the fence is checked again inside that step). So for every delivery exactly one of two things is true: it was claimed first (the cancel reports it in `inFlight` and leaves it; the processor records its result as usual), or it was cancelled first (the row is gone; no claim can ever return it). Consequences:

- Cancel never interrupts or races an SMTP transaction. A result for a cancelled delivery is only possible from a worker whose lease had already expired (another worker could claim the row at that point anyway); that late `RecordAttemptAsync` finds no row and is a no-op, so it cannot resurrect the delivery, double count anything or send a second event.
- A row whose lease has expired but whose holder never reported (`lease_owner` is still set: the worker died or stalled), and a row flagged `possible_duplicate`, **may already have been sent**. Cancelling takes it (nothing can be delivered by the queue any more), and the cancel is recorded as what it is: the `cancelled` event carries the text "Cancelled while the outcome of an earlier delivery attempt was unknown; the message may already have been sent." and is followed by a `possible_duplicate` event (the same rule `AttemptPlanner` applies to every recorded attempt, decision 83), and the webhook event has `possible_duplicate: true`. Only a row with no such doubt says "Cancelled before delivery." (A graceful shutdown or quiesce releases leases without the doubt: `ReleaseOwnedLeasesAsync` clears `lease_owner`.)
- A recipient that is *deferred, waiting for its next attempt* has no lease and is cancellable: the common case of "stop retrying this".
- Cancel does not abort a running attempt. The alternative (a `cancel_requested` flag consulted when the result is recorded) would still send the message and only hide the fact, and aborting the connection would risk a partial transmission; refusing the in-flight recipient is the only provably safe choice, and the caller can simply retry once the attempt ends (a transmission lasts seconds, the lease is minutes).
- A cancelled recipient is not suppressed and does not count against the destination; sending the message again is a resend.
- Recipient addresses given to the cancel are compared with the stored recipient as a whole address, ignoring case (the domain part is stored in lower case, the local part as submitted).

The processor needs no change: it never sees a cancelled delivery, because the row is deleted before it can be claimed. `CancelThroughEngineTests` runs the cases through the real engine (before the first attempt, deferred and waiting, mid-transaction with the remote holding the reply); the conformance suite runs the races (claim, deferral report and a second cancel against a cancel) on every backend.

### Metrics and traces

`DeliveryMetrics` (`Mta.Delivery`): attempts by outcome, group duration, holds, claims and their duration, the duration of storing results, bounces generated, and the queue gauges. The gauges (`mta_delivery_queue_depth` by state, the age of the oldest due delivery, spooled bytes) read the last `QueueSample` of `QueueGauges`, a background loop that calls `GetQueueStatsAsync` every `Observability:QueueSampleSeconds`; a scrape never queries the queue. A failed sample keeps the previous numbers and is counted. The metric table is in [../operations.md](../operations.md#monitoring).

`DeliveryTracing` adds the delivery side of the message trace (`MessageTrace`, source `Mta.Message`): `mta.queue.wait` (emitted at the first claim, starting at the acceptance time) and one `mta.delivery.attempt` span per group with a `recipient.result` event per recipient. The trace id is the message id and the parent span id is derived from it, so no trace context is stored in the queue (DESIGN-DECIDED, decision 69). With no listener each entry point costs one check.

## 8-bit and internationalized mail

`OutboundTransaction` (internal to `Mta.Delivery`) holds one transaction's stored message, envelope and DKIM signer, and turns the answer of each server's EHLO into the bytes and MAIL FROM parameters actually used. Each variant is built at most once per transaction (a second MX host reuses it). Standards: RFC 6152 (8BITMIME), RFC 6531/6532/6533 (SMTPUTF8, UTF-8 headers, internationalized DSN), RFC 2045 section 6.4, RFC 3463 status codes.

| Message | Server | Result |
|---|---|---|
| 8-bit body | offers `8BITMIME` | `BODY=8BITMIME`, bytes unchanged (signed as they are) |
| 8-bit body | no `8BITMIME` | body converted to 7-bit by `EightBitDowngrader` (`Mta.Mime`), no `BODY` parameter, **then** signed; if no safe conversion exists: permanent `554 5.6.1` naming the reason |
| 7-bit body | any | no `BODY` parameter |
| valid UTF-8 in the header section (also when every address is ASCII), or the persisted flag `ClaimedDelivery.HeadersUtf8` | offers `SMTPUTF8` | `SMTPUTF8` declared |
| same | no `SMTPUTF8` | nothing is sent: permanent `554 5.6.9` (headers are not downgraded: RFC 6857 is experimental) |
| sender with a non-ASCII local part | no `SMTPUTF8` | permanent `553 5.6.7` for the whole transaction (after the other hosts of the domain were asked) (a bounce domain makes the sender an ASCII VERP address, which avoids it) |
| recipient with a non-ASCII local part | no `SMTPUTF8` | the others in the group are sent without `SMTPUTF8`; that recipient is offered to the other hosts and fails with `553 5.6.7` only if all refuse |

* "Needs SMTPUTF8" is decided by `EmailAddress.RequiresSmtpUtf8` (non-ASCII local part), not `IsInternational`: a domain is held as an A-label, so `user@bücher.example` is plain ASCII on the wire.
* The persisted flag (`AcceptedMessage.HeadersUtf8`, column `delivery_queue.headers_utf8`, schema version 5 / PostgreSQL `V005`) is decided at intake from the message bytes (`MessageInspector.HasValidUtf8Headers`), not from the submitter's MAIL FROM parameter; delivery also re-checks the stored bytes, so rows queued before the upgrade are handled. UTF-8 that is not valid (8-bit headers in a legacy charset) is not announced as SMTPUTF8 and is sent as is.
* 5.6.x replies are classified `PermanentContent`: the message bounces, the recipient is **not** suppressed. The bounce (DSN) carries the text.
* **A refusal is final only when every candidate host was asked and refused.** A server that lacks an extension does not end the delivery while another MX host of the domain has not been asked: the refusal is remembered and the next host is tried. If a host failed in another way (unreachable, TLS, banner), or was not asked at all in this attempt (circuit breaker open, `MaxMxHostsPerAttempt` reached, no address), the result is a temporary `4.4.1` and the delivery is retried until it expires.
* **Recipients are not failed on the first MX.** When a host takes the group except for recipients whose address it cannot take (no SMTPUTF8), those recipients are offered to the remaining hosts in a transaction of their own (`AttemptResult.Followup`); the others are recorded as delivered or failed by the first host. They fail with `5.6.7` only if every host that answers refuses. (One level only: a second partial refusal on a later host is final for those recipients.)
* **No rerouting through a relay.** A capability refusal is a permanent reply and `RoutePlanner` never reroutes a permanent reply: the relay chain is opt-in per domain for networks that block port 25 (decision 18), not a way around a destination's limits. A relay that supports the extension is reached when the relay is the only route, not as a fallback after a refusal.
* Conversion rules are in [mime.md](mime.md#8bitmime-downgrade); the DKIM-signed bytes are exactly the converted bytes (the conversion changes the body and the `Content-Transfer-Encoding` fields, which a signature made before it would not survive).
* Bounce messages for internationalized recipients use RFC 6533: `message/global-delivery-status` with `Final-Recipient: utf-8; ...` (see `DsnBuilder`), `message/global-headers` or `message/global` for the returned original when its headers hold UTF-8, and the DSN is queued with the SMTPUTF8 flag when its own header section holds UTF-8 (an internationalized sender). Such a report is itself 8-bit and goes through the same conversion for servers without `8BITMIME`.

## TLS-RPT sending address

`sending-mta-ip` in TLS-RPT failure details is `Delivery:PublicSendingIp` when configured; otherwise the local address of the TCP connection, but only when it is a public address (private, loopback and link-local addresses are left out of reports that go to other organizations). The local address comes from `SmtpClientConnection.LocalIpAddress`, also carried by `SmtpClientException.LocalIpAddress` for failures during setup). When a policy blocks an MX host before any connection exists, it is the address the operating system would use to reach it (a UDP "connect" probe that sends nothing). Successful sessions are only counted, as RFC 8460 asks.

## Inbound

`IngestHandler` is the `ISmtpServerHandler`. Submission listeners authenticate a tenant's SMTP credential (PBKDF2 hash, shared lockout through `AuthThrottle`, constant work for unknown users) and pass each message to `SubmissionService`, the one path into the queue for SMTP and the HTTP API: size and recipient limits, `SenderPolicy` (From header domain and envelope sender must belong to the tenant and be verified), `Bcc` removal, Message-ID and Date repair, content extraction for history when `History:Mode=Full`, durable intake. The bounce listener accepts only recipients that are valid signed bounce addresses (or postmaster/abuse), always answers 250 for them and hands the message to `BounceProcessor`: permanent DSN failures that the reply classifier attributes to the recipient suppress it, abuse complaints suppress as complaints, and both are published as webhooks. With `History:Mode=Full` the report is also **attached to the message it is about**: the VERP token (verified, so trusted) names the tenant, the `Message-ID` in the returned headers (stored in `message_index.message_id_header` when the message was accepted, normalized without angle brackets and in lower case) finds the tenant's message (the newest, if a client reused an id), and a `bounced` or `complained` event is appended to its history with the recipient, the enhanced status and the diagnostic; the message status follows (`delivered` becomes `bounced`, or `partial` with several recipients; a complaint makes a delivered message `complained`). The webhook payload then carries `message_id`. With `StatsOnly` nothing per message is stored (the lookup finds nothing), and the suppression and the webhook happen exactly as before. A report whose token names another tenant can only ever look among that tenant's messages. Nothing on the bounce listener can queue mail for delivery.

### Parse once

`SubmissionService` parses the submitted message a single time. The sender check (From domain), the header repair (is there a Message-ID, a Date, a Bcc) and the history extraction (`MessageContentExtractor.Extract(MimeMessage)`) all use that parse. Only headers are added or removed, so subject, bodies and attachments are those of the stored message. The Bcc rule is dropped only when the parsed header list is complete (not cut by `MaxHeaderCount` or `MaxHeaderBytes`) and has no Bcc; otherwise the editor removes it as before, so a Bcc behind the header limits cannot reach the stored copy. The parse objects live in a per-thread `MimeParseBuffers` lent for the synchronous `SubmissionService.Prepare` (valid until it returns; everything kept is a copy), the same content types are shared (`ContentTypeCache`), and the steps of a submission are `Prepare` (no waiting; says when it needs the tenant's domain list or attachment setting loaded), `StoreAsync` (the storage's own task), `Complete` / `Abandon`: the SMTP handler calls them itself so that a message waiting for storage holds one suspended frame fewer, and `SubmitAsync` (API) is the same steps in a loop. Allocation figures: [../benchmarks.md](../benchmarks.md#allocation-work-third-round-2026-10-15).

## Inbound route actions (`Mta.Host/Inbound`)

Design [section 11.7](../design.md#117-route-actions-executed-by-a-worker-after-the-250) and decision 97. The actions of received mail are carried out by `InboundActionRunner`, a hosted service (`InboundActionService`) next to the delivery engine and the webhook dispatcher.

* **Pool.** One claimer per replica keeps up to `Inbound:Action:Concurrency` attempts in flight (`ClaimActionsAsync`, oldest due first; the claim counts the attempt). A row is leased for `Inbound:Action:Lease` and completed with `CompleteActionAsync` carrying `ClaimedAttempt`, so a completion from a claim whose lease ran out (even under the same owner) is refused and publishes nothing. A claimed action that waits for its tenant's slot extends its lease. Shutdown cancels the attempts and gives back the claims it still holds (`ReleaseOwnedActionLeasesAsync`: the attempt was not made); a backend switch pauses it and quiesces it with the delivery engine (`HostSwitchControl`).
* **One attempt** (`ProcessAsync`), in this order: past the last rung (`attempts_exhausted`, a runner that died on it before); `Inbound:Enabled` off (`inbound_disabled`, a deferral); tenant missing (`tenant_missing`) or suspended (`tenant_suspended`, a deferral); route gone (`route_deleted`); then the **route's current action**: `store`/`discard` complete `done` with the note `route_is_now_store`/`route_is_now_discard`, `webhook` posts, `forward` calls the `IInboundForwarder`. A missing body is `body_missing`.
* **Result to outcome.** `InboundActionResult.Done/Retry/Failed`. A `Retry` (an HTTP failure, a deferral) is stored as `Pending` with `now + RetrySchedule[attempt - 1]` while rungs remain, else `Failed`; a final failure publishes `inbound.action.failed` (`data`: `inbound_id`, `route_id`, `action`, `error`, `attempts`) after the completion was recorded. `actionLastError` is a code (`webhook_http_503`, `webhook_timeout`, `webhook_ssrf_blocked`, `webhook_connect_failed`, `webhook_gone`, `webhook_throttled`, `webhook_redirect_not_followed`, `endpoint_disabled`, `endpoint_missing`, `endpoint_not_of_tenant`, `secret_unreadable`, `too_large_for_raw_webhook`, ...): never a URL, an address or the receiver's answer (the outbox attempt log keeps a response snippet; inbound deliberately does not).
* **Webhook.** `WebhookTransport` (Mta.Webhooks) is the one HTTP stack of the dispatcher and the runner: Standard Webhooks signing over the exact body bytes, the SSRF guard on the address actually connected to, the tenant allowlist, no redirects, no proxy, no cookies, no trace headers. `WebhookEndpointHealth` is the one place that updates the endpoint (success clears the failing streak, a failure starts it or disables the endpoint after `Webhooks:DisableAfter`, a `410` disables it at once); it re-reads the endpoint before writing so a secret rotation made during the call is not overwritten. For inbound a `410` disables the endpoint and **the message keeps its ladder** (re-enabling inside it delivers). The runner checks `endpoint.TenantId == message.TenantId` before sending (the route write checks it too).
* **Formats** (`InboundWebhookPayload`). `json`: envelope `{ id, type: "inbound.message.received", timestamp, data }` built with `Utf8JsonWriter` (non-ASCII and `<>&'` escaped, unpaired surrogates replaced), content from `InboundContentReader` (bounded MIME parse), text and HTML cut at `Inbound:Webhook:MaxTextBytes`, headers capped at 256 KiB of text, attachments listed with an authenticated path (`Inbound:ApiBaseUrl` prefix) and never inlined; a message the parser cannot read yields the envelope and verdicts with `message.parse_failed: true`. `raw_mime`: the stored bytes as `message/rfc822`, the envelope and verdicts in `EggMail-*` headers whose values are percent-encoded UTF-8 (`EncodeHeaderValue`: letters, digits and `-._~@+:,;=!$'()*/` stay, everything else is encoded, at most 1024 characters), above `Inbound:Webhook:MaxRawMessageBytes` the action fails at once. `webhook-id` is `evt_<inbound id>` (`evt_<id>-<n>` after the n-th manual retry).
* **Fairness.** At most `Inbound:Action:MaxConcurrencyPerTenant` attempts of one tenant run at once. The storage claim cannot skip a tenant, so a very large backlog of one tenant for a receiver that does not answer still delays other tenants' work on that replica (follow-up: a claim that excludes saturated tenants).
* **Forward** (`InboundForwarder`, decision 98). Queues one `AcceptedMessage` with `Source = Forward` through `IMessageIntake`: recipients are the route's `forwardTo` minus the suppressed ones (`IsSuppressedAsync` here; all suppressed completes `done` with the note `all_targets_suppressed` and keeps the body), envelope sender an **SRS0 address at the route's domain** (`IForwardSrs`, at most 64 octets; the null reverse-path stays null), `SendingDomain` = the route's domain (so the DKIM signer and the sending limits are the route domain's, never the From domain's), idempotency key `inbound:<id>` kept a year with no fingerprint, no Subject/content copy in the outbound history. Refused with a code: a target in the route's domain, in a domain this server receives for or in the bounce domain (`forward_target_is_local`: the loop closed at run time as well as at write time), a message that proves 3 hops (`loop_detected`, `mta_inbound_forward_loops_total`), and a message whose From is in the route's organizational domain and did not pass DMARC (`unauthenticated_local_sender`: the SRS envelope and our signature would otherwise make a spoof of the tenant's own domain pass SPF and DMARC at the final receiver).
* **The copy** is the stored message with headers added on top only: one `X-EggMail-Hops` (`ForwardHops`: HMAC over the body hash with a key derived from the bounce-token ring, every older marker removed, forged ones counted as zero) and an **ARC set** sealed with the route domain's active DKIM key (`ConfigArcSealerProvider`, `ArcSealer`). The chain is validated now with `ArcValidator` (10 instances at most): `cv=pass` for a valid chain, `cv=none` without one, `cv=fail` when it does not validate or the validation was inconclusive (RFC 8617 section 5.1.1). No key or a sealer that cannot take the message: unsealed. The ARC set is added at queue time, not by the engine, because the verdicts it records exist only here; the queued bytes are what is delivered.
* **Engine rules for `Source = Forward`** (`DeliveryProcessor`, `OutboundTransaction`): `ChooseEnvelopeFromAsync` keeps the envelope (no VERP rewrite); the transaction is **byte-exact** (`byteExact`): a server without 8BITMIME is a permanent `5.6.1` for that server instead of a 7-bit conversion (SMTPUTF8 was already a permanent `5.6.9`), because converting would break the original DKIM signatures that carry DMARC for the copy; the DKIM signature the engine adds is the route domain's (it signs by `SendingDomain`) and the original signatures stay byte-identical; `DsnService.Applies` is false for a forward, so neither a failure nor a delay notice is ever generated (there is no delay notice in the engine today; the rule is the one method). The tenant's sending caps, warm-up and the suppression check at delivery apply as for any queued mail.
* **SRS bounces** (`SrsBounceHandler`): a bounce to an SRS0 address of ours is accepted only from the null sender with a valid hash and age (`IForwardSrs.IsValid`, every key of the ring), counted (`mta_inbound_srs_bounces_dropped_total`), logged without addresses and dropped. The receive path of the `Inbound` listener role calls `runtime.SrsBounces`.
* **Metrics.** `mta_inbound_actions_total{kind,outcome}`, `mta_inbound_action_duration_seconds{kind}`, `mta_inbound_actions{state}` (sampled every 15 s with `GetUsageAsync`).

## Known gaps

- **Behaviour change.** A message with UTF-8 header fields used to be sent as is to every server; it now bounces with `5.6.9` (nothing is sent) when the server lacks SMTPUTF8, as RFC 6531 requires. Header downgrading (RFC 6857, experimental) is not implemented, so such mail cannot reach those servers. The `8BITMIME` conversion does not touch 8-bit header fields of nested parts or embedded messages either (it refuses, see mime.md).
- `BINARYMIME`/`CHUNKING` are not used for binary bodies: a `binary`-encoded part is base64-encoded when the server lacks `8BITMIME` and sent as 8-bit otherwise.
- The capability fallback to the next MX host is tested with two loopback servers (IPv4 and IPv6 loopback on the same port); those tests are reported as skipped, with the reason, on a machine without a usable IPv6 loopback address.
- Throttle state and circuit breakers are per process (see `components/policy.md`). The sending counters are persisted and shared through the config store (see `components/policy.md`); TLS-RPT counters and pending reports are persisted too (see `components/tls.md`).
