# HTTP API (v1)

The contract between the host and the dashboard (and API clients). Base path `/api/v1`. JSON in and out, UTF-8, timestamps are ISO 8601 UTC with milliseconds (`2026-10-12T08:00:00.000Z`), ids are lower-case 32-hex-digit UUIDv7 strings (no hyphens). The same endpoints behave identically on both storage backends (decision E); anything that depends on `History:Mode` says so and uses the error rules of [design.md §5.2](design.md#52-api-behavior-when-history-is-not-recorded-or-has-expired-design-decided). Implementation notes are in [components/api.md](components/api.md).

Items marked **(addition)** were not in the first version of this document: response shapes the dashboard needs ([components/dashboard.md](components/dashboard.md), "API contract gaps") and behaviour the implementation had to decide.

Conventions: response members are camelCase except where listed as snake_case (`next_cursor`, `request_id`, `event_types`, `content_type`, `content_id`, `reply_to`, `store_attachments`, `history_mode`, `expired_at`, `retention_days`). Optional members that have no value are omitted; members typed `... | null` are written as `null`. Unknown members in a response must be ignored by clients. Lists are either a bare array (domains, webhooks, keys, credentials, tenants, certificates, events, attempts, recent events) or `{ "items": [...], "next_cursor": "..." | null }` (messages, suppressions); `next_cursor` is opaque.

## Authentication

- **API clients:** `Authorization: Bearer <api key>` (`egm_<8 character id>_<43 character secret>`). Keys are shown once at creation, stored as SHA-256 digests, scoped to one tenant and to a list of scopes (`send`, `read`, `domains`, `webhooks`, `suppressions`, `keys`). A key of a suspended tenant is refused (`403 tenant_disabled`). A key never reaches `/admin/*`, and naming another tenant in `X-Tenant-Id` is `403 forbidden`.
- **Dashboard:** `POST /api/v1/session` with `{ "user": "...", "password": "..." }` sets an HttpOnly, `SameSite=Strict` cookie `eggmail_session` (`Secure` unless the request is plain HTTP from a loopback peer; `Api:CookieSecure`) and returns `{ user, role, tenantId }`. The cookie holds a random secret; the server keeps only its SHA-256 digest and the session (absolute lifetime 12 h, ended after 2 h without use; `Api:SessionLifetime` and `Api:SessionIdleTimeout`). Mutating requests (`POST`, `PUT`, `PATCH`, `DELETE`) with a cookie must carry the `X-CSRF-Token` header returned by `GET /api/v1/me` as `csrfToken`, otherwise `403 forbidden`. Bearer requests need no CSRF token. A new sign-in replaces the session of the cookie it presents. **(addition)** `DELETE /api/v1/session` signs out (idempotent: `204` even without a session; with a live session it needs the CSRF token).
- **Roles:** `admin` (all tenants; selects the tenant for tenant endpoints with the `X-Tenant-Id` header: missing is `400 validation_failed` with field `X-Tenant-Id`, unknown is `404`) and `tenant` (one tenant; a different `X-Tenant-Id` is `403`). `/admin/*` needs the admin role.
- `GET /api/v1/me` returns `{ user, role, tenantId, tenantName, csrfToken, authenticatedBy: "session" | "api_key", scopes? }` (**addition**; `csrfToken` is null for API keys).
- Failed logins are rate limited per client address and per user name (10 failures in 15 minutes lock that address or user for the rest of the window: `429 rate_limited` with `Retry-After`; user names are normalized like the lookup, so padding or case does not give a new budget, and a successful sign-in clears only that user's count, never the address's) and share the counters with SMTP AUTH, so an attacker does not get a fresh budget per port. Unknown users and wrong passwords answer identically (and cost the same time).
- **Tenant isolation:** every query is keyed by the tenant the request resolved to. A resource of another tenant is indistinguishable from one that does not exist (`404`), for every verb.

## Errors

RFC 9457 problem details (`application/problem+json`): `{ "type", "title", "status", "detail", "code", "request_id", ... }`. `type` is `https://eggmail.example/problems/<code>` (a placeholder, no domain is registered). `request_id` (`req_` + 16 hex digits) is also sent as `X-Request-Id` on every response. Responses are `Cache-Control: no-store`. Stable `code` values:

| code | status | meaning |
|---|---|---|
| `unauthorized` | 401 | missing, malformed, unknown or revoked credentials, or an ended session (`WWW-Authenticate: Bearer`) |
| `forbidden` | 403 | wrong role or scope, missing/invalid CSRF token, wrong `X-Tenant-Id` |
| `not_found` | 404 | unknown resource or path |
| `validation_failed` | 400 | `errors: [{field, message}]`; field names are request member names, `name[i]` for array elements, `a.b` for nested members, or a header/query name; unknown request members, malformed JSON and wrong types are reported the same way |
| `rate_limited` | 429 | with `Retry-After` (seconds): failed logins, "Verify now", a busy server |
| `domain_not_verified` | 403 | the From domain is not registered to the tenant, is pending/failed, or sending is paused; `reason` carries the specific cause (`sender_domain_not_registered`, `sender_domain_not_verified`, `sender_domain_verification_failed`, `sending_paused`) |
| `recipient_suppressed` | | reserved; suppressed recipients are accepted and recorded as `suppressed` |
| `payload_too_large` | 413 | request body or message over the limit |
| `idempotency_conflict` | 409 | the `Idempotency-Key` was used with a different request |
| `history_not_recorded` | 410 | `History:Mode=StatsOnly` (with `history_mode: "StatsOnly"`) |
| `body_expired` | 410 | content past `Content:RetentionDays` (with `expired_at`, `retention_days`) |
| `message_not_found` | 404 | unknown id, or older than `Retention:MetadataDays` |
| `attachments_not_stored` | 409 | resend of a message whose attachments were not kept |
| `not_ready` | 503 | storage (a `StorageUnavailableException` from the provider), the switch engine or ACME not available; `Retry-After: 5` |
| `query_too_slow` | 503 | **(addition)** a message search or statistics query ran past the database's statement timeout (`Storage:Postgres:ReadOnlyStatementTimeoutSeconds` on the read-only role); no `Retry-After`: narrow the query (shorter time range, more filters) |
| `conflict` | 409 | **(addition)** the request conflicts with the current state (rotation in progress, switch step in the wrong state, duplicate upload, ...) |
| `tenant_disabled` | 403 | **(addition)** the tenant is suspended |
| `content_not_recorded` | 410 | **(addition)** the content of the message was never recorded (`Content:Mode=None`) |
| `unsupported_media_type` | 415 | **(addition)** the body is not `application/json` |
| `server_error` | 500 | **(addition)** unexpected failure; the detail is generic and the cause is only in the server log, quote `request_id` |

Request bodies are limited (JSON: 1 MiB `Api:MaxBodyBytes`, the two sending endpoints 40 MiB `Api:MaxSendBodyBytes`) and checked while streaming, so an oversized chunked body is also refused.

## Capabilities

`GET /api/v1/capabilities` (no auth needed for the dashboard shell to adapt; cached for a few seconds) returns:

```json
{ "version": "0.1.0", "backend": "sqlite", "history": { "mode": "full" }, "content": { "retentionDays": 7, "storeAttachments": false },
  "limits": { "maxMessageBytes": 26214400, "maxRecipients": 50 }, "warnings": [ { "code": "sqlite_sync_off", "message": "..." } ] }
```

`backend` is `sqlite`, `postgres` (or `memory` in tests). `history.mode` is `full` or `statsonly`. `content.storeAttachments` is the global default and only true when the master switch `Content:AllowAttachmentStorage` is on. The dashboard hides per-message pages only when `history.mode` is `statsonly`, never based on `backend`. `warnings` drives the persistent banner (decision P); `sqlite_sync_off` is shown on every page while it is present. Codes in use: `sqlite_sync_off`, `queue_persistence_memory`, `self_signed_certificate` (only a first-run certificate is active), `certificate_expiring` (14 days), `certificate_expired`.

## Sending

`POST /api/v1/messages` (scope `send`), optional `Idempotency-Key` header (1 to 255 printable ASCII characters):

```json
{ "from": "Name <sender@example.com>", "to": ["a@x.test"], "cc": [], "bcc": [], "reply_to": "r@example.com",
  "subject": "Hello", "text": "plain", "html": "<p>html</p>",
  "headers": { "X-Campaign": "autumn" },
  "attachments": [ { "filename": "a.pdf", "content_type": "application/pdf", "content": "<base64>", "content_id": null } ],
  "store_attachments": false, "tags": ["welcome"] }
```

Response `202`: `{ "id": "<message id>", "status": "queued", "recipients": 1 }` (`recipients` counts distinct addresses). `subject` and at least one of `text`/`html` are required. Validation: the From domain must belong to the tenant and be `verified` (or `temporary_failure`; a subdomain of a registered domain is fine unless it is registered itself), at most 50 recipients in total (`to` + `cc` + `bcc`, `Smtp:MaxRecipients`), total size within `maxMessageBytes` (`413 payload_too_large`), no CR/LF/NUL in subject or headers (rejected, never sanitized), custom headers must not be ones the server owns (`From`, `Sender`, `To`, `Cc`, `Bcc`, `Reply-To`, `Subject`, `Date`, `Message-ID`, MIME and content headers, `Received`, `Return-Path`, `DKIM-Signature`, `Authentication-Results`, ARC, `Resent-*`, `In-Reply-To`, `References`, `X-Mta-*`), attachments are base64, a `content_id` makes the attachment an inline resource. `Bcc` recipients get the message but the header is never written. International addresses are composed with UTF-8 headers and queued as SMTPUTF8. Suppressed recipients are accepted into the response but recorded as `suppressed` when delivery is attempted. `store_attachments` follows the precedence per-send flag, then the tenant setting `Content:StoreAttachments`, then the global default, behind the master switch `Content:AllowAttachmentStorage`. **(addition)** `tags` are validated (at most 10, 1 to 64 characters without control characters; a repeated tag is kept once) and stored with the message's history (`History:Mode=full`; under `statsonly` nothing is stored per message). They are returned by the messages API below and can be searched with `tag`. `/messages/raw` takes no tags.

`Idempotency-Key` (per tenant, remembered 24 h): the same key with the same body returns the original result (`202` with the original id, header `Idempotent-Replayed: true`, nothing new is queued); the same key with a different body (compared by SHA-256 of the request bytes, and the endpoint) is `409 idempotency_conflict` and nothing is queued. A request that is refused (validation, unverified domain) does not use up the key.

`POST /api/v1/messages/raw` accepts `{ "from", "to": [...], "raw": "<base64 RFC 5322 message>", "store_attachments"? }` for pre-built (for example already DKIM-signed) mail; bare LF line endings are normalized to CRLF; the header From must be a verified domain of the tenant, exactly as for composed mail. Both endpoints go through the same submission service as SMTP, so limits and sender policy are identical. The number of send bodies held in memory at once is bounded (`429 rate_limited` when the server is busy).

## Messages (`read` scope; per-message history, `History:Mode=full`)

- `GET /messages?recipient=&sender=&subject=&status=&tag=&from=&to=&limit=&cursor=` → `{ items: [MessageSummary], next_cursor }`, newest first, `limit` 1 to 200 (default 50). `recipient` and `sender` match exactly (case-insensitive), `subject` is a substring, **(addition)** `tag` matches one whole tag exactly (case-sensitive, at most 64 characters), `from`/`to` are `[from, to)` timestamps. **(addition)** `MessageSummary` = `{ id, receivedAt, subject, from, recipients: [..], recipientCount, status, size, tags: [..] }` (`tags` is empty for a message sent without tags); `from` is the envelope sender; `recipients` holds at most 5 addresses (with `recipientCount` for the rest) and is empty when the storage provider cannot list them cheaply.
- `GET /messages/{id}` → `{ id, tenantId, receivedAt, subject, from, recipients: [..], recipientCount, status, size, tags: [..], content: { state: "available"|"body_expired"|"not_recorded", text?, html?, attachments: [{ filename, content_type, size, content_id }], truncated }, rawRetained }`. `status` is one of `queued`, `delivered`, `deferred`, `partial`, `bounced`, `expired`, `suppressed`, `cancelled`, `complained` and is the aggregate over recipients. **(addition)** A bounce or complaint that arrives after the remote server accepted the message (an asynchronous report to the bounce address) is attached to the message: a `bounced` or `complained` event appears in `/events` (with the reported recipient, enhanced code and diagnostic) and a `delivered` message becomes `bounced` (`partial` when it had several recipients) or `complained`. The message is found by the `Message-ID` in the returned headers within the tenant named by the signed bounce address, so a bounce that does not quote it (or quotes a message this server did not send) is only suppressed and published as a webhook. Nothing is attached under `statsonly`.
- `GET /messages/{id}/events` → `[ { id, type, at, recipient, smtpCode, enhancedCode, message, mxHost, route, tls } ]` (types: `queued`, `delivered`, `deferred`, `bounced`, `expired`, `suppressed`, `cancelled`, `complained`, `aborted_by_switch`, `possible_duplicate`; **(addition)** `bounced` and `complained` can also come from an asynchronous report, without a delivery attempt behind them). **(addition)** `tls` is `null` or `{ used, version?, cipher?, verified, policy?, peerSubject?, peerIssuer?, peerSha256?, policyErrors?, startTlsAdvertised, plaintextFallback }`.
- `GET /messages/{id}/content` → `{ state, text?, html?, attachments, truncated }`; `410 body_expired` once past `Content:RetentionDays`; **(addition)** `410 content_not_recorded` when content was never recorded.
- `POST /messages/{id}/resend` → `202` `{ id, recomposed }` with the new message id; from retained raw (`recomposed: false`), or re-composed from the stored text/html for attachment-free messages (`recomposed: true`; headers are not byte-identical, the From display name is lost and only a single recipient appears in `To`, so Bcc'd recipients are never revealed); `409 attachments_not_stored`; `410 body_expired`; **(addition)** `409 conflict` when the stored content was truncated or the message has no sender. **(addition)** Resending needs the `send` scope (it sends mail), not `read`; the sender policy runs again.
- Under `History:Mode=statsonly` all of the above return `410 history_not_recorded`.

## Domains (`domains` scope)

- `GET /domains`, `POST /domains` `{ "name": "mail.example.com" }` (`201`; creates an RSA-2048 DKIM key whose private half is stored protected, and returns the records), `GET /domains/{id}`, `DELETE /domains/{id}` (`204`). Names are normalized (lower case, A-labels, no trailing dot); a name must be a host name with at least two labels (no IP addresses, no underscore); a registered name (by any tenant) is `400 validation_failed` on `name`; at most 200 domains per tenant (`Api:MaxDomainsPerTenant`).
- Domain object: `{ id, name, status: "pending"|"verifying"|"verified"|"temporary_failure"|"failed", sendingPaused, createdAt, lastCheckedAt, nextCheckAt, lastError, returnPathVerified, records: [ { type, host, value, ttl, purpose: "dkim"|"return_path"|"spf"|"dmarc", status: "ok"|"missing"|"invalid"|"pending", found?, expected, required } ], dkim: { selector, publicKey, active, createdAt, retiredAt }, dkimKeys: [..] }`. **(addition)** `createdAt`, `returnPathVerified`, `records[].required` (only required records decide verification; SPF and DMARC are advice) and `dkimKeys` (every key, oldest first); `dkim` describes the newest key, and `active: false` means it does not sign yet (see rotation). `records[].status` and `found` come from the last check of the domain, stored per record, so a restart or another replica shows the same result; a DNS outage during a check keeps the previous result of the records it could not look up. Only a domain that has never been checked since results were stored (a verified domain from before schema version 4) shows its required records as `ok` and the rest as `pending` until its next check. Checks and key rotations of one domain are serialized across all replicas by a lease in the config store (`Verify now` answers `429` and a rotation `409` while another replica holds it; a replica that dies mid-check frees the domain after five minutes).
- State machine (design §8): the first check is 90 s after creation, then every 90 s for 15 minutes, every 15 minutes for 24 hours, then hourly; verified domains are checked daily. `Pending`, `Verifying` and `Failed` block sending (`403 domain_not_verified`); `TemporaryFailure` keeps sending. A verified domain moves to `temporary_failure` after two consecutive failed checks (the first is confirmed after 15 minutes), and to `failed` with `sendingPaused: true` after 72 hours of that; when the records return it is `verified` again and the pause is lifted. A DNS outage (SERVFAIL, timeout) never changes the state. `lastError` names the first missing or wrong required record.
- `POST /domains/{id}/verify` (rate limited to once per 30 s per domain, counting scheduled checks: `429 rate_limited` with `Retry-After`) → the domain object after an immediate check.
- `POST /domains/{id}/dkim/rotate` publishes selector N+1 (`egg<YYYYMM>`, with `-2`, `-3`, ... when that month's name was used; names are never reused). The new key is listed in `records` and `dkimKeys` as advice and does **not** sign yet: the current key keeps signing, so a record that is not published yet cannot break DKIM. When a check finds the new record in DNS, signing switches to it and the old key is retired but stays published (and checked as advice) for 7 days, then drops out of `records`. Rotating while a rotation is pending is `409 conflict`. **(addition)** `DELETE /domains/{id}/dkim/rotate` cancels a pending rotation (the unused key is deleted, `404` when none is pending; the selector name is not reused).

## Suppressions (`suppressions` scope)

`GET /suppressions?cursor=&limit=` (`limit` 1 to 500, default 50; ordered by address) → `{ items: [{ address, reason, createdAt, source }], next_cursor }`, `POST /suppressions` `{ "address": "...", "reason": "manual" }` (`201`, or `200` when the address was listed and is updated), `DELETE /suppressions/{address}` (`204`, `404` when not listed). Reasons: `manual` (default), `bounce`, `complaint`, `unsubscribe`. Addresses are lower-cased.

## Webhooks (`webhooks` scope)

- `GET/POST /webhooks`, `GET/PATCH/DELETE /webhooks/{id}`. Create: `{ "url": "https://...", "event_types": ["message.delivered", ...] }` → `201` with the signing secret once (`secret`, `whsec_...`). **(addition)** Object: `{ id, url, event_types, enabled, disabledReason, disabledAt, createdAt, secretRotationPending, secret? }`. Event types: `message.delivered`, `message.deferred`, `message.bounced`, `message.expired`, `message.suppressed`, `message.complained`, `webhook.endpoint.disabled`, `webhook.test`, or `*` for all. `PATCH` takes `url`, `event_types`, `enabled` (re-enabling clears the disabled reason). At most 50 endpoints per tenant (`Api:MaxWebhooksPerTenant`). **(addition)** `message.bounced` and `message.complained` that come from an asynchronous report have `data` `{ message_id, recipient, original_message_id, enhanced_code, response, feedback_type, asynchronous: true }`: `message_id` is this server's id of the message when the report could be attached to it (see `/messages`) and `null` otherwise; `original_message_id` is the `Message-ID` header the report quoted.
- HTTPS only unless the operator allows http (`Webhooks:AllowHttp`); the SSRF guard refuses localhost, non-public addresses (loopback, private, link-local including `169.254.169.254`, unique-local, multicast) and credentials in the URL at registration, and again for every resolved address at delivery. Internal endpoints need the tenant allowlist (**addition**: tenant setting `Webhooks:AllowedNetworks`, a comma separated CIDR list that **only an administrator can set**, so a tenant cannot lift its own protection).
- `POST /webhooks/{id}/rotate-secret` returns the endpoint with the new secret; deliveries are signed with the new and the previous secret (at most two) until the old one is removed with **(addition)** `DELETE /webhooks/{id}/previous-secret` (`204`, `404` when no rotation is pending). `POST /webhooks/{id}/test` queues a `webhook.test` event to that endpoint whatever it subscribes to (`202` `{ outboxId, status }`; `409` when the endpoint is disabled).
- `GET /webhooks/{id}/attempts?limit=` (1 to 200, default 50) → the attempt log, newest first: `[ { id, outboxId, at, status, durationMs, errorClass, snippet } ]` (status null on a network error, snippet ≤ 1 KB).
- `POST /webhook-events/{outboxId}/replay` re-queues a finished or failed delivery of the tenant (`202` `{ outboxId, status }`; `404` for a pending, unknown or foreign one).

## Credentials (`keys` scope)

`GET/POST/DELETE /api-keys` (create returns the key once as `key`; **(addition)** object `{ id, name, prefix, scopes, createdAt, lastUsedAt, key? }`; `DELETE` revokes, revoked keys are no longer listed; a key can only create keys with scopes it has itself; at most 100 active keys per tenant, `Api:MaxApiKeysPerTenant`) and `GET/POST/DELETE /smtp-credentials` (SMTP AUTH users for this tenant; creating one needs the `send` scope as well as `keys`, because the credential can send mail; create takes `{ "username": "..." }` (3 to 64 of `A-Za-z0-9._@-`, unique on the server) and returns a generated password once as `password`; object `{ id, username, createdAt, enabled, password? }`; at most 100 per tenant, `Api:MaxSmtpCredentialsPerTenant`). Both lists are bare arrays.

## Statistics (`read` scope)

`GET /stats?from=&to=&granularity=hour|day&domain=` → **(addition)** `{ granularity, rows: [...] }` with rows `{ period, sendingDomain, recipientDomain, accepted, delivered, deferred, hardBounce, softBounce, expired, complained, rejected, suppressed }` per period start, sending domain and recipient domain bucket. Defaults: `to` now, `from` 24 h (hour) or 30 days (day) earlier; at most 35 days at hour granularity and 800 days at day granularity; more than 50,000 rows is `400 validation_failed` (narrow the range or filter by `domain`). `GET /stats/recent-events?limit=` (1 to 1000, default 50) → the content-free ring, newest first: `[ { at, type, recipientDomain, tenantId, code? } ]`. Available on every backend and in both history modes.

## Settings

- **(addition)** `GET /settings` (scope `read`) and `PUT /settings` (a signed-in user or an admin acting on a tenant; API keys cannot change settings) for the tenant: `{ items: [{ key, value, type: "string"|"number"|"boolean"|"enum", options?, description, locked, requiresRestart }] }`; `PUT` takes `{ "values": { "key": value } }` and returns the same shape; an invalid or locked key fails the whole update with `validation_failed` and `field` = the key. Tenant settings: `Content:StoreAttachments` (boolean; locked when the operator has not allowed attachment storage; until a tenant sets it the global default `Content:StoreAttachments` applies, and a tenant that sets it to false overrides a global true; SMTP submissions follow the same tenant setting and have no per-send flag), `Webhooks:AllowedNetworks` (string, administrators only: locked for tenant users), `Smtp:MaxRecipients` (read-only).
- **(addition)** `GET/PUT /admin/settings` for the global settings with the same shapes: `History:Mode`, `Retention:MetadataDays`, `Webhooks:OutboxRetentionDays`, `Webhooks:AttemptLogDays`, `Stats:HourlyRetentionDays`, `Stats:DailyRetentionDays`, `Content:RetentionDays` (6 to 30), `Content:StoreAttachments`, `Content:AllowAttachmentStorage`, `Queue:MaxLifetimeDays`, and the deployment-only `Smtp:MaxMessageSize`, `Smtp:MaxRecipients`, `Sqlite:SyncMode`. A value is `locked: true` when it is deployment-only or the deployment configuration (environment, mounted files, command line) sets its key (decision N). Retention values accept `0` (keep forever, decision 28) except `Content:RetentionDays`. Values are stored in the config store (the stored-settings layer, decision N layer 4) and are applied **at the next start**: every global setting is returned with `requiresRestart: true`, and none is applied live (a change of `History:Mode` or a retention value reopens the storage options at the next start). The per-tenant settings `Sending:PerHour`, `Sending:PerDay` and `Webhooks:AllowedNetworks` are live (refreshed within 30 seconds, and 30 seconds respectively; see `SendingConfigurator` and the webhook allowlist cache).

## Admin (role `admin`)

- `GET/POST/PATCH /admin/tenants`: **(addition)** tenant `{ id, name, slug, status: "active"|"suspended", createdAt, storeAttachments }`; `POST { name }` creates an active tenant with a unique slug; `PATCH { name?, status? }`. Suspending stops the tenant's keys, sessions and sending at once.
- `GET /admin/status` → **(addition)** `{ version, backend, historyMode, uptimeSeconds, queue: { depth, deferred, oldestDueAt }, storage: { healthy, detail, warnings }, certificates: [{ subject, notAfter, source }], pressure?, switch: { state } }`. `pressure` (`writerQueueDepth`, `writerQueueOverThresholdSeconds`, `commitP99Ms`, `advisory`) is advisory only (decision C) and present when the backend measures it.
- `GET /admin/certificates` → `[ { id, name, subject, issuer, san, notBefore, notAfter, source: "acme"|"upload"|"self_signed", active, thumbprint } ]`. `POST /admin/certificates` uploads `{ certificatePem, privateKeyPem }` (leaf first, chain allowed, unencrypted key) or `{ pfxBase64, pfxPassword }` (`201`); the key must belong to the certificate, which must be currently valid; the private key is stored protected; the same certificate twice is `409`; an upload deactivates the first-run self-signed certificate. `POST /admin/certificates/acme` `{ "domains": [...] }` (1 to 10 names, `*.` wildcards allowed) starts an order in the background (`202` `{ status: "pending", message }`; `409` while one runs; `503 not_ready` when ACME is not configured). **(addition)** `GET /admin/certificates/acme` lists the renewal state (`certificateName, status, lastAttemptAt, nextAttemptAt, failures, lastError`); certificates requested this way are renewed with the configured one.
- `POST /admin/maintenance/run` starts the storage maintenance in the background (`202` `{ status: "started"|"running" }`); **(addition)** `GET /admin/maintenance` → `{ running, startedAt, finishedAt, error, reports: [{ job, durationMs, rowsAffected, detail }] }`.
- Backend switch (decision 14, design §4.6), never automatic: `POST /admin/storage/switch/preflight` `{ "to": "postgres"|"sqlite", "target": {...}, "include": ["queue","history"], "mode": "drain"|"quiesce" }`, `POST .../start` (adds `exportPassphrase`, at least 12 characters, and `confirmation`, the phrase `switch to <postgres|sqlite>`), `GET /admin/storage/switch` (state, progress, report; states: `none`, `draining`, `quiescing`, `fenced`, `exporting`, `importing`, `verifying`, `verified`, `confirmed`, `active`, `finalized`, `rolled_back`, `failed`; `orchestratorManaged` is known from the start, `cutoverPatch` is created by `activate` with `kind` `patch` or `bootstrap`), `POST .../confirm`, `.../activate`, `.../rollback`, `.../finalize`. The API validates the request and delegates to the switch engine (`IStorageSwitchService`); the same engine backs `mta migrate-storage`. `IStorageSwitchService` is implemented over `IStorageSwitchEngine` (`Mta.Storage.Portability`, see [components/switch.md](components/switch.md)). Without a configured target status reads `{ state: "none", available: false }` and every operation answers `503 not_ready`. While a switch drains, quiesces or fences the instance, mail submission answers `503` with `Retry-After` (`SwitchRuntimeState.AcceptingApi`) and the banner is shown (`SwitchRuntimeState.Banner`). The shapes of the request and of the responses (`PreflightReport`, `SwitchStatus`) are those of [components/dashboard.md](components/dashboard.md) item 13; a step in the wrong state is `409 conflict`.

### Relay routes and TLS policies (role `admin`, **addition**)

Both are server-wide records of the config store (no tenant: a relay changes the sending IP, SPF and bounce path of every tenant whose recipients it carries, and a TLS level applies to a destination whoever sends to it), so only the admin role reaches them. A tenant user, an API key or an anonymous caller gets `403 forbidden` or `401 unauthorized`; a session needs the CSRF token for every change. Every successful change writes one structured log line (who, what, never a secret); the API has no audit table. The delivery engine of the process that served the request reloads both lists at once; other replicas, and a process whose notification was lost, pick the change up within the engine's refresh interval (30 s). A change applies to the next delivery attempt, which includes the retries of mail that is already queued. The records are part of the config part of a backend-switch bundle.

**Relay routes** (design §7.2), `/admin/relay-routes`:

- `GET /admin/relay-routes` (bare array, by priority then name), `POST` (`201`), `GET /admin/relay-routes/{id}`, `PATCH` (any subset of the create members), `DELETE` (`204`). An unknown id is `404 not_found`.
- Object: `{ id, name, host, port, tlsMode, userName | null, hasPassword, priority, enabled, domains: [..], warnings: [..] }`. **The password is write-only**: it is accepted in `password` (create, `PATCH`), protected with Data Protection (purpose `EggMail.Secrets.RelayPassword.v1`) before it is stored, and never returned or logged; `hasPassword` says whether one is stored. `warnings` are advice computed from the record (a certificate that is not validated while credentials are set, plaintext, a `*` route).
- Create `{ name, host, port?, tlsMode?, userName?, password?, priority?, enabled?, domains }`: `name` 1 to 64 of `A-Za-z0-9._-` starting with a letter or digit, unique ignoring case, not `direct` (the name of direct delivery; the name is recorded as the `route` of every delivery that used the relay); `host` a host name (lower-cased, A-label, no trailing dot) or an IP address; `port` 1 to 65535 (default 587, 465 for `implicit`); `tlsMode` `none`, `starttls`, `required`, `verify` (default) or `implicit`; `priority` 0 to 1000, default 100, lower numbers are tried first, after direct delivery; `enabled` default true; `domains` 1 to 100 recipient-domain patterns (exact name, `*.suffix` for the domain and everything below it, or `*`; normalized, repeated entries kept once). **A relay is opt-in per domain**: a route is only used for the domains it lists, so an empty list is refused. At most 50 routes.
- `userName` and `password` go together (a password needs a user name and the other way round); credentials are refused with `tlsMode: none` (the password would be sent in plaintext; the client also refuses to authenticate without TLS). A `PATCH` that changes `userName` must send the new `password` (the stored one belongs to the old user); one that only sends `password` replaces it; `removeCredentials: true` deletes both (it cannot be combined with `userName` or `password`); a `PATCH` that makes the mode `none` on a route with credentials is refused.
- TLS modes: `none` no TLS; `starttls` STARTTLS when offered, any certificate, plaintext otherwise; `required` STARTTLS required, certificate **not** validated (encryption only); `verify` STARTTLS required, chain and host name validated; `implicit` TLS from the first byte (port 465), chain and host name validated. Use `verify` or `implicit` whenever there is a password.
- How the chain works (design §7.2): direct MX delivery first, then the enabled relays whose `domains` match, by `priority`. The next route is tried after a connect timeout or refusal; a 4xx, a TLS failure or a dropped connection retries the same route later; a 5xx is final and never rerouted. Each route has a circuit breaker with a cooldown. Every delivery records the route that carried it (`route` in `/messages/{id}/events`).

**TLS policies** (design §7.3), `/admin/tls-policies`:

- `GET` (bare array, ordered by pattern), `POST` (`201`), `GET /{id}`, `PATCH`, `DELETE` (`204`).
- Object `{ id, domainPattern, level, warnings: [..] }`; create `{ domainPattern, level }`. `domainPattern` is a recipient domain, `*.suffix` or `*` (normalized as above, unique: a second policy for the same pattern, or moving one onto a taken pattern, is `400` on `domainPattern`); the most specific pattern wins (exact name, then the longest `*.suffix`, then `*`); `level` is `none`, `may`, `encrypt` or `verify`. At most 500 policies. A destination without a policy gets `may`.
- Levels: `none` never uses TLS; `may` uses STARTTLS when offered, accepts any certificate and falls back to plaintext; `encrypt` requires TLS and does not validate the certificate; `verify` requires TLS and a valid certificate for the MX host name. With `encrypt` and `verify` a server that cannot do TLS is retried later and the mail finally expires; nothing is sent in plaintext.
- **Interplay with MTA-STS and DANE** (as implemented by `OutboundTlsPolicyResolver`; [components/tls.md](components/tls.md)): level `none` switches TLS off and **MTA-STS and DANE are not consulted** (an explicit operator override: mail can go in plaintext even where the destination publishes an enforcing policy; the response carries a warning). For every other level a usable, DNSSEC-validated DANE policy of the MX always wins, MTA-STS is ignored for that MX, and a DANE failure is never overridden by MTA-STS (the MX is skipped and the mail deferred). Without DANE, an MTA-STS `enforce` policy requires an allowed MX, TLS and a valid certificate whatever the level; in `testing` mode the level is the floor (`encrypt` still requires TLS, `verify` still validates). The level decides only the destinations that publish neither, so `may`, `encrypt` and `verify` can only make a destination stricter than what it publishes, never weaker. DANE needs `Dns:TrustAuthenticatedData` behind a validating resolver; without it only MTA-STS and the level apply.

## Operational endpoints (no `/api/v1` prefix)

`GET /healthz` (liveness, always cheap), `GET /readyz` (readiness; `503` with `Retry-After` when the storage backend is down; response `{ status, warnings }`, internals are never included), `GET /metrics` (Prometheus text exposition of the `Mta.*` meters, answered only to loopback and private networks (`Api:MetricsAllowedNetworks`) and never to a request that carries `X-Forwarded-For`/`Forwarded`; `404` when switched off).

## Compatibility

Additive changes only within `v1`. Unknown JSON members in requests are rejected with `validation_failed`; unknown members in responses must be ignored by clients.
