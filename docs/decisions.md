## Product and goals

1. EggMail is an open-source, self-hosted outbound email server (SMTP ingress, HTTP API, delivery tracking, dashboard) from eggspot. Primary goal: the fastest SMTP server, claimed only after reproducible measurement ([benchmarks.md](benchmarks.md)).
2. .NET 10 LTS (supported to 2028-11-14). Docker deployable.
3. **Two storage backends, feature-identical** (revised by E; the earlier "Lite = statistics only" is **SUPERSEDED**): PostgreSQL and SQLite, behind storage interfaces, with a shared core. **SQLite is the default backend** (decision Q). "Lite" (SQLite) and "Full" (PostgreSQL) are friendly names for the two backends' default shapes with identical behavioural defaults, including `History:Mode=Full` (decisions J and 29); any combination is allowed. Performance is a permanent first-class goal on **both** backends: the SQLite backend is engineered for large, high-throughput workloads and is not treated as a toy (decision 27).

## Build boundary

4. Hand-written, BCL-only SMTP stack: SMTP server and client (including BDAT/CHUNKING, full SMTPUTF8, PIPELINING, SIZE, 8BITMIME, ENHANCEDSTATUSCODES, STARTTLS, AUTH PLAIN/LOGIN), MIME, DKIM sign and verify (RSA-2048 only), SPF, DMARC, DSN/ARF, DNS client, MTA-STS, TLS-RPT, DANE. ARC is optional and deferrable. Enforced by CI: those assemblies have no package references.
5. Libraries allowed elsewhere: Npgsql + EF Core, Microsoft.Data.Sqlite, Certes (ACME), OpenTelemetry with OTLP, Data Protection, dashboard frontend stack, tests (MimeKit and MailKit as oracles only).
6. DANE uses a local validating resolver (Unbound on loopback). This is the one carve-out from "no external binaries".
7. **A single image** (decision S, [release.md](release.md)), chiseled with ICU (the `-extra` variant) plus a startup Unicode self-test. It runs out of the box on the SQLite backend with one volume at `/data`; PostgreSQL is selected by configuration in the same image.

## Storage

8. PostgreSQL backend: Postgres only, via EF Core only. One database, one schema, three roles (owner, runtime, read-only). Minimum PG 16, default `postgres:17`. Managed HA is a deployment prerequisite; `451` during a database outage is accepted.
9. Tables: live queue unpartitioned and small; events and content day-partitioned; retention is partition drop (`DETACH … CONCURRENTLY`, then `DROP`), created ahead by an in-app job under a transaction-level advisory lock. Claim with native `FOR UPDATE SKIP LOCKED … RETURNING` through `SqlQuery<T>`. A pure-LINQ `ExecuteUpdate` claim is the test fallback.
10. Migrations: `Auto` by default (EF 9+ takes a database-wide lock), or `Never` plus `mta migrate-db` and a script. Two connection strings: schema owner and runtime.
11. No blob store. FS, S3 and R2 providers are dropped. R2 is removed. An `IMessageBodyStore` interface remains for a possible later provider.
12. Content (`History:Mode=Full`, on either backend): subject + text + html stored by default for 7 days (6–30). Raw message stays verbatim in `message_spool` until all recipients are final. Attachments are not stored unless enabled per tenant or per send (then raw is moved to `message_raw_retained`). Resend is available from retained raw; attachment-free messages can be re-composed. Event metadata kept 30 days.
13. SQLite backend (revised by E; the earlier "Lite mode: statistics only, no per-message history" is **SUPERSEDED**): SQLite in separate files (`queue.db`, `stats.db`, `config.db`, plus `history.db` when `History:Mode=Full`, which is the default), single node, one replica, local volume only, multi-tenant like every backend. Characteristics, not missing features: single-writer ceiling, no partition drop (retention is batched `DELETE` plus `incremental_vacuum`), no built-in HA. Default `synchronous=OFF` for the data files (**owner-decided**; `config.db` stays `Full`, see F): **process-crash-safe, not power-loss-safe**. `250` means the data was handed to the OS, not fsynced; an OS crash or power loss can corrupt the database (per the SQLite docs) and lose all queued mail, including mail already acknowledged. No acknowledgement setting is required; EggMail warns loudly instead (startup log, persistent dashboard banner, metric/health detail, README; decision P). Knobs: `Sqlite:SyncMode = Off | Normal | Full`, `Sqlite:ConfigSyncMode`, `Sqlite:QueuePersistence = Persistent | Memory` (renamed from `QueueDurability`; "durable queue" is retired). Startup integrity check, quarantine of a corrupt file, start empty with an alert, optional `VACUUM INTO` backups. Behavioural defaults are identical to the PostgreSQL backend (decision 29, J). Statistics and the recent-events ring exist on every backend. Webhooks with a persisted outbox. No throughput cap.
14. **Backend switching is manual only, never automatic, and symmetric** (owner-decided; **SUPERSEDES** the earlier "Lite → Full guided switch" and the earlier "Full → Lite unsupported / config-only export"). One portable, versioned bundle (NDJSON plus manifest); a CLI (`mta migrate-storage --to postgres|sqlite`) and a guided dashboard action sharing one engine; steps preflight, drain/quiesce, export, import, verify, confirm, activate, finalize; source fenced and kept read-only until finalized; rollback before activation, reverse switch after. Config, certificates/ACME state, suppressions, webhook endpoints and stats always move; queued mail moves with `--quiesce` (or is simply drained with `--drain`, the safe default); per-message history moves when `History:Mode=Full` on both sides (streamed, resumable, skippable, **in v1**, decision I). Secrets are re-protected through Data Protection (decision H). See [design.md §4.6](design.md#46-switching-backends-manual-and-symmetric).
15. Two EF providers: one `DbContext`, separate migrations assemblies, provider-specific hot-path stores, a shared `IStatsStore` using `ON CONFLICT` upserts.

## Webhooks

16. Standard Webhooks signing, retry schedule immediate/5 s/5 m/30 m/2 h/5 h/10 h/10 h, 15 s timeout, 410 disables, disable after 5 days of failure, SSRF guard (validate resolved IPs, no redirects, HTTPS default), 7-day default outbox and attempt-log retention, configurable, `0` = unlimited (decision B).

## Network and TLS

17. Ports (each switchable): 587 STARTTLS, 465 implicit TLS, 2525 STARTTLS on by default; 2587 and 2465 off; port 25 bounce role only; plain only on loopback or internal networks. Container ports are high (5587, 4465, 2525, 2526) and mapped outward. Dashboard on 8080 (HTTP, probes) and 8443 (HTTPS), optionally published as 443.
18. Outbound: direct MX on port 25; relay fallback chain on 587, 465 or 2525 is opt-in per domain, with every delivery recording which route was used.
19. TLS: one certificate store **in the database** (config store, both backends; decision K) serving SMTP and the dashboard through an own `ServerCertificateSelector`; TLS 1.2 minimum; certificate hot reload by polling the database, with an optional file/environment override; ACME with Certes, DNS-01 default (Cloudflare first); outbound opportunistic by default with per-domain policy, MTA-STS enforce, TLS version, cipher and peer certificate recorded per attempt.
20. Domain verification: DKIM TXT with RSA-2048 (CNAME delegation optional later), return-path CNAME, SPF include optional, DMARC informational. State machine: the consolidated record is truncated after "State machine"; the proposed machine from the earlier domain-verification research is summarized in [design.md §8](design.md#8-domain-verification) and needs confirmation.

## Secrets and security

21. API keys shown once and stored as SHA-256 digests; SMTP auth PLAIN/LOGIN only; DKIM keys and the Data Protection key ring wrapped with a certificate or KMS. Encryption at rest is a storage-layer responsibility (envelope encryption deferred behind an interface).
22. Security review is in-house (STRIDE threat model, ASVS L2/L3, fuzzing, smuggling and STARTTLS-injection suites, port pen-tests, DoS tests, container hardening, cross-review and a red-hat week). An external audit is recommended before first production-critical use.

## Deployment

23. SQLite backend (the default): one container, one volume at `/data`, one replica. PostgreSQL backend: app + managed Postgres, via compose or Kubernetes; replicas above 1 are safe (no local blobs). Health: `--healthcheck`, liveness separate from readiness.

## Performance and plan

24. Pipelines-based server, zero-byte reads for idle connections, group-commit writers; durable and non-durable results always reported together, with the two backends benchmarked separately on the identical feature set (the SQLite default `synchronous=OFF` is a non-durable configuration); Postfix, KumoMTA and Haraka as baselines on the same hardware.
25. Estimate: about 279 engineer-weeks central (about 206–410): about 21 months with 4 engineers, about 38 with 2 ([plan.md](plan.md)). The +15 over the earlier 264 is new author estimates: Lite corruption handling, the symmetric switch engine with quiesce, resumable history migration and Data Protection bundle protection, history stores on SQLite, orchestrator-aware cutover, certificates in the database, and the release automation (+0.5).
26. Cut order: as listed in [plan.md](plan.md#cut-order).
27. **Design principle:** performance optimization is a permanent first-class goal on both backends. The SQLite backend is engineered to perform well for large and high-throughput workloads, not treated as a toy. Benchmarks cover both backends separately with identical feature sets ([benchmarks.md](benchmarks.md)).
28. **Retention convention:** a retention value of `0` means "keep forever"; negative values are invalid. Allowed for webhook outbox/attempt log, `Retention:MetadataDays`, `Stats:HourlyRetentionDays` and `Stats:DailyRetentionDays` (with documented disk-growth cost and manual cleanup). **Not** allowed for `Content:RetentionDays`, which stays 6–30 (**OWNER-DECIDED**, decision O; floor: must outlive the 5-day queue lifetime; ceiling: personal-data and storage bound). Suppressions have no expiry. Same knobs on both backends; only the cleanup mechanism differs. Analysis in [design.md §5.1](design.md#51-retention-knobs-and-unlimited-retention).
29. **Storage backend and history level are orthogonal settings** (owner correction E): `Storage:Backend = Sqlite | Postgres` (default `Sqlite`, decision Q) and `History:Mode = StatsOnly | Full`. **Defaults are identical on both backends (decision J): `History:Mode=Full`**, with `StatsOnly` one setting away as the lightweight option; any combination is allowed. No feature is gated on the backend: the dashboard shows the same pages on both, and per-message lookups under `StatsOnly` return `410 Gone` `history_not_recorded` (decision M). Backend differences are documented as characteristics ([design.md §4.2](design.md#42-backend-characteristics-not-feature-differences)).
30. **Portable bundle and effective settings:** switching backends records the *effective* values of all settings in the bundle and writes them explicitly into the target, so behavior never changes silently; secrets are re-protected through Data Protection and never written in clear; the importer refuses a non-empty target that does not carry the same switch id.
31. **Secrets in the bundle** use Data Protection with a bundle-specific key ring protected by a passphrase-protected throwaway certificate; the target re-protects under its own ring (decision H).
32. **Quiesce semantics:** stop accepting (`421`/`503`), wait for in-flight deliveries up to `Switch:QuiesceTimeoutSeconds` (default 30), then requeue what remains with the same message id and retry state preserved and a `possible_duplicate` flag/event (decision R); durable source fence, transfer marks, ids and idempotency keys preserved, target does not dispatch until activated, rollback before activation (decision I).
33. **History migration** is in v1: chunked, checksummed, resumable, skippable, and can backfill after activation; throughput and time are unmeasured.
34. **Certificates and ACME state in the database**, DP-protected, with a renewal lease and database polling for hot reload (decision K).
35. **History API status:** `410` for not recorded or expired content, `404` for unknown, `200` with `body_expired` for the message resource (decision M).
36. **Configuration precedence and cutover** under orchestrators (decision N).
37. **Default backend and single image:** `Storage:Backend` defaults to `Sqlite`; one Docker image serves both backends (decisions Q, S).
38. **Loud warnings for `synchronous=OFF`:** startup log warning, persistent dashboard banner, metric and health detail, README text; no acknowledgement gate (decision P).
39. **Release plan:** [release.md](release.md): GHCR `ghcr.io/eggspot/eggmail`, tags `vX.Y.Z`, `X.Y`, `latest`, `nightly`; `GITHUB_TOKEN` with `packages: write`; SBOM and provenance; GitHub Release with changelog and checksums; the package must be made public once by hand (decision S).
40. **Funding:** policy draft in [funding.md](funding.md); no feature gating or priority code for sponsors; other platforms (Open Collective, Ko-fi, Liberapay, custom links) are added to `FUNDING.yml` only when the owner names them (decision T).

## Implementation decisions (DESIGN-DECIDED during implementation)

Choices the implementation forced that the design left open. Each can be reversed; the reason is given so a reviewer can judge it. Component details are in `docs/components/`.

41. **Bounce addresses are stateless VERP tokens** `b+<base32>@<bounce domain>` (`Delivery:BounceDomain`): version and key id, tenant id, the first 8 bytes of the sending domain's id, hours since an epoch (24 bits) and a truncated HMAC-SHA-256, with key rotation. The delivery engine uses it as the SMTP envelope sender for mail that is not itself a bounce; the original sender is kept for the bounce message (DSN). Async bounces and complaints are correlated to the tenant by the token only; the body decides which addresses are suppressed. *Reason:* no per-message bounce state, works the same on both backends.
42. **Only a recipient-specific permanent failure suppresses** (`PermanentRecipient` class from the reply classifier, and asynchronous DSNs classified the same way). Sender, policy, content and configuration failures bounce without suppressing. *Reason:* a wrong suppression silently stops mail to a valid address.
43. **Bounce messages (RFC 3464) are generated for SMTP-submitted mail only by default** (`Delivery:GenerateDsnForSmtpSubmissions`); API senders learn through webhooks. The bounce is queued before the failed delivery is recorded (a crash can duplicate a bounce, never lose one).
44. **Local holds are not attempts.** A sending-limit or destination-throttle hold reschedules the delivery without counting an attempt, writing an event or notifying webhooks (`DeliveryAttempt.CountAttempt`). *Reason:* otherwise throttling would advance the retry ladder and spam history.
45. **Events that are not tied to a delivery attempt** (asynchronous bounce, complaint) enter the webhook outbox through `IWebhookOutbox.EnqueueAsync`.
46. **Retry defaults** (not specified by the design): 2 m, 5 m, 15 m, 30 m, 1 h, 2 h, 4 h, then every 4 h until the 5-day lifetime ends, ±10 % jitter; greylisting 5–15 m; throttling at least 10 m. All are options (`docs/components/policy.md`) and unmeasured.
47. **DKIM private keys** are stored as PKCS#8 DER protected with Data Protection (purpose `EggMail.Secrets.DkimKey.v1`); the signing key of a domain is its newest active key, and a sending subdomain signs as its nearest registered parent domain.
48. **The Data Protection key ring is stored in the settings table** (`dataprotection.key.*`) and never deleted, so a backend switch and a restart see the same ring; `Secrets:KeyProtection=Certificate` encrypts it, `None` is development only and logs a warning at startup.
49. **API keys** are `egm_` + 8-character id + `_` + 43-character secret (positional layout; base64url can contain `_`), stored as SHA-256 digests.
50. **System-originated mail** (TLS-RPT reports) uses the empty tenant id and source `System`; it is never answered with a bounce message.
51. **Domain records:** DKIM TXT and the return-path CNAME (`bounce.<domain>` pointing at the operator's bounce domain) decide verification; SPF and DMARC are advice. A DNS failure during a check is a temporary failure and never marks a domain as missing records.
52. **Merge gate without CI:** GitHub Actions is disabled for the repository by the organization, so pull requests are merged after a full local `dotnet test` and review; the workflows are written and unproven ([open-questions.md](open-questions.md)).
58. **Unicode self-test fails fast.** `mta serve` runs the self-test of design section 10 before it opens any storage and exits with code 71 and an actionable message when IDN or normalization give wrong answers (invariant globalization mode, missing ICU); `Startup:RequireUnicodeSupport=false` downgrades it to a warning. `mta self-test` exposes the same test, and the release workflow runs it against the published image. *Reason:* a wrong A-label is silent (the registered sender domain stops matching); a fatal start is cheaper than mail from the wrong identity. The design left "fail" versus "warn" open.
