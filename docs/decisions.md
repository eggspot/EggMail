# Decisions record

Consolidated record of decisions for EggMail (as of 2026-10-12, after owner decisions A–G). Rationale and detail are in [design.md](design.md). Figures and defaults marked "proposed" are design-author choices, not independent standards.

## Owner decisions (2026-10-12)

The four items previously "decided by default" are now **OWNER-DECIDED**, with the changes below, plus a later owner correction (E) that makes the storage backends feature-identical, and two further owner decisions (F, G). Where E changes an earlier decision, the old wording is marked **SUPERSEDED** and the numbering is kept.

## Product and goals

1. EggMail is an open-source, self-hosted outbound email server (SMTP ingress, HTTP API, delivery tracking, dashboard) from eggspot. Primary goal: the fastest SMTP server, claimed only after reproducible measurement ([benchmarks.md](benchmarks.md)).
2. .NET 10 LTS (supported to 2028-11-14). Docker deployable.
3. **Two storage backends, feature-identical** (revised by E; the earlier "Lite = statistics only" is **SUPERSEDED**): PostgreSQL and SQLite, behind storage interfaces, with a shared core. "Lite" (SQLite backend + `History:Mode=StatsOnly`) and "Full" (PostgreSQL backend + `History:Mode=Full`) are friendly names for the two default presets; any combination is allowed (decision 29). Performance is a permanent first-class goal on **both** backends: the SQLite backend is engineered for large, high-throughput workloads and is not treated as a toy (decision 27).

## Build boundary

4. Hand-written, BCL-only SMTP stack: SMTP server and client (including BDAT/CHUNKING, full SMTPUTF8, PIPELINING, SIZE, 8BITMIME, ENHANCEDSTATUSCODES, STARTTLS, AUTH PLAIN/LOGIN), MIME, DKIM sign and verify (RSA-2048 only), SPF, DMARC, DSN/ARF, DNS client, MTA-STS, TLS-RPT, DANE. ARC is optional and deferrable. Enforced by CI: those assemblies have no package references.
5. Libraries allowed elsewhere: Npgsql + EF Core, Microsoft.Data.Sqlite, Certes (ACME), OpenTelemetry with OTLP, Data Protection, dashboard frontend stack, tests (MimeKit and MailKit as oracles only).
6. DANE uses a local validating resolver (Unbound on loopback). This is the one carve-out from "no external binaries".
7. One image, chiseled with ICU (the `-extra` variant) plus a startup Unicode self-test.

## Storage

8. PostgreSQL backend: Postgres only, via EF Core only. One database, one schema, three roles (owner, runtime, read-only). Minimum PG 16, default `postgres:17`. Managed HA is a deployment prerequisite; `451` during a database outage is accepted.
9. Tables: live queue unpartitioned and small; events and content day-partitioned; retention is partition drop (`DETACH … CONCURRENTLY`, then `DROP`), created ahead by an in-app job under a transaction-level advisory lock. Claim with native `FOR UPDATE SKIP LOCKED … RETURNING` through `SqlQuery<T>`. A pure-LINQ `ExecuteUpdate` claim is the test fallback.
10. Migrations: `Auto` by default (EF 9+ takes a database-wide lock), or `Never` plus `mta migrate-db` and a script. Two connection strings: schema owner and runtime.
11. No blob store. FS, S3 and R2 providers are dropped. R2 is removed. An `IMessageBodyStore` interface remains for a possible later provider.
12. Content (`History:Mode=Full`, on either backend): subject + text + html stored by default for 7 days (6–30). Raw message stays verbatim in `message_spool` until all recipients are final. Attachments are not stored unless enabled per tenant or per send (then raw is moved to `message_raw_retained`). Resend is available from retained raw; attachment-free messages can be re-composed. Event metadata kept 30 days.
13. SQLite backend (revised by E; the earlier "Lite mode: statistics only, no per-message history" is **SUPERSEDED**): SQLite in separate files (`queue.db`, `stats.db`, `config.db`, plus `history.db` when `History:Mode=Full`), single node, one replica, local volume only, multi-tenant like every backend. Characteristics, not missing features: single-writer ceiling, no partition drop (retention is batched `DELETE` plus `incremental_vacuum`), no built-in HA. Default `synchronous=OFF` for the data files (**owner-decided**; `config.db` stays `Full`, see F): **process-crash-safe, not power-loss-safe**. `250` means the data was handed to the OS, not fsynced; an OS crash or power loss can corrupt the database (per the SQLite docs) and lose all queued mail, including mail already acknowledged. Knobs: `Sqlite:SyncMode = Off | Normal | Full`, `Sqlite:ConfigSyncMode`, `Sqlite:QueuePersistence = Persistent | Memory` (renamed from `QueueDurability`; "durable queue" is retired). Startup integrity check, quarantine of a corrupt file, start empty with an alert, optional `VACUUM INTO` backups. Lite-preset defaults: `History:Mode=StatsOnly`, 48 h queue lifetime, 10 MiB max message. Statistics (hourly 30 days, daily 400 days, both may be unlimited with `0`, top-20/top-10 recipient domains, series cap) and the recent-events ring of 1,000 exist on every backend. Webhooks with a persisted outbox. No throughput cap.
14. **Backend switching is manual only, never automatic, and symmetric** (owner-decided; **SUPERSEDES** the earlier "Lite → Full guided switch" and the earlier "Full → Lite unsupported / config-only export"). One portable, versioned bundle (NDJSON plus manifest); a CLI (`mta migrate-storage --to postgres|sqlite`) and a guided dashboard action sharing one engine; steps preflight, drain/quiesce, export, import, verify, confirm, activate, finalize; source kept read-only until finalized; rollback possible. Config, suppressions, webhook endpoints and stats always move; queued mail moves only with `--quiesce` (drain-first is the default); per-message history moves only when `History:Mode=Full` on both sides. DKIM keys are re-wrapped for the target's key protection. See [design.md §4.6](design.md#46-switching-backends-manual-and-symmetric).
15. Two EF providers: one `DbContext`, separate migrations assemblies, provider-specific hot-path stores, a shared `IStatsStore` using `ON CONFLICT` upserts.

## Webhooks

16. Standard Webhooks signing, retry schedule immediate/5 s/5 m/30 m/2 h/5 h/10 h/10 h, 15 s timeout, 410 disables, disable after 5 days of failure, SSRF guard (validate resolved IPs, no redirects, HTTPS default), 7-day default outbox and attempt-log retention, configurable, `0` = unlimited (decision B).

## Network and TLS

17. Ports (each switchable): 587 STARTTLS, 465 implicit TLS, 2525 STARTTLS on by default; 2587 and 2465 off; port 25 bounce role only; plain only on loopback or internal networks. Container ports are high (5587, 4465, 2525, 2526) and mapped outward. Dashboard on 8080 (HTTP, probes) and 8443 (HTTPS), optionally published as 443.
18. Outbound: direct MX on port 25; relay fallback chain on 587, 465 or 2525 is opt-in per domain, with every delivery recording which route was used.
19. TLS: one shared certificate store; own `ServerCertificateSelector`; TLS 1.2 minimum; certificate hot reload by polling; ACME with Certes, DNS-01 default (Cloudflare first); outbound opportunistic by default with per-domain policy, MTA-STS enforce, TLS version, cipher and peer certificate recorded per attempt.
20. Domain verification: DKIM TXT with RSA-2048 (CNAME delegation optional later), return-path CNAME, SPF include optional, DMARC informational. State machine: the consolidated record is truncated after "State machine"; the proposed machine from the earlier domain-verification research is summarized in [design.md §8](design.md#8-domain-verification) and needs confirmation.

## Secrets and security

21. API keys shown once and stored as SHA-256 digests; SMTP auth PLAIN/LOGIN only; DKIM keys and the Data Protection key ring wrapped with a certificate or KMS. Encryption at rest is a storage-layer responsibility (envelope encryption deferred behind an interface).
22. Security review is in-house (STRIDE threat model, ASVS L2/L3, fuzzing, smuggling and STARTTLS-injection suites, port pen-tests, DoS tests, container hardening, cross-review and a red-hat week). An external audit is recommended before first production-critical use.

## Deployment

23. PostgreSQL backend: app + managed Postgres, via compose or Kubernetes; replicas above 1 are safe (no local blobs). SQLite backend: one container, one volume, one replica. Health: `--healthcheck`, liveness separate from readiness.

## Performance and plan

24. Pipelines-based server, zero-byte reads for idle connections, group-commit writers; durable and non-durable results always reported together, with the two backends benchmarked separately on the identical feature set (the SQLite default `synchronous=OFF` is a non-durable configuration); Postfix, KumoMTA and Haraka as baselines on the same hardware.
25. Estimate: about 272 engineer-weeks central (about 201–398): about 20 months with 4 engineers, about 37 with 2 ([plan.md](plan.md)). The +8 over the earlier 264 is new author estimates: Lite corruption handling, the symmetric switch engine, and history stores on SQLite.
26. Cut order: as listed in [plan.md](plan.md#cut-order).
27. **Design principle:** performance optimization is a permanent first-class goal on both backends. The SQLite backend is engineered to perform well for large and high-throughput workloads, not treated as a toy. Benchmarks cover both backends separately with identical feature sets ([benchmarks.md](benchmarks.md)).
28. **Retention convention:** a retention value of `0` means "keep forever"; negative values are invalid. Allowed for webhook outbox/attempt log, `Retention:MetadataDays`, `Stats:HourlyRetentionDays` and `Stats:DailyRetentionDays` (with documented disk-growth cost and manual cleanup). **Not** allowed for `Content:RetentionDays`, which stays 6–30 (floor: must outlive the 5-day queue lifetime; ceiling: personal-data and storage bound). Suppressions have no expiry. Same knobs on both backends; only the cleanup mechanism differs. Analysis in [design.md §5.1](design.md#51-retention-knobs-and-unlimited-retention).
29. **Storage backend and history level are orthogonal settings** (owner correction E): `Storage:Backend = Sqlite | Postgres` and `History:Mode = StatsOnly | Full`. Defaults follow the backend (SQLite: `StatsOnly`, 48 h queue lifetime, 10 MiB max message; PostgreSQL: `Full`, 5 days, 25 MiB), and any combination is allowed (SQLite + `Full`, PostgreSQL + `StatsOnly`). No feature is gated on the backend: the dashboard shows the same pages on both, and per-message lookups under `StatsOnly` return a clear `history_not_recorded` error (HTTP status to be decided). Backend differences are documented as characteristics ([design.md §4.2](design.md#42-backend-characteristics-not-feature-differences)).
30. **Portable bundle and effective settings:** switching backends carries the *effective* values of backend-dependent settings into the target explicitly, so behavior never changes silently; secrets are re-wrapped for the target's key protection and never written in clear; the importer refuses a non-empty target.
