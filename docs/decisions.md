## Product and goals

1. EggMail is an open-source, self-hosted outbound email server (SMTP ingress, HTTP API, delivery tracking, dashboard) from eggspot. Primary goal: the fastest SMTP server, claimed only after reproducible measurement ([benchmarks.md](benchmarks.md)).
2. .NET 10 LTS (supported to 2028-11-14). Docker deployable.
3. **Two storage backends, feature-identical** (revised by E; the earlier "Lite = statistics only" is **SUPERSEDED**): PostgreSQL and SQLite, behind storage interfaces, with a shared core. **SQLite is the default backend** (decision Q). "Lite" (SQLite) and "Full" (PostgreSQL) are friendly names for the two backends' default shapes with identical behavioural defaults, including `History:Mode=Full` (decisions J and 29); any combination is allowed. Performance is a permanent first-class goal on **both** backends: the SQLite backend is engineered for large, high-throughput workloads and is not treated as a toy (decision 27).

## Build boundary

4. Hand-written, BCL-only SMTP stack: SMTP server and client (including BDAT/CHUNKING, full SMTPUTF8, PIPELINING, SIZE, 8BITMIME, ENHANCEDSTATUSCODES, STARTTLS, AUTH PLAIN/LOGIN), MIME, DKIM sign and verify (RSA-2048 only), SPF, DMARC, DSN/ARF, DNS client, MTA-STS, TLS-RPT, DANE. ARC is optional and deferrable. Enforced by CI: those assemblies have no package references.
5. Libraries allowed elsewhere: Npgsql + EF Core, Microsoft.Data.Sqlite, Certes (ACME), OpenTelemetry with OTLP, Data Protection, dashboard frontend stack, tests (MimeKit and MailKit as oracles only).
6. DANE uses a local validating resolver (Unbound on loopback). This is the one carve-out from "no external binaries".
7. **A single image** (decision S, [release.md](release.md)), chiseled with ICU (the `-extra` variant) plus a startup Unicode self-test. It runs out of the box on the SQLite backend with one volume at `/data`; PostgreSQL is selected by configuration in the same image.

## Storage

8. PostgreSQL backend: Postgres only, via EF Core only. One database, one schema, three roles (owner, runtime, read-only). Minimum PG 16, default `postgres:17`. Managed HA is a deployment prerequisite; `451` during a database outage is accepted.
9. Tables: live queue unpartitioned and small; events and content day-partitioned; retention is partition drop (`DETACH … CONCURRENTLY`, then `DROP`), created ahead by an in-app job under a transaction-level advisory lock. Claim with native `FOR UPDATE SKIP LOCKED … RETURNING` through `SqlQuery<T>`. A pure-LINQ `ExecuteUpdate` claim is the test fallback.
10. Migrations: `Auto` by default (EF 9+ takes a database-wide lock), or `Never` plus `mta migrate-db` and a script. Two connection strings: schema owner and runtime.
11. No blob store. FS, S3 and R2 providers are dropped. R2 is removed. An `IMessageBodyStore` interface remains for a possible later provider.
12. Content (`History:Mode=Full`, on either backend): subject + text + html stored by default for 7 days (6–30). Raw message stays verbatim in `message_spool` until all recipients are final. Attachments are not stored unless enabled per tenant or per send (then raw is moved to `message_raw_retained`). Resend is available from retained raw; attachment-free messages can be re-composed. Event metadata kept 30 days.
13. SQLite backend (revised by E; the earlier "Lite mode: statistics only, no per-message history" is **SUPERSEDED**): SQLite in separate files (`queue.db`, `stats.db`, `config.db`, plus `history.db` when `History:Mode=Full`, which is the default), single node, one replica, local volume only, multi-tenant like every backend. Characteristics, not missing features: single-writer ceiling, no partition drop (retention is batched `DELETE` plus `incremental_vacuum`), no built-in HA. Default `synchronous=OFF` for the data files (**owner-decided**; `config.db` stays `Full`, see F): **process-crash-safe, not power-loss-safe**. `250` means the data was handed to the OS, not fsynced; an OS crash or power loss can corrupt the database (per the SQLite docs) and lose all queued mail, including mail already acknowledged. No acknowledgement setting is required; EggMail warns loudly instead (startup log, persistent dashboard banner, metric/health detail, README; decision P). Knobs: `Sqlite:SyncMode = Off | Normal | Full`, `Sqlite:ConfigSyncMode`, `Sqlite:QueuePersistence = Persistent | Memory` (renamed from `QueueDurability`; "durable queue" is retired). Startup integrity check, quarantine of a corrupt file, start empty with an alert, optional `VACUUM INTO` backups. Behavioural defaults are identical to the PostgreSQL backend (decision 29, J). Statistics and the recent-events ring exist on every backend. Webhooks with a persisted outbox. No throughput cap.
14. **Backend switching is manual only, never automatic, and symmetric** (owner-decided; **SUPERSEDES** the earlier "Lite → Full guided switch" and the earlier "Full → Lite unsupported / config-only export"). One portable, versioned bundle (NDJSON plus manifest); a CLI (`mta migrate-storage --to postgres|sqlite`) and a guided dashboard action sharing one engine; steps preflight, drain/quiesce, export, import, verify, confirm, activate, finalize; source fenced and kept read-only until finalized; rollback before activation, reverse switch after. Config, certificates/ACME state, suppressions, webhook endpoints and stats always move; queued mail moves with `--quiesce` (or is simply drained with `--drain`, the safe default); per-message history moves when `History:Mode=Full` on both sides (streamed, resumable, skippable, **in v1**, decision I). Secrets are re-protected through Data Protection (decision H). See [design.md §4.6](design.md#46-switching-backends-manual-and-symmetric).
15. Two EF providers: one `DbContext`, separate migrations assemblies, provider-specific hot-path stores, a shared `IStatsStore` using `ON CONFLICT` upserts.

## Webhooks

16. Standard Webhooks signing, retry schedule immediate/5 s/5 m/30 m/2 h/5 h/10 h/10 h, 15 s timeout, 410 disables, disable after 5 days of failure, SSRF guard (validate resolved IPs, no redirects, HTTPS default), 7-day default outbox and attempt-log retention, configurable, `0` = unlimited (decision B).

## Network and TLS

17. Ports (each switchable): 587 STARTTLS, 465 implicit TLS, 2525 STARTTLS on by default; 2587 and 2465 off; port 25 bounce role only; plain only on loopback or internal networks. Container ports are high (5587, 4465, 2525, 2526) and mapped outward. Dashboard on 8080 (HTTP, probes) and 8443 (HTTPS), optionally published as 443.
18. Outbound: direct MX on port 25; relay fallback chain on 587, 465 or 2525 is opt-in per domain, with every delivery recording which route was used.
19. TLS: one certificate store **in the database** (config store, both backends; decision K) serving SMTP and the dashboard through an own `ServerCertificateSelector`; TLS 1.2 minimum; certificate hot reload by polling the database, with an optional file/environment override; ACME with Certes, DNS-01 default (Cloudflare first); outbound opportunistic by default with per-domain policy, MTA-STS enforce, TLS version, cipher and peer certificate recorded per attempt.
20. Domain verification: DKIM TXT with RSA-2048 (CNAME delegation optional later), return-path CNAME, SPF include optional, DMARC informational. State machine: the consolidated record is truncated after "State machine"; the proposed machine from the earlier domain-verification research is summarized in [design.md §8](design.md#8-domain-verification) and needs confirmation.

## Secrets and security

21. API keys shown once and stored as SHA-256 digests; SMTP auth PLAIN/LOGIN only; DKIM keys and the Data Protection key ring wrapped with a certificate or KMS. Encryption at rest is a storage-layer responsibility (envelope encryption deferred behind an interface).
22. Security review is in-house (STRIDE threat model, ASVS L2/L3, fuzzing, smuggling and STARTTLS-injection suites, port pen-tests, DoS tests, container hardening, cross-review and a red-hat week). An external audit is recommended before first production-critical use.

## Deployment

23. SQLite backend (the default): one container, one volume at `/data`, one replica. PostgreSQL backend: app + managed Postgres, via compose or Kubernetes; replicas above 1 are safe (no local blobs). Health: `--healthcheck`, liveness separate from readiness.

## Performance and plan

24. Pipelines-based server, zero-byte reads for idle connections, group-commit writers; durable and non-durable results always reported together, with the two backends benchmarked separately on the identical feature set (the SQLite default `synchronous=OFF` is a non-durable configuration); Postfix, KumoMTA and Haraka as baselines on the same hardware.
25. Estimate: about 279 engineer-weeks central (about 206–410): about 21 months with 4 engineers, about 38 with 2 ([plan.md](plan.md)). The +15 over the earlier 264 is new author estimates: Lite corruption handling, the symmetric switch engine with quiesce, resumable history migration and Data Protection bundle protection, history stores on SQLite, orchestrator-aware cutover, certificates in the database, and the release automation (+0.5).
26. Cut order: as listed in [plan.md](plan.md#cut-order).
27. **Design principle:** performance optimization is a permanent first-class goal on both backends. The SQLite backend is engineered to perform well for large and high-throughput workloads, not treated as a toy. Benchmarks cover both backends separately with identical feature sets ([benchmarks.md](benchmarks.md)).
28. **Retention convention:** a retention value of `0` means "keep forever"; negative values are invalid. Allowed for webhook outbox/attempt log, `Retention:MetadataDays`, `Stats:HourlyRetentionDays` and `Stats:DailyRetentionDays` (with documented disk-growth cost and manual cleanup). **Not** allowed for `Content:RetentionDays`, which stays 6–30 (**OWNER-DECIDED**, decision O; floor: must outlive the 5-day queue lifetime; ceiling: personal-data and storage bound). Suppressions have no expiry. Same knobs on both backends; only the cleanup mechanism differs. Analysis in [design.md §5.1](design.md#51-retention-knobs-and-unlimited-retention).
29. **Storage backend and history level are orthogonal settings** (owner correction E): `Storage:Backend = Sqlite | Postgres` (default `Sqlite`, decision Q) and `History:Mode = StatsOnly | Full`. **Defaults are identical on both backends (decision J): `History:Mode=Full`**, with `StatsOnly` one setting away as the lightweight option; any combination is allowed. No feature is gated on the backend: the dashboard shows the same pages on both, and per-message lookups under `StatsOnly` return `410 Gone` `history_not_recorded` (decision M). Backend differences are documented as characteristics ([design.md §4.2](design.md#42-backend-characteristics-not-feature-differences)).
30. **Portable bundle and effective settings:** switching backends records the *effective* values of all settings in the bundle and writes them explicitly into the target, so behavior never changes silently; secrets are re-protected through Data Protection and never written in clear; the importer refuses a non-empty target that does not carry the same switch id.
31. **Secrets in the bundle** use Data Protection with a bundle-specific key ring protected by a passphrase-protected throwaway certificate; the target re-protects under its own ring (decision H).
32. **Quiesce semantics:** stop accepting (`421`/`503`), wait for in-flight deliveries up to `Switch:QuiesceTimeoutSeconds` (default 30), then requeue what remains with the same message id and retry state preserved and a `possible_duplicate` flag/event (decision R); durable source fence, transfer marks, ids and idempotency keys preserved, target does not dispatch until activated, rollback before activation (decision I).
33. **History migration** is in v1: chunked, checksummed, resumable, skippable, and can backfill after activation; throughput and time are unmeasured.
34. **Certificates and ACME state in the database**, DP-protected, with a renewal lease and database polling for hot reload (decision K).
35. **History API status:** `410` for not recorded or expired content, `404` for unknown, `200` with `body_expired` for the message resource (decision M).
36. **Configuration precedence and cutover** under orchestrators (decision N).
37. **Default backend and single image:** `Storage:Backend` defaults to `Sqlite`; one Docker image serves both backends (decisions Q, S).
38. **Loud warnings for `synchronous=OFF`:** startup log warning, persistent dashboard banner, metric and health detail, README text; no acknowledgement gate (decision P).
39. **Release plan:** [release.md](release.md): GHCR `ghcr.io/eggspot/eggmail`, tags `vX.Y.Z`, `X.Y`, `latest`, `nightly`; `GITHUB_TOKEN` with `packages: write`; SBOM and provenance; GitHub Release with changelog and checksums; the package must be made public once by hand (decision S).
40. **Funding:** policy draft in [funding.md](funding.md); no feature gating or priority code for sponsors; other platforms (Open Collective, Ko-fi, Liberapay, custom links) are added to `FUNDING.yml` only when the owner names them (decision T).

## Implementation decisions (DESIGN-DECIDED during implementation)

Choices the implementation forced that the design left open. Each can be reversed; the reason is given so a reviewer can judge it. Component details are in `docs/components/`.

41. **Bounce addresses are stateless VERP tokens** `b+<base32>@<bounce domain>` (`Delivery:BounceDomain`): version and key id, tenant id, the first 8 bytes of the sending domain's id, hours since an epoch (24 bits) and a truncated HMAC-SHA-256, with key rotation. The delivery engine uses it as the SMTP envelope sender for mail that is not itself a bounce; the original sender is kept for the bounce message (DSN). Async bounces and complaints are correlated to the tenant by the token only; the body decides which addresses are suppressed. *Reason:* no per-message bounce state, works the same on both backends.
42. **Only a recipient-specific permanent failure suppresses** (`PermanentRecipient` class from the reply classifier, and asynchronous DSNs classified the same way). Sender, policy, content and configuration failures bounce without suppressing. *Reason:* a wrong suppression silently stops mail to a valid address.
43. **Bounce messages (RFC 3464) are generated for SMTP-submitted mail only by default** (`Delivery:GenerateDsnForSmtpSubmissions`); API senders learn through webhooks. The bounce is queued before the failed delivery is recorded (a crash can duplicate a bounce, never lose one).
44. **Local holds are not attempts.** A sending-limit or destination-throttle hold reschedules the delivery without counting an attempt, writing an event or notifying webhooks (`DeliveryAttempt.CountAttempt`). *Reason:* otherwise throttling would advance the retry ladder and spam history.
45. **Events that are not tied to a delivery attempt** (asynchronous bounce, complaint) enter the webhook outbox through `IWebhookOutbox.EnqueueAsync`.
46. **Retry defaults** (not specified by the design): 2 m, 5 m, 15 m, 30 m, 1 h, 2 h, 4 h, then every 4 h until the 5-day lifetime ends, ±10 % jitter; greylisting 5–15 m; throttling at least 10 m. All are options (`docs/components/policy.md`) and unmeasured.
47. **DKIM private keys** are stored as PKCS#8 DER protected with Data Protection (purpose `EggMail.Secrets.DkimKey.v1`); the signing key of a domain is its newest active key, and a sending subdomain signs as its nearest registered parent domain.
48. **The Data Protection key ring is stored in the settings table** (`dataprotection.key.*`) and never deleted, so a backend switch and a restart see the same ring; `Secrets:KeyProtection=Certificate` encrypts it, `Kms` wraps it with an external key (decision 79), `None` is development only and logs a warning at startup. A stored ring must match the configured protection or the start is refused (decision 79).
49. **API keys** are `egm_` + 8-character id + `_` + 43-character secret (positional layout; base64url can contain `_`), stored as SHA-256 digests.
50. **System-originated mail** (TLS-RPT reports) uses the empty tenant id and source `System`; it is never answered with a bounce message.
51. **Domain records:** DKIM TXT and the return-path CNAME (`bounce.<domain>` pointing at the operator's bounce domain) decide verification; SPF and DMARC are advice. A DNS failure during a check is a temporary failure and never marks a domain as missing records.
52. **Merge gate without CI (superseded 2026-10-13):** GitHub Actions was disabled for the repository by the organization, so pull requests were merged after a full local `dotnet test` and review. Actions is enabled now: `ci` is the merge gate and a pull request is merged only when it is green.
53. **ACME is tested against Pebble in CI; the account is stored when the CA creates it** (DESIGN-DECIDED): the single `build-test` job starts `ghcr.io/letsencrypt/pebble` and `pebble-challtestsrv` (pinned tags) with `docker run` and the Integration tests run the real issuance/renewal flow with DNS-01 validated for real; they are skipped without `EGGMAIL_TEST_ACME_DIRECTORY`. Findings fixed on the way: the ACME account is persisted before the order can fail (otherwise every retry registered a new account at the CA), every failure of an attempt is recorded with back-off (an HTTP timeout used to end the renewal loop), `badNonce` repeats the order, and the dashboard HTTPS listener serves through a TLS handshake callback so the intermediate certificates are sent. DNS-01 stays the only challenge type and EAB is not supported (decision 19); both would be new design decisions ([components/acme.md](components/acme.md)).
54. **Domain verification keeps its per-record results in the store and runs under a lease.** The result of the last check of each record (`domain_record_check`) is replaced as a set by every check, kept for records a DNS outage could not look up (an outage never changes the state), and deleted with the domain. A check ("Verify now" and the scheduled pass) and a DKIM rotation take the lease `domain-verification:<domain id>` of the config store (five minutes, released at the end; the existing lease facility, the same one the ACME renewal uses) besides the in-process guard, and the scheduled pass re-reads the domain after taking it, so two replicas never check or rotate one domain at once or check it twice in a row. *Reason:* after a restart or on another replica the dashboard guessed `ok`/`pending`; two replicas could count one failure twice.
55. **State the process kept in memory is persisted in the config part, written behind.** The per-record DNS results (54), the TLS-RPT counters and unsent reports (`tls_rpt_bucket`, an append-only journal of collector flushes, merged when a completed day's report is sent) and the sending counters (`sending_counter`, flushed as deltas and read back, so replicas add to each other with a lag of one flush interval) live in the config part (schema version 4: SQLite `user_version` 4, PostgreSQL `V004`), reach the storage through `IRuntimeStateStore` on the config store (one EF implementation for SQLite and PostgreSQL, one in-memory implementation), and move in the backend switch bundle (format 1.2.0; the source flushes when it quiesces; counters import as an upsert). Flush every 10 s (counters) and every minute (TLS-RPT) and at shutdown; a crash loses at most that window; a report sent but not yet deleted is sent again. *Reason:* the config part is the durable file and always travels with the bundle; the rows are tiny and batched, so the fsync cost of `ConfigSyncMode=Full` is one per flush; the stats writer is lossy by design.
56. **Asynchronous bounces and complaints are attached to the message history by `Message-ID`.** The normalized (no angle brackets, lower case) `Message-ID` header is stored on `message_index` (`History:Mode=Full` only, indexed with the tenant); the verified VERP token names the tenant, the `Message-ID` of the returned headers finds the tenant's newest message with it, and a `bounced` or `complained` event is appended (recipient, enhanced code, diagnostic), moving a `delivered` message to `bounced` (`partial` with several recipients) or `complained`. `StatsOnly` stores nothing per message, so nothing is attached; suppression and webhook are unchanged and the webhook carries `message_id` when a message was found. A failure to attach never fails the bounce handling. Accepted trade-off: a report is authenticated only by the signed bounce address, which any recipient of the tenant's mail can reconstruct from the Return-Path, so such a party who also knows another message's `Message-ID` (random for server-generated ids, possibly guessable when a client chose it) can add a `bounced`/`complained` event to that message; the same party could already suppress arbitrary addresses (decision 42). The reported recipient is not required to be a recipient of the message, because bounces from forwarding hops name the final recipient. *Reason:* the token carries no message id (decision 41, stateless), and the header is the only correlation the remote server returns.
57. **Message `tags` are stored on the history index** as a JSON array (`message_index.tags`, `History:Mode=Full`), returned as `tags` by the messages list and detail and searched with `?tag=` (exact whole-tag match: `json_each` on SQLite, `jsonb_exists` on PostgreSQL, no separate table). *Reason:* tags are small, read with the row, and share its retention; a table per tag would add a partitioned history table to every backend for a filter that is already bounded by the other search filters.
58. **Global settings stay "applied at the next start".** The stored-settings layer (decision N layer 4) applies them below every deployment layer when the process starts, and every global setting is returned with `requiresRestart: true`; no setting of the design is documented as live, so no live path was added. The per-tenant `Sending:PerHour`, `Sending:PerDay` and `Webhooks:AllowedNetworks` were already live. *Reason:* the options they feed (storage retention, history mode, global caps) are constructor options of components that do not support changing them while running. Found while testing this: the API stores the queue lifetime as `Queue:MaxLifetimeDays` (whole days) but the configuration key is the time span `Queue:MaxLifetime`, so a stored value was silently ignored at the next start; `StoredSettings` now translates it (a test applies every editable global setting through the loader).
60. **One name for the queue lifetime in the settings layer.** `Queue:MaxLifetimeDays` (whole days) is the key the settings API stores (docs/api.md), so the loader reads it; `Queue:MaxLifetime` (a time span) stays as the documented deployment spelling and wins when both are set. *Reason:* the settings page wrote a key the loader never read, so a saved value silently did nothing. A deployment that sets either spelling locks the setting.
61. **The stored-settings layer keeps the layered configuration and is not a deployment lock.** After global settings are applied the loaded configuration still carries its source (the switch reads `SwitchTarget:*` and rewrites the bootstrap layer from it), and the activator ignores a value that came from the config store when deciding whether the deployment fixes a key. *Reason:* saving any global setting used to break the switch flow.
62. **List settings.** `Acme:Domains` and `Api:MetricsAllowedNetworks` accept indexed entries or one value separated by commas (environment-variable friendly). `Webhooks:RetrySchedule` and `Delivery:RetryDelays` replace the built-in ladder instead of extending it (the configuration binder appends to a non-empty default, which had turned a configured webhook schedule into "the default, then these").
63. **Configuration documentation is enforced by a test** (`ConfigurationDocumentationTests`): every key the loader reads must appear with its full name in `docs/operations.md`, and every key-shaped name in that guide must be read by the code. *Reason:* about a hundred keys were read by the code and missing from the guide, and `Acme`/`Tls` were documented but never bound.
64. **A submitted message is parsed once** and the parse serves the sender check, the header repair and the history extraction (**DESIGN-DECIDED**). The extractor runs on the parse of the submitted bytes, not of the stored copy: only headers are added or removed, so subject, bodies and attachments are identical. The one subtle case is a Bcc behind the header-count or header-size limit, which the parsed list does not record; the Bcc rule therefore stays unless the parsed list is complete and has no Bcc. *Reason:* the message was parsed three times per submission (3 KB and several microseconds each).
65. **Hot SQLite statements use the native API instead of `SqliteCommand`** (**DESIGN-DECIDED**): writer commands are prepared once per writer connection and bound with typed `Set` calls; the raw-message read and the suppression check run on open read connections with prepared statements (`SqliteReadSessionPool`, released by `SqliteFile.ClearPool`, which only the quarantine of a file and the disposal of the storage call; idle sessions are capped at 64 and closed after 60 s). Stored values stay byte-identical (upper-case Guid text, empty text and blobs not NULL), and the cold paths (history queries, maintenance, schema) keep using Microsoft.Data.Sqlite and EF Core. *Reason:* `Microsoft.Data.Sqlite` cost about 1.5 KB and a statement compile per execution, and EF Core registered the provider's SQL functions on every connection open (15 KB per suppression check); together about 60 % of the SQLite ingest allocation and 80 % of the storage cost of a delivery. PostgreSQL is unchanged except that it answers `IWebhookOutbox.MayHaveSubscribers` from its endpoint list.
66. **Webhook event payloads are built only when an enabled endpoint could receive them** (`IWebhookOutbox.MayHaveSubscribers`, **DESIGN-DECIDED**). The answer comes from the same cached endpoint list the fan-out uses and is "maybe" whenever that list is not current, so it cannot skip an event the fan-out would have queued. *Reason:* about 6 KB of JSON per delivery attempt was built and discarded when no endpoint exists.
67. **Allocation budget wording and status** (**DESIGN-DECIDED**; the budget itself is unchanged). "Excluding body buffers" means the stored copy of the message, the history copy of the bodies as strings and, on delivery, the message read from the spool. Measured after this round: SMTP protocol path 1.1 KB (met), whole ingest path 4.8 KB with a tiny body on SQLite (not met), delivery 25.5 KB per recipient. The remaining gap is structural (see [benchmarks.md](benchmarks.md#allocation-work-second-round-2026-10-13)) and is not closed by relaxing the budget.
68. **Async methods on the hot paths use pooled `ValueTask` builders** (`PoolingAsyncValueTaskMethodBuilder`): the SMTP session and client, the ingest handler, the submission service, the SQLite intake and queue store, and the delivery processor's private methods. Each such `ValueTask` must be awaited exactly once. *Reason:* each unpooled state machine box was 100 to 500 bytes per call and a message makes a dozen calls.
69. **Observability design:** (a) the trace id of every span about a message is the message id and all spans share one parent span id derived from it (`MessageTrace`), so submission, queue wait, each delivery attempt and each webhook form one trace across retries and replicas with no trace context stored in the queue or the webhook outbox. The shared parent is not itself exported (tracing UIs show a missing root). The alternative, a stored `traceparent` column per queue row and outbox row, would change both backends' schema and the switch bundle for little gain. (b) `Observability:TraceSampleRatio` defaults to 0.1 and is applied to the message id before any span exists (`MessageTrace.IsSampled`: the 62 random bits of the id against the ratio), so a message is traced in all spans or none and an unsampled message creates no `Activity` at all (OpenTelemetry's own ratio sampler still allocates an activity per dropped span); an MTA at thousands of messages per second would otherwise export several spans per message. The exporter's sampler is `AlwaysOn`, and the ratio is a process-wide setting (`MessageTrace.SampleRatio`). (c) Queue depth and oldest-due-age gauges read a sample refreshed by one background task every `Observability:QueueSampleSeconds` (default 15), never a query per scrape, because `GetQueueStatsAsync` reads the whole queue table; staleness is itself a metric. (d) PostgreSQL command latency and pool state are Npgsql's own `db.client.*` instruments, exported unchanged, instead of a second set of wrappers around every command; the data sources are named so the pool label is not the connection string. (e) Metric labels are fixed small sets; there is no domain, tenant or recipient label, and the Prometheus exporter caps a metric at 1000 label combinations. (f) The SQLite state facts (`sync_off`, quarantined files) are gauges rather than counters because they happen before any exporter exists. *Reason:* the operations guide told operators to alert on things that had no metric.
70. **Outbound 8-bit and internationalized mail (RFC 6152, 6531, 6532, 6533)** (DESIGN-DECIDED): what is sent is decided per server after its EHLO. `BODY=8BITMIME` only when the body has 8-bit bytes and the server offers it; otherwise the body is converted to 7-bit (quoted-printable or base64, composite entities processed recursively, never encoded as a whole except `message/global`) and **then** DKIM-signed, so the signature covers the transmitted bytes. When no safe conversion exists the delivery fails permanently with `5.6.1` and a reason; it is not retried, and the recipient is not suppressed. `SMTPUTF8` is declared when the header section holds valid UTF-8 or an address has a non-ASCII local part (an IDN domain is sent as its A-label and needs nothing); a server without it gets nothing (`5.6.9` headers, `5.6.7` addresses, per recipient when only recipients are affected). *Reasons:* a downgrade that can corrupt mail is worse than a bounce; header downgrading (RFC 6857) is experimental and has no deployed convention, so it is not attempted. A refusal for lack of an extension is final only when every candidate host was asked and refused; an unreachable host, or one that was not asked in this attempt (breaker, cap), makes it a temporary failure, and recipients whose address a host cannot take are offered to the remaining hosts before they fail. A capability refusal does not reroute through a relay (relays are for blocked port 25, decision 18). Mail with UTF-8 header fields now bounces (`5.6.9`) instead of being sent as is to a server without SMTPUTF8 (behaviour change, RFC 6531). The SMTPUTF8 flag of a message is decided at intake from its header bytes, not from the submitter's MAIL FROM parameter (a client that declares it only for an address would otherwise make every transaction of the message demand it), and is stored per queued delivery (schema version 5, PostgreSQL `V005`). Bounce reports for internationalized recipients use `message/global-delivery-status` (RFC 6533). TLS-RPT reports the connection's local address only when it is public (or `Delivery:PublicSendingIp` when configured).
71. **Dashboard is tested end to end in a real browser against the real server** (Playwright, Chromium only, in the existing CI job after the unit tests; fake DNS, recipient SMTP and webhook receiver stand in for the internet). *Reason:* the mock API had hidden contract differences (a `verifying` switch state, an activation patch that exists only after `activate`, attempt and event columns the server never fills, a bootstrap file looked up in `/data` when the data directory was given on the command line). Where the dashboard and the API disagreed, the server was changed only for real defects (the bootstrap path, `Cache-Control` of the static files, `orchestratorManaged` and `direction` reported from the start and after a restart); otherwise the dashboard follows the documented API.
72. **Coverage-guided fuzzing uses SharpFuzz with libFuzzer (`libfuzzer-dotnet`), not AFL++.** *DESIGN-DECIDED.* Reason: `libfuzzer-dotnet` has a prebuilt Linux release that the workflow pins and checksum-verifies, so the fuzz job needs no compiler or source build; libFuzzer keeps the instrumented .NET process alive between inputs (thousands of executions per second) and saves timeout inputs itself. The harness and targets live under `fuzz/` (`Mta.Fuzz.Harness`, which alone references the `SharpFuzz` package, and `Mta.Fuzz.Targets`); no protocol assembly references them and the architecture test guards that. The workflow runs weekly and on demand and is never a pull request check (billing rule: one job, the cheapest runner, a tight timeout).
73. **The unit test suite asserts no wall-clock time, throughput or process memory.** *DESIGN-DECIDED.* Reason: a Dkim throughput assertion failed 19 of 30 runs under heavy parallel load (reproduced), the same pattern existed in the MIME, DNS, storage and API tests, and the CI runner is a loaded two-core machine. Waits are signals or polls with generous deadlines; hang guards are minutes, not seconds; bounded work is asserted on results and on the allocated bytes of the running thread; throughput is measured by `bench/`.
74. **Attachment storage precedence is per-send flag, then tenant setting, then global default, behind the master switch; SMTP uses the same chain without the per-send flag (DESIGN-DECIDED).** Design section 5 says "SMTP ingress uses the tenant setting only"; read strictly, a tenant that never chose would store nothing whatever the operator default, which makes the global default useless for SMTP and differ from the API. So an SMTP submission uses the tenant's setting and, when the tenant never chose, the operator default, i.e. `perSend ?? tenant ?? global` with `perSend` always absent. The tenant record only has a boolean, so "never chose" is the absence of the tenant-scoped settings row `Content:StoreAttachments` (the older `tenants.store_attachments = true` still counts as a choice of yes; no schema change). The resolution lives in `SubmissionService` (`AttachmentStoragePolicy`), looks the row up only for a message that has attachments while the master switch is on, and caches it per tenant for `SubmissionOptions.DomainCacheTtl` (a change made through the settings API shows at once). A resend does not pass a per-send flag, so it cannot override a tenant's opt-out. *Reason:* the API used `tenant || global` (a tenant could not turn storing off under a global yes) and SMTP ignored the tenant setting. **Upgrade effect:** SMTP submissions with attachments are now kept after delivery wherever the tenant chose yes or the operator default (`Content:StoreAttachments` with `Content:AllowAttachmentStorage`) is yes, which uses more disk than before (operations.md, Upgrades).
75. **The release image is built with ReadyToRun** (DESIGN-DECIDED; `READYTORUN=true` in `release.yml`, default `true` in the Dockerfile; trimming stays off). Measured on GitHub-hosted runners, three runs: about 30 % faster cold start and restart (for example 1.83 s to 1.30 s), +23.7 MiB of application files (+25 MB image), steady-state ingest unchanged within noise, linux-arm64 cross-compilation works on the amd64 runner. Rule applied before measuring: at least 25 % start-up gain and under 30 MiB growth. Details and numbers: [release.md](release.md). *Reason:* the cost is disk, the gain is on every rollout and restart, and the design (§10) asked for it.
76. **The allocation regression gate uses two measurements and two thresholds** (DESIGN-DECIDED): per-step bytes per call (exact; fail above +5 %) and total allocation per accepted message through the real runtime (fail above +10 %; about 2 % noise between runs). It runs weekly and on demand, never on pull requests, against `bench/baseline/allocations.json` recorded on a GitHub-hosted runner. Throughput is never gated on shared runners. 77. **Deployment files are tested by the release workflow against the pushed image, with the instance's DNS pointed at a test stub** (DESIGN-DECIDED): `deploy/smoke/smoke.py` serves the DKIM record and an MX that leads to its own SMTP sink, so domain verification, authenticated submission and delivery are real without Internet DNS. The image test and the PostgreSQL compose test run on every build, including the daily nightly; the SQLite compose, Unbound and Kubernetes (kind) checks run for tags and manual runs only, to keep billed minutes down. The image is pushed by digest, tested, and only then tagged (`docker buildx imagetools create`), so a tag never points at an image that failed; version tags are never moved and a manual run can never create one. Container healthchecks use `/app/mta` (the chiseled image has no `mta` on `PATH`).
78. **Unicode self-test fails fast.** `mta serve`, `migrate-db`, `migrate-storage` and `admin` run the self-test of design section 10 before they open any storage and exit with code 71 and an actionable message when IDN or normalization give wrong answers (invariant globalization mode, missing ICU); `Startup:RequireUnicodeSupport=false` downgrades it to a warning. `mta self-test` exposes the same test, and the release workflow runs it against the published image. *Reason:* a wrong A-label is silent (the registered sender domain stops matching); a fatal start is cheaper than mail from the wrong identity. The design left "fail" versus "warn" open.
79. **`Secrets:KeyProtection=Kms` is a pluggable key-wrapping provider, with one built in (DESIGN-DECIDED).** The design lists `Kms` but names no service and the repository has no cloud account. So `Kms` means: every Data Protection key-ring element is wrapped by an `IKeyWrapProvider` (`Wrap`/`Unwrap`, authenticated, never exposes the key) selected by `Secrets:KmsProvider`. The built-in `LocalKey` provider uses AES-256-GCM with a 32-byte key from `Secrets:KmsKeyFile` (preferred) or `Secrets:KmsKey`; the wrapped element records the provider name and an HMAC key id, which are also authenticated data, so a wrong key is reported by name. Protocol assemblies and the host reference no cloud SDK; cloud providers (AWS KMS, Azure Key Vault, Google Cloud KMS) are not written because they need the owner's cloud account to be verified ([open-questions.md](open-questions.md)). A custom provider is registered with `KeyWrapProviders.Register` from a custom build of the host (there is no plug-in loading). **The stored ring must fit the configuration**: Data Protection treats a key it cannot read as missing and may create a new one, silently stranding the old secrets, so at start the ring is inspected first: a wrong Kms key, certificate-encrypted keys without that certificate, Kms keys without Kms, all stop the start (exit 2) with a message that names the keys and the fix; a ring that still holds keys written in the clear only warns. Changing `Secrets:KeyProtection` on an existing ring is supported only through `mta secrets rewrap` (clear to Kms or certificate, previous Kms key to the configured one; dry run unless `--apply`). The backend switch counts a source as protected only when no key is stored in the clear. No key rotation otherwise: a different key cannot open an existing ring. *Reason:* this covers the real need behind the row (a wrapping key that is not in the database, e.g. from a secret manager that mounts files) without code nobody can test, and keeps the seam for the cloud services.
80. **The read-only PostgreSQL role of design section 4.3 is implemented for the read queries of the dashboard and the HTTP API.** `Storage:Postgres:ReadOnlyConnectionString` (optional, must name a `Username`, must point at the primary) routes the history search/detail/events/retained-raw/recipients and the statistics reads, which serve the dashboard and the API's `GET /messages*` and `GET /stats*` alike, to a data source whose connections carry `statement_timeout` (5 s), `idle_in_transaction_session_timeout` (10 s) and `default_transaction_read_only=on` as startup options; the migration grants that role `SELECT` on exactly the seven tables those reads touch (and never on a secret table). A statement the server stops at the timeout (SQLSTATE 57014, when the caller did not cancel) is a `StorageQueryTimeoutException`, answered `503 query_too_slow` without `Retry-After` (the same query will time out again; narrow it): it is neither an outage (`not_ready`) nor a server error, and a statement the caller cancelled stays an `OperationCanceledException`. Health reports `read_only_role` and warns (never `Ready=false`) when the role is unusable (`postgres_read_only_unavailable`) or can write a history table or read any other table (`postgres_read_only_role_too_privileged`). *Reason:* the design specifies the role and the timeouts; a heavy message search must not be able to starve the queue. Startup options rather than `SET` because the pool resets sessions; the cost is that a pooler in transaction mode has to pass the `options` parameter. The backend switch carries the string (and a non-default timeout) to the target's pointer as a secret setting, so a switch does not silently drop the role. On PostgreSQL before 15 `CREATE` on schema `public` is granted to everyone: revoke it (operations.md).
81. **Replicas on one PostgreSQL database share exactly the state for which a per-process copy is wrong or unsafe, and the rest stays per process** (DESIGN-DECIDED). Decided piece by piece, with the evidence in `tests/Mta.Integration.Tests/MultiReplicaTests.cs` (real runtimes over one PostgreSQL; in CI with `EGGMAIL_TEST_POSTGRES`, locally with installed PostgreSQL binaries) and `tests/Mta.Policy.Tests/ReplicaCoordinatorTests.cs`. One vocabulary: *replica coordination* is what the replicas of a deployment exchange through the database (`IReplicaCoordination`, the `ReplicaCoordinator` that runs it):

    | State | Decision | Why |
    |---|---|---|
    | Failed-login budget (`AuthThrottle`, SMTP AUTH and the API sign-in) | **Shared** in the database: failures per key, stored as an HMAC-SHA256 digest under a Data Protection-protected key, in buckets of a fifteenth of the window. Cost: one indexed read per login attempt, one small write per failed attempt, and one delete only after a successful login whose read found failures on record for the keys it clears (none otherwise, so an ordinary login costs the read only). Writes are not cancelled with the request and are bounded to 2 s; falls back to the process's own counts if the database cannot be reached or answers too slowly; in memory on SQLite | Security: with N replicas behind a load balancer the budget was N times larger, and an attacker needs no cleverness to spread attempts. A login already costs a PBKDF2 verification of 600,000 iterations and a credential lookup, so one more small statement is noise, and nothing is added to the mail path. The key is a digest so that a copy of the table says nothing about which addresses or user names failed; SMTP AUTH and the API normalize user names the same way, so an account has one budget whichever door is used |
    | Per-destination connection and rate ceilings (`DestinationThrottle`) | **Shared out**: every replica takes its share of each ceiling, computed from the live replica set (a heartbeat row every 5 s; a replica silent for 20 s drops out; a leaving replica deregisters). Learned limits are rescaled from an exact fraction when the set changes, so a flapping set cannot ratchet them up | Politeness to remote servers is a promise about the installation, not about a process: 3 replicas at the default ceiling would open 60 connections to one provider. The share is arithmetic on a number that changes every few seconds, so the hot path never waits for the database. A static share cannot move spare capacity to a busy replica; claims are spread evenly by `SKIP LOCKED`, so the loss is small, and the safe side of the error is sending less |
    | What a destination told one replica (a throttling reply, a burst of refused connections) and open circuit breakers (`RouteHealth`) | **Eventually shared**: published as short-lived signals on the next round (at most 5 s later) and adopted by the others, never echoed back. A slowdown is the same multiplicative decrease with its cooldown. An open circuit is adopted **with bounds, so that one sick replica (its own network, its own egress address) cannot open circuits fleet-wide**: only MX hosts (a `route:` circuit is never adopted, since it would take a relay out of every plan), for at most the base cooldown (5 min) from the moment of adoption whatever cooldown the other replica has backed off to, and not at all for a host this replica connected to within the last 2 minutes. Closing a circuit is not propagated: every replica probes for itself once its cooldown is over, and a circuit that closes early on its originator stays open on the others for the rest of their (at most 5 minute) adoption | A destination that throttles one IP throttles all replicas that share it, and a down MX would otherwise cost every replica its own five timed-out connections and its own probes. Sharing "closed" would need a distributed probe slot for little gain: a probe is one connection per replica per cooldown. The bounds trade a little repeated probing (a replica whose peers are right still learns the rest by its own failures) for a hard limit on what a wrong peer can cost |
    | Sending counters behind the caps and the warm-up (`SendingCounterPersistence`) | **Already shared** by decision 55 (deltas, lag of one flush interval). **Not made exact**: a cap can be overshot by at most what the other replicas send in one flush interval (10 s) | An exact cap across replicas needs a database round trip per reservation or leased blocks of the cap with a prefetching loop; a plain fair share of the remaining headroom was analyzed and rejected because replicas see each other's usage at different moments and can still overshoot, so it would add complexity without a guarantee. Caps protect reputation and quota; operators who need a hard ceiling set the cap lower by what their replicas send in 10 s |
    | TLS-RPT collector and sender | **Already coordinated** by decision 55 (append-only journal of flushes, merged when the day is complete, sender under a ten-minute lease renewed per report); now proven with three runtimes sending at the same moment: one report per domain and day, with everyone's counts | Nothing to add. A crash between sending and deleting still sends the report again (at-least-once) |
    | Domain verification, ACME renewal, certificates | **Already shared** (leases, decisions 54 and K) | |
    | `SendBudget` (bytes of API request bodies in flight), SMTP connection limits (`MaxConnections`, `MaxConnectionsPerIp`, `MaxInFlightBytes`), connection pool, MTA-STS, DKIM, DNS and domain-id caches | **Per process, by nature** | They protect this process's memory, sockets and file descriptors, or are caches whose worst case is one extra fetch. Behind a load balancer the per-address connection limit is per replica |

    The coordination lives in `Mta.Policy.ReplicaCoordinator`, behind the optional `IStorage.Replicas` (`IReplicaCoordination`), implemented by PostgreSQL (three tables, `replica_heartbeat`, `replica_signal`, `auth_failure`, schema version 6, written with single atomic statements on a pool of two connections of its own, so claims cannot starve the heartbeat) and by the in-memory backend (so several runtimes over one `InMemoryStorage` behave like replicas in tests); it is `null` on SQLite, which is one process by design. The tables are ephemeral and are not part of the backend switch bundle. **Clocks:** heartbeats, liveness, signal validity and retention use the database server's clock and signals are durations, so replica clocks are never compared for the replica set and the signals; the failed-login buckets use each replica's own clock and tolerate a skew of about one bucket (1 minute); leases keep their existing assumption. A round that fails or takes more than 4 s keeps the last share and the unpublished signals (the newest per key, dropped once they have ended). **Partition:** a replica cut off from the database for longer than 20 s is dropped by the others while it keeps its old share, so for that time the shares add up to more than a ceiling; it rejoins at its next successful beat (an outage that long stops its claims as well). A replica that has just started joins before the delivery engine starts; the others learn of it within 5 s, and in those seconds the sum of the shares can exceed a ceiling. **Rolling updates:** an older build does not take part, so during a rollout the new replicas share the ceilings and the failed-login budget among themselves only (see operations.md).
82. **A report of an attempt whose lease another replica has taken over is flagged `possible_duplicate` too** (DESIGN-DECIDED; found by the two-replica chaos test). Claiming a delivery whose lease expired sets the row's `possible_duplicate` flag and the claimer's attempt carries it, but the replica that was still sending when its lease ran out did not know, so when it finished first it recorded a plain `delivered` although the other replica might send as well: the remote then held two copies and nothing said so. The attempt planner now also looks at the row's flag when an attempt is recorded (all three backends, one shared function). *Reason:* the promise is that a message reaches a remote twice only where it is flagged; the lease length (default 15 minutes) makes this rare, not impossible.
